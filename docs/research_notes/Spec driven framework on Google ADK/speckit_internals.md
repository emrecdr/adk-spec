# GitHub Spec Kit internals (state as of 2026-11-20)

Provenance: almost everything below was read directly from a shallow clone of `github/spec-kit` `main` at commit `a4d571229e164e440f8950cac034607bae7b7518` (committed 2026-11-20, "fix(extensions): describe extension list options accurately (#5496)"). Links point at `blob/main`; if `main` has moved, pin to that commit. The clone was only read, never executed. Short quotes are verbatim from the files cited.

Important framing for the reader: Spec Kit in November 2026 is much larger than the 2025 "templates plus three slash commands" kit. It is now a Python CLI (`specify`, about 85k lines under `src/specify_cli/`) with five composable primitives (integrations, extensions, presets, workflows, workflow steps) plus bundles and catalogs. The classic SDD prompt/templates core is still there and is small (9 command prompts, 5 templates, 6 helper scripts in three shell variants).

## 1. Core philosophy, current version and release cadence

### Takeaway
The philosophy document (`spec-driven.md`) still argues for a "power inversion" in which specifications are the executable source of truth and code is a regenerated expression of them, but the shipped product in late 2026 is more pragmatic: it describes itself as a toolkit of "structured processes, reusable templates, and documented outcomes", explicitly declines to enforce any spec-persistence model, and its own repo gitignores `specs/`. Current release is 1.4.3 (2026-11-19), 1.0.0 shipped 2026-08-21, and releases land every one to five days.

### Cited Findings
- Power inversion, verbatim: "Spec-Driven Development (SDD) inverts this power structure. Specifications don't serve code—code serves specifications. The Product Requirements Document (PRD) isn't a guide for implementation; it's the source that generates implementation." — [spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- Executable-spec claim: "SDD eliminates the gap by making specifications and their concrete implementation plans born from the specification executable. When specifications and implementation plans generate code, there is no gap—only transformation." — [spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- Intent-driven development: "The intent of the development team is expressed in natural language ("**intent-driven development**"), design assets, core principles and other guidelines. The **lingua franca** of development moves to a higher level, and code is the last-mile approach." — [spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- Six stated core principles: Specifications as the Lingua Franca; Executable Specifications; Continuous Refinement ("Consistency validation happens continuously, not as a one-time gate"); Research-Driven Context; Bidirectional Feedback (production reality informs spec evolution); Branching for Exploration (multiple implementations from one spec). — [spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- The design thesis most relevant to a new framework is "Template-Driven Quality: How Structure Constrains LLMs for Better Outcomes": "The templates act as sophisticated prompts that constrain the LLM's output in productive ways". Seven named mechanisms: (1) preventing premature implementation detail (WHAT/WHY, not HOW), (2) forcing explicit uncertainty markers `[NEEDS CLARIFICATION]`, (3) structured thinking through checklists that act as "unit tests" for the spec, (4) constitutional compliance through gates, (5) hierarchical detail management (keep plan high-level, push detail to separate files), (6) test-first thinking (contracts, then tests, then source), (7) preventing speculative features. — [spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- Current README positioning is broader than SDD: "Spec Kit is an open source toolkit that gives AI coding agents structured processes, reusable templates, and documented outcomes. Start with a ready-made process, customize it, or bring your own." Three first-party processes: Spec-Driven Development (ships in core), bug fixing and idea assessment (bundled opt-in extensions). "These are independent entry points, not mandatory phases." — [README.md](https://github.com/github/spec-kit/blob/main/README.md)
- Minimal SDD flow per README (Copilot skills syntax): `/speckit-constitution`, `/speckit-specify`, `/speckit-plan`, `/speckit-tasks`, `/speckit-implement`, `/speckit-converge`; "Repeat implement and converge until convergence reports `Converged`." — [README.md](https://github.com/github/spec-kit/blob/main/README.md)
- Original three development paths: 0-to-1 ("Greenfield"), Creative Exploration (parallel implementations), Iterative Enhancement ("Brownfield"); original core sequence "Specify → Plan → Tasks → Implement". — [docs/overview/history.md](https://github.com/github/spec-kit/blob/main/docs/overview/history.md)
- Enduring themes as stated by the project: intent before implementation; durable artifacts; agent-independent process; method adapts to the work; community shapes the kit. — [docs/overview/history.md](https://github.com/github/spec-kit/blob/main/docs/overview/history.md)
- The project does not enforce spec-as-source in practice. The persistence guide lists four post-delivery models (flow-back, flow-forward, living spec, constitution-only) and says "None is the default, and none is required by Spec Kit" and "The model is a team convention, not a CLI setting." It cites Fowler's spec-first / spec-anchored / spec-as-source levels. — [docs/how-to/persisting-specs.md](https://github.com/github/spec-kit/blob/main/docs/how-to/persisting-specs.md)
- Spec Kit's own repo uses the constitution-only model: "it tracks `.specify/memory/constitution.md`, while `specs/` is gitignored and feature artifacts are not tracked." Confirmed in `.gitignore`, which ignores `.specify/` and `specs/` with the comment that they are "meant for dogfooding Spec Kit during its own feature development". — [docs/how-to/persisting-specs.md](https://github.com/github/spec-kit/blob/main/docs/how-to/persisting-specs.md); [.gitignore](https://github.com/github/spec-kit/blob/main/.gitignore)
- Version: `pyproject.toml` on `main` reads `version = "1.4.4.dev0"`; the newest released entry in the changelog is `## [1.4.3] - 2026-11-19`. Package name `specify-cli`, entry point `specify = "specify_cli:main"`, `requires-python = ">=3.11"`, dependencies include typer, click, rich, pyyaml, pathspec, json5, `mcp>=2.2.0,<3.0.0`, `pydantic>=2.13.0,<3.0.0`, `lark>=1.3.1,<2.0.0`. ### Inferences
- Every 1.x release block in the changelog spans exactly 25 lines (headings at lines 5, 30, 55, 80, ...), i.e. 20 entries each, the last always "chore: release X, begin Y.dev0 development". Releases therefore look like they are cut automatically every roughly 20 merged PRs rather than on a calendar. A large share of those entries are community-catalog updates, so version numbers overstate core change.
- There is a visible gap between the manifesto (code as "continuously regenerated output") and the shipped mechanics (code is written once by `/speckit.implement`, then patched through an implement/converge loop; nothing regenerates code from a changed spec). A new framework should copy the mechanics and treat the manifesto as aspiration.
- `spec-driven.md` is partly stale relative to the templates (see section 4): it still describes "three powerful commands", branch creation inside `/speckit.specify`, "Phase -1" gates and a nine-article constitution, none of which match the current templates I read.

### Gaps
- I did not fetch the GitHub Releases page or PyPI, so "1.4.3 is the latest published release" rests on the changelog in the repo, not on the registry.
- Star count and current contributor numbers were not checked.

## 2. Exact on-disk layout after `specify init`, and what each file contains

### Takeaway
`specify init` writes a shared, agent-neutral `.specify/` tree (constitution, templates, one script variant, init options, hash manifest, bundled workflow) plus agent-specific command or skill files in the agent's own folder; per-feature artifacts live in `specs/<prefix>-<short-name>/` and are located through a pointer file `.specify/feature.json`, not through the git branch name. Git setup and agent-context files are no longer core: they come from opt-in extensions.

### Cited Findings
- `specify init [<project_name>]` options: `--integration <key>`, `--integration-options`, `--script sh|ps|py`, `--here`, `--force`, `--allow-symlinks`, `--ignore-agent-tools`, `--preset <id>` (the source also defines a repeatable `--extension` and `--trust-extension-urls`). It "Creates a new Spec Kit project with the necessary directory structure, templates, scripts, and AI coding agent integration files." With no `--integration`, interactive runs prompt and non-interactive runs default to GitHub Copilot. — [docs/overview/core.md](https://github.com/github/spec-kit/blob/main/docs/overview/core.md); [src/specify_cli/command_init.py](https://github.com/github/spec-kit/blob/main/src/specify_cli/command_init.py)
- Git is not initialized by init: "Git repository initialization and branching are managed by the **git extension**, which is not installed by default. Run `specify extension add git` after init to enable git workflows." — [docs/overview/core.md](https://github.com/github/spec-kit/blob/main/docs/overview/core.md)
- Init step sequence in code (progress tracker labels): "Check required tools", "Select coding agent integration", "Select script type", "Install integration", "Install shared infrastructure", "Constitution setup", "Install bundled workflow", optional "Install extension: ...", "Finalize". — [src/specify_cli/command_init.py](https://github.com/github/spec-kit/blob/main/src/specify_cli/command_init.py)
- Assets bundled in the wheel so init works offline: the five page templates (`checklist-`, `constitution-`, `plan-`, `spec-`, `tasks-template.md`) plus `vscode-settings.json`; `templates/commands`; `scripts/bash`, `scripts/powershell`, `scripts/python`; extensions `git`, `agent-context`, `assess`, `bug`, `github`; workflows `speckit`, `bugfix`, `assess` ("`specify init` installs only `speckit`; `bugfix`/`assess` are opt-in via first-party bundles"); presets `lean`, `constitution-sync`; bundle catalog snapshots. — [pyproject.toml](https://github.com/github/spec-kit/blob/main/pyproject.toml)
- `.specify/memory/constitution.md`: materialized at init from the resolved `constitution-template` if missing ("existing file preserved" otherwise); resolution goes through the preset stack, so a preset can seed a ratified constitution. — [src/specify_cli/command_init.py](https://github.com/github/spec-kit/blob/main/src/specify_cli/command_init.py)
- `.specify/templates/`: core templates; `.specify/templates/overrides/<name>.md` is the project-local override location (highest priority). — [scripts/bash/common.sh](https://github.com/github/spec-kit/blob/main/scripts/bash/common.sh); [docs/how-to/customization.md](https://github.com/github/spec-kit/blob/main/docs/how-to/customization.md)
- `.specify/scripts/<bash|powershell|python>/`: `check-prerequisites`, `common`, `create-new-feature`, `resolve-template`, `setup-plan`, `setup-tasks` (same six in each variant; Python names use underscores). Only the chosen variant is installed: `--script sh` → `bash/`, `ps` → `powershell/`, `py` → `python/` plus the platform's shell variant (`bash`, or `powershell` on Windows). — [scripts/](https://github.com/github/spec-kit/tree/main/scripts); [src/specify_cli/shared_infra.py](https://github.com/github/spec-kit/blob/main/src/specify_cli/shared_infra.py)
- Source prompts refer to repo-relative paths (`scripts/...`, `templates/...`, `/memory/constitution.md`); at install time they are rewritten "to the `.specify/...` paths used in generated projects". — [src/specify_cli/agents.py](https://github.com/github/spec-kit/blob/main/src/specify_cli/agents.py)
- The single hidden `.specify/` root traces back to a highly upvoted early request, "Proposal: Set root directory to .specify" (57 thumbs-up, opened 2025-09-05), to stop cluttering the repo root with `memory/`, `scripts/`, `templates/`. — [issue #38](https://github.com/github/spec-kit/issues/38)
- `.specify/init-options.json`: records init choices; keys written by code are `ai`, `integration`, `here`, `script`, `feature_numbering` (default `"sequential"`, preserved across re-init), `speckit_version`, `allow_symlinks`, and `ai_skills: true` when the integration runs in skills mode. `branch_numbering` is a deprecated alias of `feature_numbering`. — [src/specify_cli/command_init.py](https://github.com/github/spec-kit/blob/main/src/specify_cli/command_init.py); [docs/overview/core.md](https://github.com/github/spec-kit/blob/main/docs/overview/core.md); [templates/commands/specify.md](https://github.com/github/spec-kit/blob/main/templates/commands/specify.md)
- `.specify/feature.json`: the current-feature pointer, exactly `{"feature_directory": "specs/003-user-auth"}`; written by `/speckit.specify` and by the helper scripts; machine-local. — [templates/commands/specify.md](https://github.com/github/spec-kit/blob/main/templates/commands/specify.md); [scripts/bash/common.sh](https://github.com/github/spec-kit/blob/main/scripts/bash/common.sh)
- `.specify/.gitignore` (managed, user edits preserved) ignores `feature.json`, `extensions/*/local-config.yml`, `integrations/packages/`, `integrations/packages.json`, "while leaving everything else under `.specify/` (constitution, templates, scripts, extension config) shareable". — [src/specify_cli/shared_infra.py](https://github.com/github/spec-kit/blob/main/src/specify_cli/shared_infra.py); [docs/overview/core.md](https://github.com/github/spec-kit/blob/main/docs/overview/core.md)
- `.specify/integrations/speckit.manifest.json`: per-file SHA-256 manifest of shared infrastructure. On refresh, files whose hash still matches are overwritten with the new bundled version; files whose hash diverged "are treated as user customizations and preserved with a warning"; `force=True` overwrites every regular file; symlinks are never followed. — [src/specify_cli/shared_infra.py](https://github.com/github/spec-kit/blob/main/src/specify_cli/shared_infra.py)
- `.specify/workflows/speckit/workflow.yml`: the bundled "Full SDD Cycle" workflow, copied at init. — [src/specify_cli/command_init.py](https://github.com/github/spec-kit/blob/main/src/specify_cli/command_init.py); [workflows/speckit/workflow.yml](https://github.com/github/spec-kit/blob/main/workflows/speckit/workflow.yml)
- Present only after adding components: `.specify/extensions/<id>/` (commands, scripts, config such as `git-config.yml`), `.specify/extensions.yml` (hook registry read by every command prompt), `.specify/presets/<id>/` and `.specify/presets/.registry` (priority and enabled flags), optional `.specify/integration-events.yml`. — [scripts/bash/common.sh](https://github.com/github/spec-kit/blob/main/scripts/bash/common.sh); [extensions/git/git-config.yml](https://github.com/github/spec-kit/blob/main/extensions/git/git-config.yml); [docs/integrations/cli.md](https://github.com/github/spec-kit/blob/main/docs/integrations/cli.md)
- Agent-specific output lives in the agent's folder, for example Claude Code gets skills at `.claude/skills/speckit-plan/SKILL.md` (registrar config `dir: .claude/skills`, `extension: /SKILL.md`) and Copilot's default is skills under `.github/skills/speckit-specify/SKILL.md`. — [src/specify_cli/integrations/claude/__init__.py](https://github.com/github/spec-kit/blob/main/src/specify_cli/integrations/claude/__init__.py); [docs/overview/artifacts.md](https://github.com/github/spec-kit/blob/main/docs/overview/artifacts.md)
- Feature directory documented in the plan template:
  ```text
  specs/[###-feature]/
  ├── plan.md              # This file
  ├── research.md          # Phase 0 output
  ├── data-model.md        # Phase 1 output
  ├── quickstart.md        # Phase 1 output
  ├── contracts/           # Phase 1 output
  └── tasks.md             # Phase 2 output (tasks command - NOT created by plan)
  ```
  plus `spec.md` and `checklists/` created by the specify and checklist commands. — [templates/plan-template.md](https://github.com/github/spec-kit/blob/main/templates/plan-template.md); [templates/commands/specify.md](https://github.com/github/spec-kit/blob/main/templates/commands/specify.md)
- Directory naming: `<prefix>-<short-name>` where prefix is `NNN` ("next available 3-digit number after scanning existing directories in `specs/`") or `YYYYMMDD-HHMMSS` when `feature_numbering` is `"timestamp"`; examples `003-user-auth`, `20260319-143022-user-auth`. Numbers expand past three digits automatically. — [templates/commands/specify.md](https://github.com/github/spec-kit/blob/main/templates/commands/specify.md); [spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- "The spec directory name and the git branch name are independent — they may be the same but that is the user's choice." — [templates/commands/specify.md](https://github.com/github/spec-kit/blob/main/templates/commands/specify.md)
- Per-file content. `spec.md`: user stories, requirements, success criteria, assumptions (section 5). `plan.md`: technical context, constitution check, structure, complexity tracking (section 5). `research.md`: one entry per unknown in the form "Decision: [what was chosen] / Rationale: [why chosen] / Alternatives considered: [what else evaluated]". `data-model.md`: "Entity name, fields, relationships", "Validation rules from requirements", "State transitions if applicable"; it is "the canonical source for field constraints". `contracts/`: interface contracts in "the contract format appropriate for the project type" (public APIs for libraries, command schemas for CLIs, endpoints for web services, grammars for parsers, UI contracts), skipped "if project is purely internal". `quickstart.md`: "runnable validation scenarios that prove the feature works end-to-end" with prerequisites, setup commands, run commands and expected outcomes, and explicitly no implementation code. `tasks.md`: phased checklist of tasks (section 5), later extended by `## Phase N: Convergence` sections. — [templates/commands/plan.md](https://github.com/github/spec-kit/blob/main/templates/commands/plan.md); [templates/commands/tasks.md](https://github.com/github/spec-kit/blob/main/templates/commands/tasks.md); [templates/commands/converge.md](https://github.com/github/spec-kit/blob/main/templates/commands/converge.md)
- `checklists/requirements.md` is the built-in "Specification Quality Checklist" created by `/speckit.specify` and re-evaluated by `/speckit.clarify`; `checklists/<domain>.md` (for example `ux.md`, `api.md`, `security.md`) are custom, reviewer-owned files from `/speckit.checklist`. — [templates/commands/specify.md](https://github.com/github/spec-kit/blob/main/templates/commands/specify.md); [templates/commands/checklist.md](https://github.com/github/spec-kit/blob/main/templates/commands/checklist.md)
- Extension processes write outside `specs/`: bug reports in `.specify/bugs/<slug>/`, assessments in `.specify/assessments/<slug>/`. — [README.md](https://github.com/github/spec-kit/blob/main/README.md)
- Agent context files (`CLAUDE.md`, `.github/copilot-instructions.md`, `AGENTS.md`) are managed by the `agent-context` extension, which rewrites only a delimited block (default markers `<!-- SPECKIT START -->` / `<!-- SPECKIT END -->`) that points at the most recent `specs/**/plan.md`. — [extensions/agent-context/commands/speckit.agent-context.update.md](https://github.com/github/spec-kit/blob/main/extensions/agent-context/commands/speckit.agent-context.update.md)

### Inferences
- The move from "current git branch names the feature" (2025 behaviour) to an explicit pointer file plus env overrides (`SPECIFY_FEATURE_DIRECTORY`, `SPECIFY_FEATURE`, `SPECIFY_FEATURE_NO_PERSIST`) is the main structural change to copy: it decouples specs from git and makes concurrent agents on one checkout possible.
- The hash-manifest upgrade scheme (overwrite if untouched, preserve if edited) is a cheap, reusable answer to "how do we upgrade scaffolded files without clobbering user edits".

### Gaps
- No doc in the repo prints a single canonical tree of a freshly initialized project; the layout above is assembled from code and prompts, and I did not run `specify init` (running anything from the clone was out of bounds).
- Whether any integration adapter auto-installs the `agent-context` extension was not traced. `command_init.py` has no reference to it, and `shared_infra.py` only removes a legacy core `update-agent-context` script "superseded by the bundled agent-context extension", which suggests it is opt-in like `git`.

## 3. Full command workflow: what each command reads, writes and enforces

### Takeaway
The core flow is now nine prompts: constitution → specify → clarify → plan → checklist → tasks → analyze → implement → converge, where only specify-before-plan is strictly required and clarify/checklist/analyze are optional quality gates. Each prompt has the same skeleton (frontmatter with a script per shell variant, user input block, pre-hooks, outline, mandatory post-hooks, completion report, "Done When" checklist), runs one deterministic script that returns JSON paths, and then leaves the content work to the LLM. `taskstoissues` and all git behaviour have moved out of core into bundled opt-in extensions.

### Cited Findings
- Canonical order: `/speckit.constitution -> /speckit.specify -> /speckit.clarify -> /speckit.plan -> /speckit.checklist -> /speckit.tasks -> /speckit.analyze -> /speckit.implement -> /speckit.converge`. "The commands are designed to run in order, but only `/speckit.specify` is strictly required before `/speckit.plan`. The clarify, checklist, and analyze commands are quality gates you add for anything with meaningful ambiguity." `/speckit.clarify` was formerly `/quizme`. — [docs/reference/agentic-sdd.md](https://github.com/github/spec-kit/blob/main/docs/reference/agentic-sdd.md)
- Core command prompt files and sizes: `analyze.md` 275 lines, `checklist.md` 379, `clarify.md` 291, `constitution.md` 179, `converge.md` 279, `implement.md` 222, `plan.md` 170, `specify.md` 349, `tasks.md` 224. Roughly 60 to 70 lines of each are near-identical hook boilerplate. — [templates/commands/](https://github.com/github/spec-kit/tree/main/templates/commands)
- Shared prompt skeleton. Frontmatter: `description`, optional `handoffs` (list of `label`, `agent`, `prompt`, optional `send: true`), and `scripts` with `sh`/`ps`/`py` variants, for example:
  ```yaml
  scripts:
    sh: scripts/bash/setup-plan.sh --json
    ps: scripts/powershell/setup-plan.ps1 -Json
    py: scripts/python/setup_plan.py --json
  ```
  Body: `## User Input` with `$ARGUMENTS` and "You **MUST** consider the user input before proceeding (if not empty)."; `## Pre-Execution Checks` (extension hooks); `## Outline` or `## Execution Steps`; `## Mandatory Post-Execution Hooks` ("You MUST complete this section before reporting completion to the user."); `## Completion Report`; `## Done When` checkbox list. — [templates/commands/plan.md](https://github.com/github/spec-kit/blob/main/templates/commands/plan.md)
- Cross-references between prompts use tokens such as `__SPECKIT_COMMAND_PLAN__`, which the CLI rewrites at install time into the agent's own invocation syntax. — [src/specify_cli/integrations/base.py](https://github.com/github/spec-kit/blob/main/src/specify_cli/integrations/base.py)
- `/speckit.constitution`. Script: `resolve-template constitution-template --json` → `TEMPLATE_CONTENT`. Reads the existing `.specify/memory/constitution.md` if present. Writes only that file ("Write only `.specify/memory/constitution.md`; do not create or modify template source files."). Enforces a Scope Guard: feature or code requests in the input are not executed but listed as deferred "Next Actions"; "You **MUST NOT** create, modify, or delete application source files". Applies semantic versioning and prepends a Sync Impact Report. Handoff: Build Specification. — [templates/commands/constitution.md](https://github.com/github/spec-kit/blob/main/templates/commands/constitution.md)
- `/speckit.specify`. Script: `resolve-template spec-template --json` → `TEMPLATE_CONTENT` (the composed template; "Do not copy a template file from disk instead: when a preset composes `spec-template`, no single file holds the full template"). Steps: generate a 2-4 word short name ("action-noun format when possible", for example "user-auth", "fix-payment-timeout"); resolve the feature directory (explicit `SPECIFY_FEATURE_DIRECTORY`, else `specs/<prefix>-<short-name>` using `feature_numbering` from `.specify/init-options.json`); `mkdir -p`; write `spec.md`; persist `.specify/feature.json`; load constitution if it exists; fill the template; create and run the quality checklist; ask at most three clarification questions. "You must only create one feature per `__SPECKIT_COMMAND_SPECIFY__` invocation". Handoffs: Build Technical Plan, Clarify Spec Requirements. — [templates/commands/specify.md](https://github.com/github/spec-kit/blob/main/templates/commands/specify.md)
- Specify execution flow, verbatim excerpt:
  ```text
  3. For unclear aspects:
     - Make informed guesses based on context and industry standards
     - Only mark with [NEEDS CLARIFICATION: specific question] if:
       - The choice significantly impacts feature scope or user experience
       - Multiple reasonable interpretations exist with different implications
       - No reasonable default exists
     - **LIMIT: Maximum 3 [NEEDS CLARIFICATION] markers total**
     - Prioritize clarifications by impact: scope > security/privacy > user experience > technical details
  ```

### Inferences
- The repeated design pattern per command is: one script call for paths and preconditions, a narrow write set stated as an explicit constraint ("Write only ...", "STRICTLY READ-ONLY", "APPEND-ONLY, NEVER REWRITE"), a bounded interaction budget (3 markers, 5 questions, 3 validation iterations, 50 findings), and a closing "Done When" list. These bounded budgets and write-set contracts are the parts most worth copying.
- Human review happens between commands rather than inside them; the only in-prompt hard stops are the checklist gate in implement, the clarification questions, and the plan's "ERROR on gate failures".
- Converge replaces "trust the checked boxes" with a re-audit of code against intent, and makes the remediation channel a task list rather than direct edits; this is a clean loop primitive for an ADK `LoopAgent`.

### Gaps
- The bug and assess extension prompts were not read in detail (out of scope for core SDD).
- The Python and PowerShell script variants were not diffed against Bash; AGENTS.md says behavioural parity is required.

## 4. How the constitution works: principles, gating, versioning and amendment

### Takeaway
The constitution is a single Markdown file of project-specific MUST/SHOULD principles that every later command loads at runtime; the plan template contains only a pointer ("Gates determined based on constitution file") that the LLM expands into gates, analyze and converge treat MUST violations as automatically CRITICAL, and amendments are made only through `/speckit.constitution` with semantic versioning and a Sync Impact Report. The famous "nine articles" and "Phase -1 simplicity / anti-abstraction gates" exist in `spec-driven.md` as narrative, not in the shipped templates.

### Cited Findings
- Shipped template structure: `# [PROJECT_NAME] Constitution`; `## Core Principles` with five slots `### [PRINCIPLE_1_NAME]` ... `### [PRINCIPLE_5_NAME]` each followed by a description placeholder; `## [SECTION_2_NAME]` (example: Additional Constraints, Security Requirements, Performance Standards); `## [SECTION_3_NAME]` (example: Development Workflow, Review Process, Quality Gates); `## Governance`; footer `**Version**: [CONSTITUTION_VERSION] | **Ratified**: [RATIFICATION_DATE] | **Last Amended**: [LAST_AMENDED_DATE]`. — [templates/constitution-template.md](https://github.com/github/spec-kit/blob/main/templates/constitution-template.md)
- Example principles given only as HTML comments in the template: "I. Library-First", "II. CLI Interface", "III. Test-First (NON-NEGOTIABLE)" ("TDD mandatory: Tests written → User approved → Tests fail → Then implement"), "IV. Integration Testing", "V. Observability, VI. Versioning & Breaking Changes, VII. Simplicity". Governance example: "Constitution supersedes all other practices; Amendments require documentation, approval, migration plan". — [templates/constitution-template.md](https://github.com/github/spec-kit/blob/main/templates/constitution-template.md)
- The number of principles is flexible: "The user might require less or more principles than the ones used in the template. If a number is specified, respect that". — [templates/commands/constitution.md](https://github.com/github/spec-kit/blob/main/templates/commands/constitution.md)
- Narrative version in the manifesto: "nine articles"; Article I Library-First, II CLI Interface Mandate, III Test-First Imperative ("NON-NEGOTIABLE"), IV to VI "intentionally defined by each project's constitution", VII Simplicity ("Maximum 3 projects for initial implementation"), VIII Anti-Abstraction ("Use framework features directly rather than wrapping them"), IX Integration-First Testing ("Prefer real databases over mocks"). It shows "Phase -1: Pre-Implementation Gates" with a Simplicity Gate ("Using ≤3 projects?", "No future-proofing?"), Anti-Abstraction Gate ("Using framework directly?", "Single model representation?") and Integration-First Gate ("Contracts defined?", "Contract tests written?"). — [spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- What the shipped plan template actually contains for gating, in full:
  ```markdown
  ## Constitution Check

  *GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

  [Gates determined based on constitution file]
  ```
  and, at the end, a `## Complexity Tracking` table headed "Fill ONLY if Constitution Check has violations that must be justified" with columns `Violation | Why Needed | Simpler Alternative Rejected Because` (example rows "4th project", "Repository pattern"). — [templates/plan-template.md](https://github.com/github/spec-kit/blob/main/templates/plan-template.md)
- Gate enforcement wording in the plan prompt: "Evaluate gates (ERROR if violations unjustified)", "Re-evaluate Constitution Check post-design", "ERROR on gate failures or unresolved clarifications". — [templates/commands/plan.md](https://github.com/github/spec-kit/blob/main/templates/commands/plan.md)
- Analyze authority clause: "The project constitution (`/memory/constitution.md`) is **non-negotiable** within this analysis scope. Constitution conflicts are automatically CRITICAL and require adjustment of the spec, plan, or tasks—not dilution, reinterpretation, or silent ignoring of the principle. If a principle itself needs to change, that must occur in a separate, explicit constitution update". Analyze extracts "principle names and MUST/SHOULD normative statements" as its rule set. — [templates/commands/analyze.md](https://github.com/github/spec-kit/blob/main/templates/commands/analyze.md)
- Converge applies the same authority to code: "Code that violates a MUST principle is the highest-severity finding and produces a corresponding remediation task. If the constitution is an unfilled template, skip constitution checks gracefully rather than failing." Constitution tasks "MUST be emitted first". — [templates/commands/converge.md](https://github.com/github/spec-kit/blob/main/templates/commands/converge.md)
- Which commands load it: plan (always reads it), analyze and converge (rule set), and specify, clarify, tasks, checklist, implement and taskstoissues via "**IF EXISTS**: Load `/memory/constitution.md` for project principles and governance constraints." — [templates/commands/](https://github.com/github/spec-kit/tree/main/templates/commands)
- Versioning rules, verbatim: "`CONSTITUTION_VERSION` must increment according to semantic versioning rules: MAJOR: Backward incompatible governance/principle removals or redefinitions. MINOR: New principle/section added or materially expanded guidance. PATCH: Clarifications, wording, typo fixes, non-semantic refinements." `RATIFICATION_DATE` is the original adoption date; `LAST_AMENDED_DATE` is today if changed; dates ISO `YYYY-MM-DD`; unknowns become `TODO(<FIELD_NAME>): explanation`. — [templates/commands/constitution.md](https://github.com/github/spec-kit/blob/main/templates/commands/constitution.md)
- Amendment output: a Sync Impact Report "as an HTML comment at the top of the constitution file" listing version change old → new, modified principles, added and removed sections, follow-up TODOs. It "is temporary scratch material for human review of the amendment, not governance content; it is expected to be removed before the amended constitution file is committed." The command also proposes a commit message such as `docs: amend constitution to vX.Y.Z (...)`. — [templates/commands/constitution.md](https://github.com/github/spec-kit/blob/main/templates/commands/constitution.md)
- Quality rules for principles: "Principles are declarative, testable, and free of vague language ("should" → replace with MUST/SHOULD rationale where appropriate)"; the Governance section must list "amendment procedure, versioning policy, and compliance review expectations". — [templates/commands/constitution.md](https://github.com/github/spec-kit/blob/main/templates/commands/constitution.md)
- Behaviour change (current): the constitution command no longer rewrites other templates. Scope Guard: "Dependent templates and commands read the constitution at runtime and are not modified here." The opt-in `constitution-sync` preset restores propagation: "This propagation used to be built into `/constitution`; it was dropped when the command moved to the preset model." Reasons given for dropping it: propagation "duplicates the constitution as the source of truth and can fight the composition stack", "Materialized copies can drift", and "A pre-filled Constitution Check can bias `/plan`". — [templates/commands/constitution.md](https://github.com/github/spec-kit/blob/main/templates/commands/constitution.md); [presets/constitution-sync/README.md](https://github.com/github/spec-kit/blob/main/presets/constitution-sync/README.md)
- The upgrade guide documents the reversal and its rationale (PR #3790): the command "**no longer edits** `plan-template.md`, `spec-template.md`, `tasks-template.md`, installed command files, or guidance docs." "Spec Kit uses **runtime resolution**: `plan`, `tasks`, and `analyze` read `.specify/memory/constitution.md` live on every run, and `analyze` is the dedicated drift checker. The governed templates carry a pointer, not a copy". "Propagation duplicated the single source of truth and fought the preset/override composition system". — [docs/upgrade.md](https://github.com/github/spec-kit/blob/main/docs/upgrade.md)
- A search of the bundled `templates/`, `presets/` and `extensions/` trees for "Phase -1", "Simplicity Gate" and "Anti-Abstraction" returns no match; those named gates appear only in the manifesto. — [templates/](https://github.com/github/spec-kit/tree/main/templates); [spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- Conflict between sources: the command reference still says `/speckit.constitution` "keeps dependent templates in sync", which contradicts the command prompt and the preset README above. The prompt and upgrade notes are the more specific and newer sources. — [docs/reference/agentic-sdd.md](https://github.com/github/spec-kit/blob/main/docs/reference/agentic-sdd.md); contradicted by [templates/commands/constitution.md](https://github.com/github/spec-kit/blob/main/templates/commands/constitution.md)
- Worked example: Spec Kit's own constitution is v1.0.0 with five principles: "I. Code Quality & Architectural Discipline", "II. Test-Backed Change (NON-NEGOTIABLE)", "III. CLI & User-Experience Consistency", "IV. Offline-First Performance & Resource Discipline", "V. Minimal Dependencies & Safe, Idempotent File Operations", plus sections "Security & Cross-Platform Constraints", "Development Workflow & Quality Gates", "Governance"; it was "derived from an exhaustive multi-pass analysis of the source tree" (a brownfield constitution). — [.specify/memory/constitution.md](https://github.com/github/spec-kit/blob/main/.specify/memory/constitution.md)
- Brownfield guidance for writing one: use "principles that are already true for the repository or that the team has explicitly agreed to adopt"; "Do not invent standards merely to fill the constitution template... unrealistic rules create noise instead of useful constraints." — [docs/how-to/existing-projects.md](https://github.com/github/spec-kit/blob/main/docs/how-to/existing-projects.md)
- The constitution is not a spec store: "Amend the constitution only when governing principles or constraints change; do not turn it into a collection of feature specifications." — [docs/how-to/persisting-specs.md](https://github.com/github/spec-kit/blob/main/docs/how-to/persisting-specs.md)

### Inferences
- All constitutional gating is LLM-evaluated prose. There is no deterministic check that a plan's Constitution Check was filled in, that a violation has a Complexity Tracking row, or that the gate was re-run after design. A new framework could keep the runtime-pointer idea but have a tool parse principles into a structured gate list and validate the plan section mechanically.
- "Immutable principles" in the manifesto versus "semver-amended file" in the prompt: in practice the constitution is mutable but changes are funnelled through one command and made visible through version bumps and the impact report.
- The decision to stop materializing constitution content into templates (single source of truth, read at runtime) is a deliberate design reversal and a useful precedent: derive at use time rather than copy at write time.

### Gaps
- The upgrade guide attributes the propagation change to PR #3790 but does not name the release that first shipped it.
- Community presets outside this repo may reintroduce hardcoded gates; only the bundled trees were searched.

## 5. Precise structure of the spec, plan and tasks templates

### Takeaway
The spec template is organised around prioritized, independently testable user stories with Given/When/Then scenarios, numbered FR and SC identifiers, and an Assumptions section that absorbs defaults instead of questions; the plan template is a short fill-in form (technical context, constitution check, structure, complexity tracking) whose heavy content is pushed to sibling files; the tasks template enforces a machine-parseable line grammar and phases per user story so each story is a shippable increment.

### Cited Findings
- Spec template header fields: `# Feature Specification: [FEATURE NAME]`, `**Feature Branch**: `[###-feature-name]``, `**Created**: [DATE]`, `**Status**: Draft`, `**Input**: User description: "$ARGUMENTS"`. — [templates/spec-template.md](https://github.com/github/spec-kit/blob/main/templates/spec-template.md)
- Spec sections in order: `## User Scenarios & Testing *(mandatory)*` (with `### User Story N - [Brief Title] (Priority: P1)` blocks and `### Edge Cases`), `## Requirements *(mandatory)*` (`### Functional Requirements`, `### Key Entities *(include if feature involves data)*`), `## Success Criteria *(mandatory)*` (`### Measurable Outcomes`), `## Assumptions`. — [templates/spec-template.md](https://github.com/github/spec-kit/blob/main/templates/spec-template.md)
- User story block, verbatim:
  ```markdown
  ### User Story 1 - [Brief Title] (Priority: P1)

  [Describe this user journey in plain language]

  **Why this priority**: [Explain the value and why it has this priority level]

  **Independent Test**: [Describe how this can be tested independently - e.g., "Can be fully tested by [specific action] and delivers [specific value]"]

  **Acceptance Scenarios**:

  1. **Given** [initial state], **When** [action], **Then** [expected outcome]
  ```
  — [templates/spec-template.md](https://github.com/github/spec-kit/blob/main/templates/spec-template.md)
- The independence rule is embedded as a comment: "User stories should be PRIORITIZED as user journeys ordered by importance. Each user story/journey must be INDEPENDENTLY TESTABLE - meaning if you implement just ONE of them, you should still have a viable MVP (Minimum Viable Product) that delivers value." Each story should be developable, testable, deployable and demonstrable independently. — [templates/spec-template.md](https://github.com/github/spec-kit/blob/main/templates/spec-template.md)
- Requirements format: `- **FR-001**: System MUST [specific capability, e.g., "allow users to create accounts"]`, `- **FR-003**: Users MUST be able to [key interaction...]`; unclear ones are written inline: `- **FR-006**: System MUST authenticate users via [NEEDS CLARIFICATION: auth method not specified - email/password, SSO, OAuth?]`. Key entities: `- **[Entity 1]**: [What it represents, key attributes without implementation]`. — [templates/spec-template.md](https://github.com/github/spec-kit/blob/main/templates/spec-template.md)
- Success criteria format: `- **SC-001**: [Measurable metric, e.g., "Users can complete account creation in under 2 minutes"]`, with the comment "These must be technology-agnostic and measurable." The specify prompt adds good and bad examples (good: "95% of searches return results in under 1 second"; bad: "API response time is under 200ms", "Redis cache hit rate above 80%") and four tests: Measurable, Technology-agnostic, User-focused, Verifiable. — [templates/spec-template.md](https://github.com/github/spec-kit/blob/main/templates/spec-template.md); [templates/commands/specify.md](https://github.com/github/spec-kit/blob/main/templates/commands/specify.md)
- Assumptions section: placeholders filled "based on reasonable defaults chosen when the feature description did not specify certain details" (target users, scope boundaries, data/environment, dependencies). — [templates/spec-template.md](https://github.com/github/spec-kit/blob/main/templates/spec-template.md)
- `[NEEDS CLARIFICATION]` limits. Current rule: maximum three markers in total; anything beyond is resolved by informed guess and recorded in Assumptions; listed "reasonable defaults (don't ask about these)" include data retention, performance targets, error handling, authentication method, integration patterns. This reverses the older stance still quoted in the manifesto ("Mark all ambiguities... Don't guess: If the prompt doesn't specify something, mark it"). — [templates/commands/specify.md](https://github.com/github/spec-kit/blob/main/templates/commands/specify.md); older stance in [spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- Spec writing rules in the prompt: "Focus on **WHAT** users need and **WHY**. Avoid HOW to implement (no tech stack, APIs, code structure). Written for business stakeholders, not developers. DO NOT create any checklists that are embedded in the spec." "When a section doesn't apply, remove it entirely (don't leave as "N/A")". — [templates/commands/specify.md](https://github.com/github/spec-kit/blob/main/templates/commands/specify.md)
- Plan template header: `# Implementation Plan: [FEATURE]`, `**Branch**: ... | **Date**: [DATE] | **Spec**: [link]`, `**Input**: Feature specification from `/specs/[###-feature-name]/spec.md``. Sections: `## Summary`, `## Technical Context`, `## Constitution Check`, `## Project Structure` (`### Documentation (this feature)`, `### Source Code (repository root)`, `**Structure Decision**`), `## Complexity Tracking`. 113 lines in total. — [templates/plan-template.md](https://github.com/github/spec-kit/blob/main/templates/plan-template.md)

### Inferences
- The stable identifier scheme (FR-###, SC-###, US#, T###, CHK###, plus `US1/AC2` for acceptance scenarios) is what makes analyze, converge and taskstoissues possible; none of those IDs are validated by code, only by prompt.
- The template set has no "Clarifications" heading (clarify adds it), no non-functional requirements section (NFRs are expected to appear as success criteria or edge cases), and no out-of-scope section (scope boundaries go to Assumptions). Those are natural extension points.
- The plan template is deliberately thin; most plan quality comes from the prompt's Phase 0 and Phase 1 instructions and from the sibling files.

### Gaps
- No JSON or schema form of any artifact exists; everything is free Markdown, so I could not report a formal grammar beyond the prompt rules quoted above.

## 6. How clarify, analyze and checklist work in detail

### Takeaway
Clarify is a bounded interactive interview (ten-category ambiguity taxonomy, at most five questions, one at a time, each with a recommended answer, written back into the spec after every answer). Analyze is a read-only, severity-graded consistency report over spec, plan, tasks, data-model and constitution, capped at 50 findings. Checklist generates reviewer-owned "unit tests for English" that test the quality of the requirements text, never the implementation, and whose checkbox state later gates implement.

### Cited Findings
- Clarify taxonomy (each category marked Clear / Partial / Missing): Functional Scope & Behavior; Domain & Data Model; Interaction & UX Flow; Non-Functional Quality Attributes (performance, scalability, reliability, observability, security and privacy, compliance); Integration & External Dependencies; Edge Cases & Failure Handling; Constraints & Tradeoffs; Terminology & Consistency; Completion Signals; Misc / Placeholders (TODO markers, "Ambiguous adjectives ("robust", "intuitive") lacking quantification"). — [templates/commands/clarify.md](https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md)
- Question budget and shape: "Maximum of 5 total questions across the whole session"; each answerable by "A short multiple‑choice selection (2–5 distinct, mutually exclusive options), OR A one-word / short‑phrase answer (explicitly constrain: "Answer in <=5 words")"; prioritised by "(Impact * Uncertainty) heuristic"; only questions that "materially impact architecture, data modeling, task decomposition, test design, UX behavior, operational readiness, or compliance validation". — [templates/commands/clarify.md](https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md)
- Interaction protocol: "Present EXACTLY ONE question at a time"; "Never reveal future queued questions in advance"; each question leads with `**Question:**` and a full interrogative (a label such as "Acceptance device/runtime matrix (FR-023)" is declared INVALID), followed by a one-sentence "Why it matters", then `**Recommended:** Option [X] - <reasoning>` and an options table, or `**Suggested:** <answer>` for short answers; the user can reply "yes" or "recommended". Stops when ambiguities are resolved, the user says "done", or five questions were asked. — [templates/commands/clarify.md](https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md)
- Write-back after each answer: ensure `## Clarifications` and `### Session YYYY-MM-DD` exist, append `- Q: <question> → A: <final answer>`, then apply the answer to the right section (functional → Functional Requirements; data → data model/entities; non-functional → Success Criteria as a metric; edge case → Edge Cases; terminology → normalize across the spec). "If the clarification invalidates an earlier ambiguous statement, replace that statement instead of duplicating; leave no obsolete contradictory text." "Save the spec file AFTER each integration to minimize risk of context loss (atomic overwrite)." — [templates/commands/clarify.md](https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md)
- Clarify post-validation: one bullet per accepted answer, total ≤ 5, no lingering placeholders, no contradictory earlier statement, "only allowed new headings: `## Clarifications`, `### Session YYYY-MM-DD`". It then re-evaluates `checklists/requirements.md`, toggling only markers whose state changed, and reports "12/16 → 15/16 items passing" with newly passing, regressions and still-unchecked lists. — [templates/commands/clarify.md](https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md)
- Clarify completion report includes a coverage table with a status per taxonomy category: Resolved, Deferred, Clear, Outstanding. — [templates/commands/clarify.md](https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md)
- Analyze preconditions and constraints: "This command MUST run only after `__SPECKIT_COMMAND_TASKS__` has successfully produced a complete `tasks.md`." "**STRICTLY READ-ONLY**: Do **not** modify any files. Output a structured analysis report." — [templates/commands/analyze.md](https://github.com/github/spec-kit/blob/main/templates/commands/analyze.md)
- Analyze internal models: requirements inventory keyed by FR-/SC- IDs (success criteria included only when they "require buildable work", excluding "post-launch outcome metrics and business KPIs"); user story/action inventory; task coverage mapping ("inference by keyword / explicit reference patterns like IDs or key phrases"); constrained-field inventory and field citation mapping (when data-model.md exists); constitution rule set. — [templates/commands/analyze.md](https://github.com/github/spec-kit/blob/main/templates/commands/analyze.md)
- Six detection passes: A Duplication; B Ambiguity ("vague adjectives (fast, scalable, secure, intuitive, robust) lacking measurable criteria", placeholders `TODO, TKTK, ???`); C Underspecification; D Constitution Alignment; E Coverage Gaps ("Requirements with zero associated tasks", "Tasks with no mapped requirement/story", uncited constrained fields); F Inconsistency (terminology drift, entities in plan but not spec, task ordering contradictions, conflicting requirements such as "one requires Next.js while other specifies Vue", task-stated field constraints that contradict data-model.md). — [templates/commands/analyze.md](https://github.com/github/spec-kit/blob/main/templates/commands/analyze.md)
- Severity heuristic, verbatim: "**CRITICAL**: Violates constitution MUST, missing core spec artifact, or requirement with zero coverage that blocks baseline functionality. **HIGH**: Duplicate or conflicting requirement, ambiguous security/performance attribute, untestable acceptance criterion, missing/unresolved constrained-field citations (Coverage), or contradictory task constraints (Inconsistency)... **MEDIUM**: Terminology drift, missing non-functional task coverage, underspecified edge case. **LOW**: Style/wording improvements, minor redundancy not affecting execution order". — [templates/commands/analyze.md](https://github.com/github/spec-kit/blob/main/templates/commands/analyze.md)
- Analyze report format: findings table `| ID | Category | Severity | Location(s) | Summary | Recommendation |` with stable IDs "prefixed by category initial" (for example A1); Coverage Summary table `| Requirement Key | Has Task? | Task IDs | Notes |`; Constrained-Field Coverage table; Constitution Alignment Issues; Unmapped Tasks; Metrics (Total Requirements, Total Tasks, Coverage %, Ambiguity Count, Duplication Count, Critical Issues Count). "Limit to 50 findings total; aggregate remainder in overflow summary." "Rerunning without changes should produce consistent IDs and counts". — [templates/commands/analyze.md](https://github.com/github/spec-kit/blob/main/templates/commands/analyze.md)
- Analyze outcome handling: "If CRITICAL issues exist: Recommend resolving before `__SPECKIT_COMMAND_IMPLEMENT__`"; then ask "Would you like me to suggest concrete remediation edits for the top N issues?" "(Do NOT apply them automatically.)". The reference doc says to "return to the earlier step that owns them and fix them at the source". — [templates/commands/analyze.md](https://github.com/github/spec-kit/blob/main/templates/commands/analyze.md); [docs/reference/agentic-sdd.md](https://github.com/github/spec-kit/blob/main/docs/reference/agentic-sdd.md)
- Checklist concept, verbatim: "Checklists are **UNIT TESTS FOR REQUIREMENTS WRITING** - they validate the quality, clarity, and completeness of requirements in a given domain." "If your spec is code written in English, the checklist is its unit test suite." Wrong: "Verify the button clicks correctly". Right: "Is 'prominent display' quantified with specific sizing/positioning?" — [templates/commands/checklist.md](https://github.com/github/spec-kit/blob/main/templates/commands/checklist.md)
- Checklist intake: up to three dynamically derived clarifying questions (archetypes: scope refinement, risk prioritization, depth calibration, audience framing, boundary exclusion, scenario class gap), up to two follow-ups, "Do not exceed five total questions"; defaults when interaction is impossible: "Depth: Standard; Audience: Reviewer (PR) if code-related; Author otherwise; Focus: Top 2 relevance clusters". — [templates/commands/checklist.md](https://github.com/github/spec-kit/blob/main/templates/commands/checklist.md)
- Checklist item rules: question form about what is written; quality dimension in brackets (`[Completeness]`, `[Clarity]`, `[Consistency]`, `[Measurability]`, `[Coverage]`); reference `[Spec §X.Y]` or markers `[Gap]`, `[Ambiguity]`, `[Conflict]`, `[Assumption]`; "MINIMUM: ≥80% of items MUST include at least one traceability reference"; soft cap of 40 candidate items; categories: Requirement Completeness, Requirement Clarity, Requirement Consistency, Acceptance Criteria Quality, Scenario Coverage, Edge Case Coverage, Non-Functional Requirements, Dependencies & Assumptions, Ambiguities & Conflicts. — [templates/commands/checklist.md](https://github.com/github/spec-kit/blob/main/templates/commands/checklist.md)
- Prohibited patterns: "Any item starting with "Verify", "Test", "Confirm", "Check" + implementation behavior"; "References to code execution, user actions, system behavior"; "Test cases, test plans, QA procedures". Example correct item: `- [ ] CHK001 - Are the number and layout of featured episodes explicitly specified? [Completeness, Spec §FR-001]`. — [templates/commands/checklist.md](https://github.com/github/spec-kit/blob/main/templates/commands/checklist.md)
- File behaviour: one file per domain (`ux.md`, `api.md`, `security.md`, `performance.md`); new file starts at CHK001; existing file is appended to, continuing numbering; "Never delete or replace existing checklist content". — [templates/commands/checklist.md](https://github.com/github/spec-kit/blob/main/templates/commands/checklist.md)
- Ownership and lifecycle: "Custom checklists generated by this command are reviewer-owned"; the command "MUST NOT mark generated items `[x]`"; "An agent may assist with evaluating items only when explicitly asked by the reviewer"; implement reads the markers as a gate and "must not silently self-approve them". The built-in `checklists/requirements.md` is the one exception, maintained by specify and clarify. — [templates/commands/checklist.md](https://github.com/github/spec-kit/blob/main/templates/commands/checklist.md); [docs/reference/agentic-sdd.md](https://github.com/github/spec-kit/blob/main/docs/reference/agentic-sdd.md)

### Inferences
- Three distinct review layers exist with different owners: (a) self-check by the authoring agent (`requirements.md`), (b) human-owned requirement-quality checklists, (c) agent-run cross-artifact analysis. Only (b) is a real gate, and even that is a soft gate (the user can answer "yes" to proceed).
- "Every question ships with a recommended answer and can be accepted with 'yes'" is a low-friction human-in-the-loop pattern that maps well onto an ADK tool-confirmation or long-running-tool step.
- Analyze's determinism claim ("consistent IDs and counts") is aspirational: there is no stored report or hashing; findings are regenerated by the LLM on each run and are not persisted unless the user saves them.

### Gaps
- No evidence was collected on how reliably agents honour these limits in practice (for example the 80% traceability minimum); that needs issue-tracker or field evidence.

## 7. What is deterministic (scripts and the `specify` CLI) versus left to the LLM

### Takeaway
Deterministic code handles project scaffolding, feature-path resolution, precondition checks, template resolution and composition, prompt rendering per agent, upgrades, and (optionally) workflow orchestration; it communicates with prompts through small JSON objects on stdout. Everything semantic is left to the LLM, including some things one might expect to be code: feature numbering in the core specify prompt, hook dispatch, checklist counting, gate evaluation and task check-off.

### Cited Findings
- Script-to-prompt JSON contracts (Bash; PowerShell and Python mirror them):
  - `check-prerequisites.sh --json` → `{"FEATURE_DIR":"...","AVAILABLE_DOCS":["research.md","data-model.md","contracts/","quickstart.md"]}`; `--paths-only` → `{REPO_ROOT, BRANCH, FEATURE_DIR, FEATURE_SPEC, IMPL_PLAN, TASKS}` with no validation; `--template NAME` adds `TEMPLATE_CONTENT`; `--require-spec`, `--require-tasks`, `--include-tasks` tighten checks.
  - `setup-plan.sh --json` → `{FEATURE_SPEC, IMPL_PLAN, FEATURE_DIR, BRANCH}`.
  - `setup-tasks.sh --json` → `{FEATURE_DIR, AVAILABLE_DOCS, TASKS_TEMPLATE, TASKS_TEMPLATE_CONTENT}`.
  - `resolve-template.sh <name> --json` → `{TEMPLATE_NAME, TEMPLATE_CONTENT}`.
  - `create-new-feature.sh --json` → `{BRANCH_NAME, SPEC_FILE, FEATURE_NUM}` (plus `DRY_RUN:true`).
  — [scripts/bash/check-prerequisites.sh](https://github.com/github/spec-kit/blob/main/scripts/bash/check-prerequisites.sh); [scripts/bash/setup-plan.sh](https://github.com/github/spec-kit/blob/main/scripts/bash/setup-plan.sh); [scripts/bash/setup-tasks.sh](https://github.com/github/spec-kit/blob/main/scripts/bash/setup-tasks.sh); [scripts/bash/resolve-template.sh](https://github.com/github/spec-kit/blob/main/scripts/bash/resolve-template.sh); [scripts/bash/create-new-feature.sh](https://github.com/github/spec-kit/blob/main/scripts/bash/create-new-feature.sh)
- Precondition errors are actionable and name the command to run, for example "ERROR: plan.md not found in $FEATURE_DIR / Run <plan command> first to create the implementation plan."; an empty `plan.md` is also rejected. Diagnostics go to stderr so stdout stays parseable JSON. — [scripts/bash/check-prerequisites.sh](https://github.com/github/spec-kit/blob/main/scripts/bash/check-prerequisites.sh)
- JSON is built with `jq` when available and with a `printf` + `json_escape` fallback otherwise; path values are emitted with `printf '%q'` "preventing shell injection via crafted branch names or paths". — [scripts/bash/common.sh](https://github.com/github/spec-kit/blob/main/scripts/bash/common.sh)
- Feature resolution (`get_feature_paths`), in priority order: "1. - `setup-plan` copies the resolved plan template to `plan.md` only if it does not exist ("Plan already exists at ..., skipping template copy"), so re-running plan never clobbers a plan by script. — [scripts/bash/setup-plan.sh](https://github.com/github/spec-kit/blob/main/scripts/bash/setup-plan.sh)

Unicode names are preserved (`001-添加用户`). — [scripts/bash/create-new-feature.sh](https://github.com/github/spec-kit/blob/main/scripts/bash/create-new-feature.sh); [docs/overview/core.md](https://github.com/github/spec-kit/blob/main/docs/overview/core.md)

- Workflow engine: a deterministic orchestrator that runs YAML workflows whose steps dispatch commands or prompts to an agent's CLI headlessly. Emitting the block alone does not run the hook." Conditions are explicitly not evaluated by the agent: "do **not** attempt to interpret or evaluate hook `condition` expressions... skip the hook and leave condition evaluation to the HookExecutor implementation". — [templates/commands/plan.md](https://github.com/github/spec-kit/blob/main/templates/commands/plan.md)
- A Python `HookExecutor` class exists in the CLI and can sort hooks by priority and evaluate conditions (`config.<path>` or `env.<VAR>` with `is set`, `==`, `!=`), but the docs state the agent-run path bypasses it: "Current command templates do not evaluate conditions and skip hooks with a non-empty condition", "Current command templates use configured YAML order, not priority sorting", and the `auto_execute_hooks` setting "is reserved and is not consulted when hooks are surfaced or invoked." — [docs/extensions/api.md](https://github.com/github/spec-kit/blob/main/docs/extensions/api.md); [src/specify_cli/extensions/__init__.py](https://github.com/github/spec-kit/blob/main/src/specify_cli/extensions/__init__.py)
- By contrast, runtime events (July 2026) are executed directly as scripts by the agent's native hook system (`session_start`, `pre_tool_use`, `post_tool_use`, `session_end`, `user_prompt_submit`, `stop` mapped to Claude Code's `SessionStart`, `PreToolUse`, ... in `.claude/settings.json`): "Unlike command hooks, these events execute scripts directly rather than asking the agent to follow additional instructions." — [docs/overview/history.md](https://github.com/github/spec-kit/blob/main/docs/overview/history.md); [src/specify_cli/integrations/claude/__init__.py](https://github.com/github/spec-kit/blob/main/src/specify_cli/integrations/claude/__init__.py)
- Left to the LLM by prompt: short-name generation; spec, plan, research, data-model, contracts, quickstart and tasks content; constitution gate evaluation; the spec quality self-check; counting checklist checkboxes in implement; marking tasks `[X]`; ignore-file generation; all analyze and converge findings. — [templates/commands/](https://github.com/github/spec-kit/tree/main/templates/commands)
- Three script variants are maintained with required parity: Bash, PowerShell ("MUST target Windows PowerShell 5.1") and Python (opt-in `--script py`; non-interactive init defaults to `sh` on POSIX or `ps` on Windows). — [AGENTS.md](https://github.com/github/spec-kit/blob/main/AGENTS.md); [design/integration.md](https://github.com/github/spec-kit/blob/main/design/integration.md)

### Inferences
- The deterministic layer is intentionally thin on semantics: no script parses a spec, validates FR numbering, checks the task grammar, or computes coverage. For a Python/ADK framework this is the biggest opportunity: the task line grammar, ID uniqueness, FR→task coverage, checklist counts and "converged means tasks.md unchanged" are all trivially checkable in code and could be ADK tools or callbacks instead of prompt instructions.
- Maintaining three shell variants exists only because Spec Kit targets agents that can run shell but have no host runtime. A framework that owns its runtime (ADK) can replace the scripts with Python function tools and drop that cost entirely.
- The JSON-over-stdout contract (script returns absolute paths and a list of available docs; prompt reads only what exists) is a good fit for ADK session state: a "resolve feature context" tool could populate state keys equivalent to `FEATURE_DIR`, `AVAILABLE_DOCS`.

### Gaps
- `docs/workflow-steps/types.md` was read only at heading level (command, prompt, shell, GitHub, init, slots, gate, if/then/else, switch, while, do-while, fan-out, fan-in, workflow composition); the on-disk format of workflow run state was not examined.
- No caller of `HookExecutor` in an agent-run path was identified, so when conditional hooks actually execute (other than in tests or tooling) is unresolved.
- The PowerShell and Python script variants were not compared line by line with Bash.

## 8. Extensions, presets, customization, and multi-agent support

### Takeaway
Customization is layered: project-local overrides beat presets (priority-ordered) beat extensions beat core, with `replace`, `prepend`, `append` and `wrap` composition; extensions add commands, scripts, config and hooks, presets change existing templates and commands, workflows automate, bundles package. Agent support is an adapter registry of 41 named agents (plus `generic` and `none`) that renders the same Markdown command sources into four output flavours (Markdown commands, TOML commands, YAML recipes, agent skills).

### Cited Findings
- The five primitives and their roles: "**Integrations** connect Spec Kit to coding agents. **Extensions** add capabilities, commands, templates, scripts, and hooks. **Presets** customize or replace behavior. **Workflows** automate multi-step processes. **Workflow steps** provide reusable units of workflow behavior." Bundles package extensions, presets, workflows and steps for a role or team; catalogs make components discoverable. — [docs/overview/history.md](https://github.com/github/spec-kit/blob/main/docs/overview/history.md)
- Choosing a building block (from the customization guide): new command or process, or an external tool → Extension; change format or terminology of specs/plans/tasks, or enforce organizational standards → Preset; one-off template tweak → project-local override in `.specify/templates/overrides/`; automate a multi-step process → Workflow; role-based setup → Bundle. — [docs/how-to/customization.md](https://github.com/github/spec-kit/blob/main/docs/how-to/customization.md)
- Resolution order: "1. Project-local overrides. 2. Installed presets, in priority order. 3. Installed extensions, in priority order. 4. Spec Kit core templates in `.specify/templates/`." Templates "are resolved when needed, using the first match by default"; commands differ: "installing extensions or presets materializes command files into the active integration's directory. Agents do not re-resolve that stack every time they invoke a command." — [docs/how-to/customization.md](https://github.com/github/spec-kit/blob/main/docs/how-to/customization.md)
- Extension manifest (`extension.yml`, `schema_version: "1.0"`): `extension` (id, name, version, description, author, repository, license); `requires` (`speckit_version`, `tools` with `required`); `provides.commands` (name such as `speckit.git.feature`, file, description) and `provides.config`; `hooks` keyed by event with `command`, `optional`, `prompt`, `description`; `tags`; `config.defaults`. — [extensions/git/extension.yml](https://github.com/github/spec-kit/blob/main/extensions/git/extension.yml)
- Hook events seen in core prompts and the git manifest: `before_` and `after_` for `constitution`, `specify`, `clarify`, `plan`, `tasks`, `implement`, `checklist`, `analyze`, `converge`, `taskstoissues`. Hooks are either mandatory (`optional: false`, auto-executed) or optional (printed as a suggestion with its `prompt`). — [extensions/git/extension.yml](https://github.com/github/spec-kit/blob/main/extensions/git/extension.yml); [templates/commands/converge.md](https://github.com/github/spec-kit/blob/main/templates/commands/converge.md)
- Preset manifest (`preset.yml`): `provides.templates` entries with `type` (for example `"command"`), `name`, `file`, `description`, `replaces`. The `lean` preset replaces five commands; `constitution-sync` ships "a single `wrap`-strategy override of `speckit.constitution`" that "composes on top of the current core command (via `{CORE_TEMPLATE}`)". Presets can be stacked with priorities and enabled or disabled. 1.4.3 added "bounded Markdown section replacement" for presets. — [presets/lean/preset.yml](https://github.com/github/spec-kit/blob/main/presets/lean/preset.yml); [presets/constitution-sync/README.md](https://github.com/github/spec-kit/blob/main/presets/constitution-sync/README.md); [CHANGELOG.md](https://github.com/github/spec-kit/blob/main/CHANGELOG.md)
- Composition strategies, declared per artifact in the manifest: `replace` (default), `prepend`, `append`, `wrap` (placeholder `{CORE_TEMPLATE}`; `$CORE_SCRIPT` for scripts) and `replace-section` with a `selector` naming one Markdown heading by GitHub-style anchor (templates and commands only). "A highest-precedence `replace` layer wins entirely. Otherwise, resolution finds the nearest lower `replace` base and applies only the layers above it, bottom-up." Within the preset and extension layers "lower priority numbers win, then alphabetical IDs break ties". Composed commands use "the highest-priority available frontmatter" and inherit `scripts` from the base. — [docs/presets/api.md](https://github.com/github/spec-kit/blob/main/docs/presets/api.md)
- Project hook registry `.specify/extensions.yml`: top-level `installed` (extension IDs), `settings`, and `hooks` grouped by event; each hook entry has `extension`, `command`, `enabled`, `optional`, `priority` (integer ≥ 1, default 10), `prompt`, `description`, `condition`. — [docs/extensions/api.md](https://github.com/github/spec-kit/blob/main/docs/extensions/api.md)
- Workflows are customized without forking through overlays: "An overlay can fill a named slot or insert, replace, and remove steps; it cannot change the base input schema." — [docs/workflows/overview.md](https://github.com/github/spec-kit/blob/main/docs/workflows/overview.md)
- Presets can override commands and templates "supplied by the core **and by installed extensions**"; suggested uses include regulatory traceability, test-first task ordering, security review gates in plans, localization, and adapting to Agile, Kanban, Waterfall, jobs-to-be-done or DDD. — [docs/how-to/customization.md](https://github.com/github/spec-kit/blob/main/docs/how-to/customization.md)
- Integration contract: each agent is a Python class declaring `key`, `config` (name, folder, commands subdirectory, install URL, `requires_cli`) and `registrar_config` (output dir, format, argument placeholder, file extension). Output flavours: Markdown commands (`commands/speckit.plan.md`, `$ARGUMENTS`), TOML commands (`commands/speckit.plan.toml`, `{{args}}`), YAML recipes (`recipes/speckit.plan.yaml`, `{{args}}`), Agent skills (`skills/speckit-plan/SKILL.md`, `$ARGUMENTS`). — [design/integration.md](https://github.com/github/spec-kit/blob/main/design/integration.md)
- Invocation spelling differs per agent: dotted `/speckit.specify` (reference notation), `/speckit-specify` (Copilot default skills mode), `$speckit-specify` (Codex, Command Code, ZCode skills), `/skill:speckit-specify` (Kimi). Copilot switched to skills by default in August 2026, "replacing the legacy markdown-command layout as its default delivery route". — [docs/integrations/cli.md](https://github.com/github/spec-kit/blob/main/docs/integrations/cli.md); [docs/overview/history.md](https://github.com/github/spec-kit/blob/main/docs/overview/history.md)
- Supported integration keys (43 rows): alquimia, amp, agy (Antigravity), auggie, claude, cline, codebuddy, codex, command-code, cursor-agent, dsh, devin, docker-agent, droid, firebender, forge, gemini, copilot, goose, grok, hermes, bob, junie, kilocode, kimi, kiro-cli, lingma, mcode, vibe, muse, none, omp, opencode, pi, qodercli, qwen, rovodev, shai, tabnine, trae, zcode, zed, generic. `generic` takes a user-supplied `--commands-dir`; `none` installs shared scaffolding only. — [docs/integrations/index.md](https://github.com/github/spec-kit/blob/main/docs/integrations/index.md); [design/integration.md](https://github.com/github/spec-kit/blob/main/design/integration.md)
- Claude Code adapter specifics: skills in `.claude/skills`, per-command `argument-hint` text (for example specify: "Describe the feature you want to specify"), native events written to `.claude/settings.json`. A previous attempt to run `analyze` in a forked subagent (`context: fork`) was reverted: "`/speckit-analyze` returns a 300-500 line report that is injected back into the main conversation. In long sessions each subsequent fork inherits that growing context, compounding overhead until the chat freezes (#3185)." — [src/specify_cli/integrations/claude/__init__.py](https://github.com/github/spec-kit/blob/main/src/specify_cli/integrations/claude/__init__.py)
- Multi-agent teams: start agent-neutral (`specify init my-project --integration none`), each developer runs `specify integration switch <key>` locally and switches back to `none` before committing; "Do not manually edit Spec Kit-generated agent commands or skills. Maintain customizations in reviewed presets or project-local overrides." Multiple integrations can be installed if `multi_install_safe`. — [docs/integrations/index.md](https://github.com/github/spec-kit/blob/main/docs/integrations/index.md)
- Generated `SKILL.md` frontmatter carries `metadata.version` provenance (added 1.4.2) but "this metadata does not perform stale-skill detection or upgrades". — [docs/integrations/index.md](https://github.com/github/spec-kit/blob/main/docs/integrations/index.md)
- Trust model for third-party components: "Catalog listings are not audits or endorsements, so review community source code before installing or running it"; the default community integration catalog is discovery-only, and external adapters need an explicit trust decision (`--trust-integration`). — [README.md](https://github.com/github/spec-kit/blob/main/README.md); [design/integration.md](https://github.com/github/spec-kit/blob/main/design/integration.md)

### Inferences
- The split "templates resolve at runtime, commands materialize at install time" is a consequence of agents loading static prompt files. A framework with its own runtime can resolve both at run time, which removes the whole reconciliation problem (commands being "clobbered the next time the stack reconciles").
- For an ADK framework the worthwhile ideas here are the layering order, the four composition strategies, before/after hook events per phase, and an introspection command that shows which layer supplies each artifact. The 43-agent adapter matrix is not needed.
- Because hooks run by asking the model to run another command, mandatory hooks are only as reliable as the model's compliance; ADK `before_agent_callback` / `after_agent_callback` would make the same hook points deterministic.

### Gaps
- `docs/extensions/api.md` and `docs/presets/api.md` were read only for hook configuration, file resolution and composition strategies; their Python API sections, extension config layering and runtime-event schema were seen at heading level only.
- Bundle manifest format (`bundle.yml`) and catalog JSON schemas were not examined.

## 9. Documented limitations, known issues and commonly requested features; brownfield and spec evolution

### Takeaway
The repo's own docs concede the main structural limits: there is no automatic reconciliation between spec, plan and tasks; spec persistence after delivery is left to team convention; brownfield adoption means "initialize in place and spec the next bounded change", with no inference of specs from existing code; and large features degrade from context exhaustion unless implementation is staged by hand. The tracker agrees: the most-upvoted issue in the project's history (105 thumbs-up) and its most-commented top discussion (132 comments) are both about updating and evolving existing specs, followed by brownfield adoption, upgrades, monorepos and agent support.

### Cited Findings
- No reconciliation command: "Core has no dedicated command that automatically reconciles differences among `spec.md`, `plan.md`, and `tasks.md`. Analyze reports inconsistencies without editing artifacts. Reconcile them directly, or use an extension according to its documented behavior." — [docs/how-to/evolving-specs.md](https://github.com/github/spec-kit/blob/main/docs/how-to/evolving-specs.md)
- Spec evolution procedure for a changed requirement: assess whether it is "a defect against agreed intent" or "a proposed change to that intent"; write the intended contract in `spec.md` (new feature directory via `/speckit.specify` or revise the existing one); re-run or revise plan and tasks; run analyze; then implement and converge. "The implementation is evidence for the discussion, not a replacement source of requirements." — [docs/how-to/evolving-specs.md](https://github.com/github/spec-kit/blob/main/docs/how-to/evolving-specs.md)
- Converge will not accept code as the new truth: "It does not rewrite artifacts to accept code as a replacement for documented intent." — [docs/how-to/evolving-specs.md](https://github.com/github/spec-kit/blob/main/docs/how-to/evolving-specs.md)
- Spec persistence is undecided by design; each model has a named risk: flow-back "silent divergence"; flow-forward "duplication. Related decisions can be spread across multiple feature directories"; living spec "losing useful implementation rationale if derived artifacts are discarded"; constitution-only "losing intent and rationale that cannot be reliably recovered by regenerating artifacts". — [docs/how-to/persisting-specs.md](https://github.com/github/spec-kit/blob/main/docs/how-to/persisting-specs.md)
- Brownfield: "You do not need to recreate an existing system from specifications before using Spec Kit." Run `specify init --here --force --integration <key>`; init "does not rewrite your application or infer specifications for existing behavior." "The new `spec.md` defines the change you intend to make, not a retroactive specification of every existing behavior." "Do not make "document the entire existing system" your first feature unless that inventory is itself the intended deliverable." Architecture discovery and brownfield bootstrapping are delegated to community extensions. — [docs/how-to/existing-projects.md](https://github.com/github/spec-kit/blob/main/docs/how-to/existing-projects.md)
- `--force` "may replace files at conflicting managed paths, so use it only after creating a reviewable baseline." — [docs/how-to/existing-projects.md](https://github.com/github/spec-kit/blob/main/docs/how-to/existing-projects.md)
- Feature specs are per-change, numbered directories; there is no built-in capability-level or system-level living spec. A community article linked from the README ("Living Specs in SpecKit", 2026-10-15) "explores maintaining capability-level specifications as a project evolves", which indicates this is addressed outside core. — [README.md](https://github.com/github/spec-kit/blob/main/README.md)
- Context-size pressure is acknowledged: stage `/speckit.implement` "to avoid overwhelming the agent's context"; analyze is told to use "Progressive disclosure" and cap findings at 50; the Claude fork experiment was reverted because large analyze reports made long sessions freeze (#3185). — [docs/reference/agentic-sdd.md](https://github.com/github/spec-kit/blob/main/docs/reference/agentic-sdd.md); [templates/commands/analyze.md](https://github.com/github/spec-kit/blob/main/templates/commands/analyze.md); [src/specify_cli/integrations/claude/__init__.py](https://github.com/github/spec-kit/blob/main/src/specify_cli/integrations/claude/__init__.py)
- Known issue classes visible in code comments and changelog: `feature.json` written by read-only path resolution dirtied the working tree (#3025); concurrent agents overwriting each other's `feature.json` (#4128, #4129); Windows `python3` alias stub breaking JSON parsing (#3304); option-like feature descriptions such as `-n` being eaten by `echo` (#5245, #5247); many PowerShell 5.1 encoding and bracketed-path fixes in 1.4.1 to 1.4.3. — [scripts/bash/common.sh](https://github.com/github/spec-kit/blob/main/scripts/bash/common.sh); [scripts/bash/check-prerequisites.sh](https://github.com/github/spec-kit/blob/main/scripts/bash/check-prerequisites.sh); [CHANGELOG.md](https://github.com/github/spec-kit/blob/main/CHANGELOG.md)
- Incomplete internal migrations are documented: the symlink policy "does not yet route all other command filesystem operations through FileHelper... The persisted setting does not imply that every filesystem operation already enforces it." — [docs/overview/core.md](https://github.com/github/spec-kit/blob/main/docs/overview/core.md)
- Stale documentation is itself a limitation: `spec-driven.md` describes three commands, in-command branch creation, `implementation-details/` files, mandatory `[NEEDS CLARIFICATION]` for every ambiguity, and Phase -1 gates, none of which match the current templates; the command reference still says the constitution command "keeps dependent templates in sync". — [spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md); [docs/reference/agentic-sdd.md](https://github.com/github/spec-kit/blob/main/docs/reference/agentic-sdd.md)
- Large-feature failure mode, in the docs' own words: "In the middle of a long `/speckit.implement` run, agents can start to lose track of the plan, ignore tasks, or hallucinate — usually right before or after context compaction is triggered. ### Inferences
- Mapping requests to today's features (my reading, not maintainer statements): the fix-loop request is answered by the `bug` extension and `/speckit.converge`; multi-agent by multi-install and `specify integration switch`; naming by the git extension's `branch_template`; upgrades by `specify self upgrade`, `specify integration upgrade` and the hash manifest; root clutter by `.specify/`. Still unanswered in core: an in-place revise flow with superseded requirements, persistent module-level or capability-level specs, reverse-engineering specs from code, and tooling for epic decomposition. These are the clearest places for a new framework to differentiate.
- GitHub marks closed issues "completed" by default and this repo auto-stales issues, so a closed high-vote issue (for example #1191) does not show the request was implemented; the docs still say core "has no dedicated command" for reconciliation and #4156 remains open.
- In a monorepo there is no shared constitution or cross-project spec in core: each member is a separate project, so organization-wide rules have to travel as presets.
- Strengths worth copying: bounded, explicit prompt contracts; stable IDs enabling traceability; the pointer-file feature context; quality gates as separate optional commands; append-only convergence loop; layered customization with introspection; hash-manifest upgrades.
- Weaknesses to avoid: almost all enforcement is by prompt; heavy Markdown volume per feature (spec, plan, research, data-model, contracts, quickstart, tasks, checklists) with no built-in lifecycle after merge; no system-level spec, so knowledge fragments across numbered feature folders; hook reliability depends on the model; documentation drift from a very fast release cadence; a large surface (43 integrations, three script languages) that a single-runtime framework does not need.
- The `lean` preset's existence is an implicit admission that the default templates are too ceremonious for small changes; a new framework should offer a scale-down path (for example a single-file quick spec) from the start.
