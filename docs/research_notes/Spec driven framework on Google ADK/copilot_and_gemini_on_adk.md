## Ways to call GitHub Copilot models from Python, and which ADK supports

### Takeaway
There are two live routes: LiteLLM's `github_copilot/<model>` provider through ADK's `LiteLlm` wrapper, which is unofficial from GitHub's side and presents itself to Copilot as VS Code's chat client, and the official Copilot SDK (now `microsoft-copilot-sdk`), which is an agent runtime rather than a chat-completions API and has no ADK integration. GitHub Models (`github/<model>`) was retired on 2026-07-30, and ADK 2.15.0 contains nothing native for Copilot.

### Cited Findings
**ADK itself**
- No Python file in the `google-adk` 2.15.0 wheel mentions "copilot", `github_copilot` or GitHub Models. — [google-adk 2.15.0 files](https://pypi.org/project/google-adk/2.15.0/#files)
- ADK's model registry sends bare `gpt-*` and `o<digit>-*` names to its own `OpenAILlm` (OpenAI's API), `claude-*` to `Claude`, and `gemini-*` to `Gemini`. The `LiteLlm` registry patterns list `openai/`, `azure/`, `anthropic/`, `bedrock/`, `vertex_ai/` and others, but not `github_copilot/`. A Copilot model must therefore be passed as an instance, `LiteLlm(model="github_copilot/<name>")`; a bare string will not reach Copilot. — [google-adk 2.15.0 files (`google/adk/models/__init__.py`)](https://pypi.org/project/google-adk/2.15.0/#files)
- ADK's documentation describes `LiteLlm` as the connector for models outside Google's ecosystem and asks for `litellm>=1.84`. It does not mention GitHub Copilot. — [ADK docs, LiteLLM](https://adk.dev/agents/models/litellm/)

**LiteLLM `github_copilot/<model>`**
- LiteLLM documents the provider for Chat Completions, Responses, Embeddings and Anthropic Messages, through its gateway or the Python SDK, and says "Your GitHub Copilot plan determines which models you can use". — [LiteLLM docs, GitHub Copilot](https://docs.litellm.ai/docs/providers/github_copilot)
- Direct SDK calls sign in with one GitHub account by OAuth device flow on first use and cache the token on disk. No API key is involved. — [LiteLLM docs, GitHub Copilot](https://docs.litellm.ai/docs/providers/github_copilot)
- The provider's default OAuth client id is `Iv1.b507a08c87ecfe98`, and every request carries headers that name VS Code's Copilot Chat: `copilot-integration-id: vscode-chat`, `editor-version: vscode/1.95.0`, `editor-plugin-version: copilot-chat/0.26.7`, `user-agent: GitHubCopilotChat/0.26.7`, `openai-intent: conversation-panel`, `x-github-api-version: 2025-04-01`. — [litellm 1.110.2 files (`litellm/llms/github_copilot/authenticator.py`, `common_utils.py`)](https://pypi.org/project/litellm/1.110.2/#files)
- LiteLLM's docs describe a second, organization-billed mode "since v1.111.0": a GitHub App with the "Copilot Requests" organization permission, whose installation token is sent with `copilot-developer-cli` as the integration id. 1.111.0 existed only as release candidates on 2026-11-20. — [LiteLLM docs, GitHub Copilot](https://docs.litellm.ai/docs/providers/github_copilot); [PyPI JSON for litellm](https://pypi.org/pypi/litellm/json)
- GitHub documents that app path on its own side: "A GitHub App installed on an organization can use an installation access token to make Copilot requests without a user signing in. The organization that owns the installation pays for the usage, and the organization's model policies and spending controls apply." — [GitHub docs, usage-based billing for organizations](https://docs.github.com/en/copilot/concepts/billing/usage-based-billing-for-organizations-and-enterprises)

**Official Copilot SDK**
- The PyPI package `github-copilot-sdk` (1.0.35, 2026-11-18) has the summary "Deprecated GitHub Copilot SDK. Migrate to microsoft-copilot-sdk." The successor `microsoft-copilot-sdk` was first published 2026-11-10; 2.0.1 is dated 2026-11-18; it requires Python 3.11 or newer and both packages carry the classifier "Development Status :: 3 - Alpha". — [PyPI JSON for github-copilot-sdk](https://pypi.org/pypi/github-copilot-sdk/json); [PyPI JSON for microsoft-copilot-sdk](https://pypi.org/pypi/microsoft-copilot-sdk/json)
- The repository README says "GitHub Copilot SDK is becoming Microsoft Copilot SDK", gives `pip install microsoft-copilot-sdk`, and its FAQ says the SDK "is generally available and follows semantic versioning". — [Copilot SDK repository](https://github.com/github/copilot-sdk)
- The SDK "exposes the same engine behind Copilot CLI: a production-tested agent runtime you can invoke programmatically". It talks JSON-RPC to a native runtime, runs its own planning and tool loop behind a permission handler, and does not expose a raw chat-completions call. — [Copilot SDK repository](https://github.com/github/copilot-sdk)
- SDK authentication, in priority order: an explicit `github_token`; `GITHUB_COPILOT_API_TOKEN` with `COPILOT_API_URL`; the environment variables `COPILOT_GITHUB_TOKEN`, `GH_TOKEN`, `GITHUB_TOKEN`; stored credentials from a `copilot` CLI login; `gh auth` credentials. Supported token prefixes are `gho_`, `ghu_` and `github_pat_`; classic `ghp_` tokens are not supported. — [GitHub docs, Copilot SDK authentication](https://docs.github.com/en/copilot/how-tos/copilot-sdk/auth/authenticate)
- A Copilot subscription is required for the signed-in, OAuth and environment-variable methods; server-to-server (GitHub App installation token, `ghs_`, one-hour life) needs no user subscription but an organization policy; BYOK needs no subscription and is billed by the model provider. — [GitHub docs, Copilot SDK authentication](https://docs.github.com/en/copilot/how-tos/copilot-sdk/auth/authenticate); [GitHub docs, server-to-server tokens](https://docs.github.com/en/copilot/how-tos/copilot-sdk/auth/server-to-server-tokens)
- The Python SDK downloads its runtime with `python -m copilot download-runtime`, or on first use. — [GitHub docs, Copilot SDK bundled runtime](https://docs.github.com/en/copilot/how-tos/copilot-sdk/setup/bundled-cli)

**Billing, limits and terms**
- Copilot usage is billed in GitHub AI Credits by tokens at each model's rate ("1 AI credit = $0.01 USD"). Copilot Chat, Copilot CLI, cloud agent, Spaces, Spark and "third-party coding agents" consume credits; code completions do not. — [GitHub docs, usage-based billing for individuals](https://docs.github.com/en/copilot/concepts/billing/usage-based-billing-for-individuals)
- Monthly allowances: Pro 1,500 credits ($10), Pro+ 7,000 ($39), Max 20,000 ($100); Business 1,900 and Enterprise 3,900 per user, pooled. Additional usage is enabled by default on Business and Enterprise unless the "AI credits paid usage" policy is disabled. — [GitHub docs, usage-based billing for individuals](https://docs.github.com/en/copilot/concepts/billing/usage-based-billing-for-individuals); [GitHub docs, usage-based billing for organizations](https://docs.github.com/en/copilot/concepts/billing/usage-based-billing-for-organizations-and-enterprises)
- "Premium request" multipliers survive only for subscribers on existing annual Pro and Pro+ plans under "request-based billing (legacy)". — [GitHub docs, models and pricing](https://docs.github.com/en/copilot/reference/copilot-billing/models-and-pricing)
- GitHub publishes no numeric rate limits. Its page says limits are temporary, exist for capacity, fairness and "abuse mitigation", and advises: "If you're making frequent or automated requests", consider adjusting usage. — [GitHub docs, rate limits](https://docs.github.com/en/copilot/concepts/rate-limits)
- GitHub's Terms of Service, Section H: "Abuse or excessively frequent requests to GitHub via the API may result in" suspension of API access, and "You may not share API tokens to exceed GitHub's rate limitations." — [GitHub Terms of Service](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service)
- GitHub's Acceptable Use Policies prohibit "using our servers for any form of excessive automated bulk activity" and say "You will not reproduce, duplicate, copy, sell, resell or exploit any portion of the Service, use of the Service, or access to the Service without our express written permission." — [GitHub Acceptable Use Policies](https://docs.github.com/en/site-policy/acceptable-use-policies/github-acceptable-use-policies)
- Which terms govern Copilot depends on how it was bought: GitHub Generative AI Services Terms for Business and Enterprise bought from GitHub, Microsoft's Product Terms when bought through Microsoft, and Section J of the Terms of Service for everyone else. — [GitHub Terms for Additional Products and Features](https://docs.github.com/en/site-policy/github-terms/github-terms-for-additional-products-and-features)
- `adk_review` records, as live observation, a per-user Copilot rate limit on a utility-class model that "lasts hours", and a `model_not_supported` answer when the plan or organization policy leaves a model off. — `/Users/emrec/Projects/playground/adk_review/adk_review/judge/plugins.py`, `/Users/emrec/Projects/playground/adk_review/GUIDE.md`

### Inferences
- The device-flow route used by LiteLLM, and so by the Copilot arm of the design, is not a GitHub-supported integration. The evidence is in LiteLLM's own source: it signs in with a fixed client id and labels its traffic as VS Code's Copilot Chat. GitHub's documentation lists the SDK, the CLI, IDE extensions and GitHub Apps with the "Copilot Requests" permission as the ways in, and does not list LiteLLM or a raw HTTP API. GitHub could change headers, client-id acceptance or endpoints without notice, and the behavior would break without any deprecation period.
- The seat that logged in pays for every call at token rates, and an LLM-heavy multi-agent workflow can spend a Pro allowance (1,500 credits, $15 of tokens) quickly. A spec workflow should report token usage per run and let the operator cap it.
- The terms located do not forbid a custom client by name; the exposure is the general clauses on automated bulk activity, abuse of the API, and rate-limit circumvention, plus whatever the Generative AI Services Terms say for Business and Enterprise seats. An organization that plans to run this widely on Windows should get its GitHub account team's position in writing.
- The GitHub App route (LiteLLM 1.111.0 and later) is the closest thing to an officially documented, organization-billed path that still fits ADK's `LiteLlm` wrapper. It is not yet in a stable LiteLLM release and is far outside ADK's declared LiteLLM range.
- The official SDK cannot simply replace LiteLLM under ADK: ADK needs a `BaseLlm` that returns one model turn, and the SDK returns the result of its own agent loop with its own tools. Using it would mean a custom `BaseLlm` adapter with the SDK's tools disabled, or running Copilot as a separate agent beside ADK. Neither exists in ADK or in `adk_review`.

### Gaps
- No GitHub statement was found that explicitly permits or forbids using a Copilot subscription through a third-party HTTP client such as LiteLLM. The GitHub Generative AI Services Terms and Microsoft Product Terms were not retrieved.
- Whether a GitHub App installation token is accepted on Copilot's chat-completions and responses endpoints outside the SDK, as LiteLLM 1.111.0 assumes, was not verified.
- GitHub publishes no rate-limit numbers, so the limits for sustained agent traffic through this route are unknown.

### Inferences
- A default of `gpt-4.1` is a retired model by GitHub's own table. `adk_review` already says it "answers while Copilot serves it"; a new framework should not default to it. - Every current Copilot GPT model is served only on the Responses API according to LiteLLM's map, so the Copilot arm with a GPT model depends on LiteLLM's chat-to-Responses bridge, and all of them are reasoning models with temperature restrictions (see below). Copilot's Claude models stay on chat completions.
- Models GitHub lists but LiteLLM's map lacks (`gpt-6.2-sol`, `claude-fable-5.2`, the other Gemini 4 models) can still be named, but LiteLLM then has no mode, context size or capability flags for them. A Responses-only model missing from the map would be sent to chat completions and probably fail, and ADK would treat it as lacking structured output and reasoning support. Registering the model with LiteLLM or waiting for a release is needed.
- Model availability must be configuration, validated at start: a seat's plan and its organization's policy decide what answers, and a disabled model fails at call time with `model_not_supported`.

- The Copilot API's own model-list endpoint, and whether LiteLLM exposes it, was not examined; a start-up check that asks Copilot which models the seat may use is therefore not confirmed.
- Context sizes are LiteLLM's map values, not GitHub's published numbers; GitHub's docs give no per-model context size for API-style use.

## How LiteLLM's `github_copilot` provider works (device flow, token storage, refresh, headers, Enterprise, flags)

### Takeaway
The mechanics the owner's documents describe (60-second poll, token directory, the system-to-assistant flag, GitHub Enterprise overrides) are correct for LiteLLM 1.106.2 through 1.109.x, but LiteLLM 1.110.0 rewrote the authenticator: there is no Copilot API-key exchange any more, `api-key.json`, `GITHUB_COPILOT_API_KEY_URL`, `GITHUB_COPILOT_API_KEY_FILE` and `GetAPIKeyError` are gone, and a login tool written the way `adk_review`'s is cannot import against 1.110.0 or 1.110.2.

### Cited Findings
**Common to 1.106.2, 1.108.13, 1.109.1, 1.109.3, 1.110.0 and 1.110.2**
- Device login is refused when the caller cannot block: every version read checks `can_block_current_thread()` and otherwise raises `GetAccessTokenError` (status 401) with "GitHub Copilot device-code login needs a human and cannot run inside a running event loop or a worker thread". The chat path converts it to `AuthenticationError`. — [litellm 1.110.0 files (`litellm/llms/github_copilot/authenticator.py`)](https://pypi.org/project/litellm/1.110.0/#files); [litellm 1.106.2 files (`litellm/llms/github_copilot/authenticator.py`)](https://pypi.org/project/litellm/1.106.2/#files)
- With `LITELLM_LOCAL_MODEL_COST_MAP` set to true LiteLLM uses the model map bundled in the installed version instead of fetching one. — [litellm 1.110.0 files (`litellm/litellm_core_utils/get_model_cost_map.py`)](https://pypi.org/project/litellm/1.110.0/#files)
- The system-to-assistant flag is read only in the chat-completions transformation. On the Responses path, which LiteLLM's bridge uses for models whose map entry says `mode: responses`, system messages are turned into the Responses `instructions` field, and the Copilot Responses transformation has no role rewriting. — [litellm 1.110.0 files (`litellm/llms/github_copilot/chat/transformation.py`, `litellm/llms/github_copilot/responses/transformation.py`, `litellm/completion_extras/litellm_responses_transformation/transformation.py`)](https://pypi.org/project/litellm/1.110.0/#files)
- Device flow: POST to `https://github.com/login/device/code` with `client_id` and `scope: read:user`, print "Please visit {verification_uri} and enter code {user_code} to authenticate.", then poll `https://github.com/login/oauth/access_token`. — [litellm 1.110.2 files (`litellm/llms/github_copilot/authenticator.py`)](https://pypi.org/project/litellm/1.110.2/#files)
- Polling stops after one minute: `max_attempts: Final = 12  # 1 minute (12 * 5 seconds)`, with `time.sleep(5)` between polls. The whole login is attempted up to three times, each with a new code. The poll does not handle GitHub's `slow_down` answer or read `expires_in`. — [litellm 1.110.2 files (`litellm/llms/github_copilot/authenticator.py`)](https://pypi.org/project/litellm/1.110.2/#files); [litellm 1.106.2 files (`litellm/llms/github_copilot/authenticator.py`)](https://pypi.org/project/litellm/1.106.2/#files)
- Token directory: `os.getenv("GITHUB_COPILOT_TOKEN_DIR", os.path.expanduser("~/.config/litellm/github_copilot"))`. Only the default is passed through `expanduser`; a value set in the environment is used as written, so `~/x` there names a directory literally called `~`. The access token file is `access-token`, or `GITHUB_COPILOT_ACCESS_TOKEN_FILE`. — [litellm 1.110.2 files (`litellm/llms/github_copilot/authenticator.py`)](https://pypi.org/project/litellm/1.110.2/#files)
- The default is the same expression on every operating system, so on Windows it is `%USERPROFILE%\.config\litellm\github_copilot` and on macOS `~/.config/litellm/github_copilot`; LiteLLM does not use `%APPDATA%` or `~/Library`. — [litellm 1.110.2 files (`litellm/llms/github_copilot/authenticator.py`)](https://pypi.org/project/litellm/1.110.2/#files)
- The token file is written with a plain `open(self.access_token_file, "w")`, with no permission change, and the directory is made with `os.makedirs(..., exist_ok=True)`. — [litellm 1.110.2 files (`litellm/llms/github_copilot/authenticator.py`)](https://pypi.org/project/litellm/1.110.2/#files)
- Endpoint overrides present in all four versions: `GITHUB_COPILOT_CLIENT_ID`, `GITHUB_COPILOT_DEVICE_CODE_URL`, `GITHUB_COPILOT_ACCESS_TOKEN_URL`, `GITHUB_COPILOT_API_BASE` (default `https://api.githubcopilot.com`). — [litellm 1.110.2 files (`litellm/llms/github_copilot/`)](https://pypi.org/project/litellm/1.110.2/#files); [litellm 1.106.2 files (`litellm/llms/github_copilot/`)](https://pypi.org/project/litellm/1.106.2/#files)
- `litellm.disable_copilot_system_to_assistant: bool = False` is defined in `litellm/__init__.py` with the comment "If false (default), converts all 'system' role messages to 'assistant' for GitHub Copilot compatibility. Set to true to disable this behavior." The chat transformation returns messages unchanged when it is true, with the comment "GitHub Copilot API now supports system prompts for all models (Claude, GPT, etc.)". — [litellm 1.110.2 files (`litellm/__init__.py`, `litellm/llms/github_copilot/chat/transformation.py`)](https://pypi.org/project/litellm/1.110.2/#files); [litellm 1.106.2 files](https://pypi.org/project/litellm/1.106.2/#files)
- Chat requests add `X-Initiator`: `agent` if any message has the role `tool` or `assistant`, otherwise `user`; and `Copilot-Vision-Request: true` when a message carries an image. — [litellm 1.110.2 files (`litellm/llms/github_copilot/chat/transformation.py`)](https://pypi.org/project/litellm/1.110.2/#files)
- `GithubCopilotConfig` extends LiteLLM's `OpenAIConfig`; for Claude models that LiteLLM marks as reasoning-capable it adds `thinking` and `reasoning_effort` to the supported parameters. — [litellm 1.110.2 files (`litellm/llms/github_copilot/chat/transformation.py`)](https://pypi.org/project/litellm/1.110.2/#files)

**1.106.2, 1.108.13, 1.109.1 and 1.109.3 only**
- The GitHub token is exchanged at `https://api.github.com/copilot_internal/v2/token` (override `GITHUB_COPILOT_API_KEY_URL`) for a short-lived Copilot API key, cached in `api-key.json` (override `GITHUB_COPILOT_API_KEY_FILE`) and refreshed when its `expires_at` has passed. `GetAPIKeyError` is defined in `common_utils.py` and `Authenticator.api_key_file` exists. — [litellm 1.106.2 files (`litellm/llms/github_copilot/authenticator.py`, `common_utils.py`)](https://pypi.org/project/litellm/1.106.2/#files); [litellm 1.109.1 files](https://pypi.org/project/litellm/1.109.1/#files)

**1.110.0 and 1.110.2 (identical provider directory)**
- `Authenticator.get_api_key()` is now "Return the stored GitHub access token, loading it with device flow when needed": the GitHub token itself is sent as the bearer. `api_key_file`, `_refresh_api_key`, `GetAPIKeyError`, `GITHUB_COPILOT_API_KEY_URL` and `GITHUB_COPILOT_API_KEY_FILE` do not occur anywhere in the package. — [litellm 1.110.0 files (`litellm/llms/github_copilot/authenticator.py`, `common_utils.py`)](https://pypi.org/project/litellm/1.110.0/#files); [litellm 1.110.2 files](https://pypi.org/project/litellm/1.110.2/#files)
- The API base is discovered by a GET to `https://api.github.com/copilot_internal/user` (`endpoints.api`), validated against github.com's Copilot hosts and cached in memory; the order is the call's `api_base`, that discovered value, `GITHUB_COPILOT_API_BASE`, then `https://api.githubcopilot.com`. — [litellm 1.110.2 files (`litellm/llms/github_copilot/authenticator.py`, `chat/transformation.py`)](https://pypi.org/project/litellm/1.110.2/#files)
- A `github_host.py` module accepts only `github.com` or a single-subdomain `*.ghe.com` host and derives `https://SUBDOMAIN.ghe.com/login/device/code`, `https://api.SUBDOMAIN.ghe.com/...` and `https://copilot-api.SUBDOMAIN.ghe.com`. LiteLLM's docs say GitHub Enterprise Server is rejected. — [litellm 1.110.2 files (`litellm/llms/github_copilot/github_host.py`)](https://pypi.org/project/litellm/1.110.2/#files); [LiteLLM docs, GitHub Copilot](https://docs.litellm.ai/docs/providers/github_copilot)
- LiteLLM's published provider page still lists `GITHUB_COPILOT_API_KEY_FILE` and `GITHUB_COPILOT_API_KEY_URL` and describes the `api-key.json` exchange for the SDK. That matches 1.109.x and earlier, not the 1.110.2 source. — [LiteLLM docs, GitHub Copilot](https://docs.litellm.ai/docs/providers/github_copilot); [litellm 1.110.2 files](https://pypi.org/project/litellm/1.110.2/#files)

**The owner's working code**
- `adk_review`'s login imports `GetAPIKeyError` from `litellm.llms.github_copilot.common_utils`, unlinks `auth.api_key_file`, calls the private `auth._get_device_code()` and `auth._get_github_headers()`, polls for GitHub's own `expires_in` (default 900 seconds) honoring `slow_down`, sets `os.umask(0o077)`, and chmods the token and key to `0o600` and the folder to `0o700`. Its `judge/config.py` reads `endpoints.api` from `api-key.json`. — `/Users/emrec/Projects/playground/adk_review/adk_review/login.py`, `/Users/emrec/Projects/playground/adk_review/adk_review/judge/config.py`

### Inferences
- Porting `adk_review`'s login and configuration to LiteLLM 1.110.0 or later unchanged would fail at import (`GetAPIKeyError`) and at attribute access (`api_key_file`), and its report of where calls go would read a file that no longer exists. The owner's documents pin 1.110.2 and describe the 1.106.2 mechanics side by side; one of the two has to change.
- The login tool depends on LiteLLM private names. Each LiteLLM upgrade needs a test that imports exactly what the login uses; the 1.110.0 change shows these names move between adjacent minor releases.
- The 60-second window is real and too short for a person who has to open a browser, and on every version read a first call made inside ADK's running event loop with no cached token does not prompt at all, it fails with an authentication error. A separate, blocking login command before the first run is required, which is what the owner already planned.
- `disable_copilot_system_to_assistant` changes behavior only for Copilot models served on chat completions (Claude, Gemini, Grok, Kimi in LiteLLM's map). For Copilot's GPT models, all Responses-only in that map, the instruction travels as `instructions` whatever the flag says. Setting the flag is still right, since it is the only thing protecting the chat-completions models.
- Pinning the bundled model map (`LITELLM_LOCAL_MODEL_COST_MAP=True`) trades freshness for reproducibility: LiteLLM 1.106.2's bundled map has no `gpt-6.1-terra` and nothing newer, so those models would be unknown to it until registered by hand.
- On Windows the POSIX permission steps do nothing useful; the token file is protected only by the user profile's own access control. The plan's `0o600` and `0o700` claims hold on POSIX only, as the owner's document already limits them.
- For a GitHub Enterprise Cloud tenant with data residency, the three endpoint variables plus `GITHUB_COPILOT_API_BASE` cover 1.110.2; `GITHUB_COPILOT_API_KEY_URL` is needed only on 1.109.x and earlier, and setting it on 1.110.2 has no effect.

### Gaps
- Whether Copilot's API accepts the raw GitHub OAuth token as bearer (the 1.110 design) was not confirmed by a call, only read from source.
- LiteLLM's release notes for 1.110.0 were not read, so the stated reason for dropping the API-key exchange is unknown.
- How long the GitHub OAuth token lasts and when a re-login is forced is not stated in LiteLLM's source or docs.

## What works through ADK's `LiteLlm` wrapper on a Copilot model

### Takeaway
Function calling, output schemas, system instructions, streaming and per-request timeouts all have code paths in ADK's `LiteLlm` wrapper that apply to Copilot models, and `adk_review` runs tool calls and schema-bound answers on Copilot in practice; the differences from Gemini are in how output schema plus tools is achieved, in sampling parameters that reasoning models reject, and in Gemini-only features. `_skip_mcp_handler` is a private LiteLLM `completion()` argument, not an ADK one, and it only mattered on LiteLLM 1.106.x.

### Cited Findings
- `LiteLlm.__init__(self, model, **kwargs)` stores every extra keyword in `_additional_args` and adds them to each `litellm.acompletion` call; `drop_params` is handled the same way. `messages`, `tools`, `stream` and `llm_client` are removed. — [google-adk 2.15.0 files (`google/adk/models/lite_llm.py`)](https://pypi.org/project/google-adk/2.15.0/#files)
- `_skip_mcp_handler` does not occur anywhere in `google-adk` 2.15.0. In LiteLLM it is read in `completion()`: `skip_mcp_handler: Final = kwargs.pop("_skip_mcp_handler", False)`. — [google-adk 2.15.0 files](https://pypi.org/project/google-adk/2.15.0/#files); [litellm 1.110.2 files (`litellm/main.py`)](https://pypi.org/project/litellm/1.110.2/#files)
- In LiteLLM 1.106.2 the guard is `if not skip_mcp_handler and tools:` followed by imports from `litellm.responses.mcp`, so every call that carried tools entered the MCP gateway code. In 1.108.13, 1.109.1, 1.109.3, 1.110.0 and 1.110.2 the guard is `if not skip_mcp_handler and tools and may_name_litellm_mcp_gateway(tools):`, so ordinary function tools no longer reach it. — [litellm 1.106.2 files (`litellm/main.py`)](https://pypi.org/project/litellm/1.106.2/#files); [litellm 1.110.0 files (`litellm/main.py`, `litellm/responses/mcp/tool_precheck.py`)](https://pypi.org/project/litellm/1.110.0/#files)
- `litellm.supports_response_schema` has no provider-wide default for `github_copilot`; it reads the model's map entry and returns false for a model the map does not list. — [litellm 1.110.0 files (`litellm/utils.py`)](https://pypi.org/project/litellm/1.110.0/#files)
- `adk_review` records that from LiteLLM 1.106.0 "a call carrying a tool imported it, and it needs `mcp`, a package of LiteLLM's proxy, so chat's intake failed before any call", and passes `_skip_mcp_handler=True`. — `/Users/emrec/Projects/playground/adk_review/adk_review/judge/config.py`
- System instruction: ADK inserts one `role: system` message at the head of the list from the request's system instruction. LiteLLM then rewrites it to `assistant` for Copilot unless `litellm.disable_copilot_system_to_assistant` is true. — [google-adk 2.15.0 files (`google/adk/models/lite_llm.py`)](https://pypi.org/project/google-adk/2.15.0/#files); [litellm 1.110.2 files (`litellm/llms/github_copilot/chat/transformation.py`)](https://pypi.org/project/litellm/1.110.2/#files)
- Tools: ADK converts each function declaration to an OpenAI tool parameter; tool descriptions are capped by a constant `_MAX_TOOL_DESCRIPTION_LENGTH = 1024`. `FunctionCallingConfigMode.ANY` becomes `tool_choice="required"` and `NONE` becomes `"none"`. Built-in tools without function declarations (for example `google_search`) are serialized and passed through as they are. — [google-adk 2.15.0 files (`google/adk/models/lite_llm.py`)](https://pypi.org/project/google-adk/2.15.0/#files)
- Tool-call arguments that are not valid JSON are repaired where possible; a streamed batch with any unparsable call is dropped whole and returned as `MAX_TOKENS` or `MALFORMED_FUNCTION_CALL`. Several tool calls in one response are collected by index. — [google-adk 2.15.0 files (`google/adk/models/lite_llm.py`)](https://pypi.org/project/google-adk/2.15.0/#files)
- Output schema without tools: ADK sends `response_format = {"type": "json_schema", "json_schema": {"name": ..., "strict": True, "schema": ...}}` for every non-Gemini LiteLLM model, after forcing `additionalProperties: false` and listing every property as required. — [google-adk 2.15.0 files (`google/adk/models/lite_llm.py`, `google/adk/utils/_schema_utils.py`)](https://pypi.org/project/google-adk/2.15.0/#files)
- Output schema with tools depends on `model.capabilities.output_schema_and_tools`. For `LiteLlm` it is false for any model whose name contains "claude" or is a Gemini name (outside `vertex_ai`), and otherwise follows `litellm.supports_response_schema`. When false, ADK does not send a response schema; it adds a `set_model_response` tool and an instruction to finish by calling it. — [google-adk 2.15.0 files (`google/adk/models/lite_llm.py`, `google/adk/flows/llm_flows/basic.py`, `google/adk/flows/llm_flows/prompt/_schema.py`)](https://pypi.org/project/google-adk/2.15.0/#files)

### Inferences
- On a Copilot Claude model an agent with tools and an output schema gets its structured answer through the `set_model_response` tool, the same mechanism as Gemini with an AI Studio key; on a Copilot GPT model ADK sends tools and a strict JSON schema together. One prompt and schema therefore runs through two different mechanisms depending on the model family, and both must be tested.
- The strict-schema transform makes every field required. Optional fields in a Pydantic output model must be expressed as nullable rather than omitted, or the two arms will disagree about what a valid answer is.
- With `BuiltInPlanner` on a Copilot Claude model, ADK turns thinking on and silently drops a temperature of 0. On a Copilot GPT reasoning model, LiteLLM refuses any temperature other than 1 unless `drop_params=True` is passed to `LiteLlm`. A framework that wants deterministic settings has to choose per model, and should validate offline the way `adk_review` does.
- The statement that `BuiltInPlanner` "errors on non-thinking models" does not describe the `LiteLlm` path: there the config is ignored for models LiteLLM does not mark as reasoning-capable, and translated for those it does. Gating the planner to Gemini is safe but gives up reasoning control on Copilot.
- `_skip_mcp_handler=True` is needed on LiteLLM 1.106.x and harmless later. It is an underscore-prefixed LiteLLM internal, so it can disappear or change meaning.
- Gemini-only in practice: built-in tools (`google_search`, code execution), explicit context caches, the Interactions API and service tiers, and the Live API. Built-in tools are passed through `LiteLlm` untranslated and a Copilot endpoint has no reason to accept them.

### Gaps
- Whether Copilot returns usage, cached-token counts and reasoning-token counts in the shapes ADK reads was not observed; the mapping exists, the data may not.
- Whether Copilot accepts video, audio or file blocks is unknown; only the image path has a Copilot-specific header in LiteLLM.
- Whether Copilot's chat-completions endpoint honours `response_format: json_schema` with `strict` for Claude and Gemini models, `stream_options`, `cache_control` markers, or `parallel_tool_calls` is not documented by GitHub and was not tested. `adk_review` is evidence only for `gpt-4.1`, a retired model.
- No evidence was found, in source or in `adk_review`, of an output schema combined with tools having been exercised on a Copilot model.

## The LiteLLM range `google-adk` declares, why, and the supply-chain incidents

### Takeaway
The `<1.106.3` cap is real, sits only in optional extras, and exists because LiteLLM 1.107.0, published 2026-10-21, was a credential-stealing release; an earlier incident on 2026-03-24 hit 1.82.7 and 1.82.8. LiteLLM itself tells users to pin 1.106.2 or earlier and has not, in the page read, declared later releases verified.

### Cited Findings
- `litellm>=1.84,<1.106.3` appears in the extras `all`, `extensions` and `test` of `google-adk` 2.15.0 and 2.14.1, and nowhere in the required dependencies. — [google-adk 2.15.0 files (METADATA)](https://pypi.org/project/google-adk/2.15.0/#files); [google-adk 2.14.1 files (METADATA)](https://pypi.org/project/google-adk/2.14.1/#files)
- The reason given in ADK's `pyproject.toml`: "1.107.0 was a compromised release; raise only after checking the new release is clean." — [google-adk 2.15.0 files (sdist pyproject.toml)](https://pypi.org/project/google-adk/2.15.0/#files)
- LiteLLM's incident page: `litellm==1.107.0`, "all seven wheels, live from 11:39:51 to 13:23 UTC" on 2026-10-21; Docker Hub tags `v1.107.0`, `latest`, `main-latest`, `main-stable` from 11:46:56 to 14:20 UTC. "This version contained compiled malware which steals credentials and loads remote-code execution tools." Indicators: `cook.pth`, `cook.py`, `sitecustomize.py`. — [LiteLLM, security incident Oct 21 2026](https://docs.litellm.ai/blog/security-incident-oct-21-2026)
- The same page says "All previous versions are safe", advises pinning to "1.106.2 or any explicit version published prior to now", and reports that the release workflow was run against a lookalike repository using exposed developer credentials. It does not state that 1.106.3 or later releases are verified clean; it says 1.106.3 was among the first releases signed with a rotated cosign key on 2026-10-24, and that keyless signing starts with `v1.111.0-dev.3` on 2026-11-15. — [LiteLLM, security incident Oct 21 2026](https://docs.litellm.ai/blog/security-incident-oct-21-2026)
- March incident: "The compromised PyPI packages were litellm==1.82.7 and litellm==1.82.8", live "on March 24, 2026 from 10:39 UTC for about 40 minutes before being quarantined by PyPI"; a credential stealer; attributed to "the Trivy dependency used in our CI/CD security scanning workflow". v1.83.0 was announced as the clean release, and releases v1.78.0 to v1.82.6 were audited as clean. — [LiteLLM, security update March 2026](https://docs.litellm.ai/blog/security-update-march-2026)

### Inferences
- Installing a newer LiteLLM beside ADK is mechanically possible without extras, but it leaves the range ADK tests, and it steps past a cap that Google set for a security reason and has not lifted in 2.15.0, published a month after the incident.

## Fallback, multi-model and per-agent model selection in ADK

### Takeaway
`FallbackModel` exists in both 2.14.1 and 2.15.0, is marked experimental, tries each model once, and falls back only on HTTP 429, 500, 502, 503 and 504 by default; timeouts (408) are deliberately excluded. Every `LlmAgent` takes its own `model`, as a string or a `BaseLlm` instance, so a provider-neutral factory that returns one or the other is the supported pattern and is what `adk_review` does.

### Cited Findings
- `FallbackModel(models=[...])` is importable from `google.adk.models` (lazily); entries are model names or `BaseLlm` instances; it is decorated `@experimental(FeatureName.FALLBACK_MODEL)` and registered as `FeatureStage.EXPERIMENTAL, default_on=True` ("Feature works but API may change"). — [google-adk 2.15.0 files (`google/adk/models/_fallback_model.py`, `google/adk/features/_feature_registry.py`)](https://pypi.org/project/google-adk/2.15.0/#files)
- `_fallback_model.py`, `models/__init__.py`, `registry.py`, `base_llm.py` and `_capabilities.py` are byte-identical between 2.14.1 and 2.15.0. — [google-adk 2.14.1 files](https://pypi.org/project/google-adk/2.14.1/#files); [google-adk 2.15.0 files](https://pypi.org/project/google-adk/2.15.0/#files)
- `DEFAULT_STATUS_CODES` is 429, 500, 502, 503, 504. The docstring explains 408 is left out because "408 does not say whether the request was processed before the clock ran out, and litellm reports even a client-side timeout as 408, so failing over on it risks paying for and acting on one prompt twice. Add it back for a provider whose 408 is known to mean the request was dropped." `retriable_status_codes` is a field. — [google-adk 2.15.0 files (`google/adk/models/_fallback_model.py`)](https://pypi.org/project/google-adk/2.15.0/#files)
- "Each model is tried exactly once. Retrying a single model is a separate concern, handled by that model's own retry configuration". "Once a model has yielded its first response the turn belongs to it: a later failure propagates rather than falling back". — [google-adk 2.15.0 files (`google/adk/models/_fallback_model.py`)](https://pypi.org/project/google-adk/2.15.0/#files)
- LiteLLM's `APIConnectionError` and `APIResponseValidationError` carry a hard-coded status 500 that ADK ignores, so a refused connection or DNS failure does not trigger a fallback. — [google-adk 2.15.0 files (`google/adk/models/_fallback_model.py`)](https://pypi.org/project/google-adk/2.15.0/#files)
- `FallbackModel.capabilities` returns the primary model's capabilities: "A backup that reports different capabilities does not change what the request was built for". Before each attempt the request is snapshotted and restored, and `llm_request.model` is pointed at the delegate. — [google-adk 2.15.0 files (`google/adk/models/_fallback_model.py`)](https://pypi.org/project/google-adk/2.15.0/#files)
- String entries are resolved through `LLMRegistry.new_llm`, so a string works for Gemini names but not for `github_copilot/...`. — [google-adk 2.15.0 files (`google/adk/models/_fallback_model.py`, `google/adk/models/__init__.py`)](https://pypi.org/project/google-adk/2.15.0/#files)
- ADK's public docs describe "Model routing" with `RoutedLlm` and a router function, marked experimental, with a TypeScript example only; the page does not mention `FallbackModel`. — [ADK docs, model routing](https://adk.dev/agents/models/routing/)
- `adk_review`'s factory returns a plain string on the Gemini arm and a `LiteLlm` subclass on the Copilot arm, wraps two of them in `FallbackModel(models=..., retriable_status_codes=FallbackModel.DEFAULT_STATUS_CODES | {408})`, raises its own `CallTimeoutError` with `status_code = 408` from an overall `asyncio.timeout`, skips a fallback equal to the primary, and resolves the model per role from `REVIEW_<ROLE>_MODEL`, a per-guideline preset, `REVIEW_MODEL`, then the arm's default. — `/Users/emrec/Projects/playground/adk_review/adk_review/judge/config.py`, `/Users/emrec/Projects/playground/adk_review/adk_review/judge/settings.py`

### Inferences
- The owner's phrase "429/5xx/timeout failover on either arm" is true only with the two additions `adk_review` makes: 408 added to `retriable_status_codes` and a deadline that raises an error carrying 408. The code skeleton in the architecture report builds `FallbackModel(models=models)` without them, so as written it would not fall back on a timeout.
- Nothing stops a `FallbackModel` from mixing providers, a Copilot primary with a Gemini backup, but the request is built for the primary's capabilities. If the two differ on output schema with tools, the backup receives a request shaped for the other mechanism. Keeping both entries on one arm and one model family, as `adk_review` does, avoids this.
- Recommended factory shape, following `adk_review` and the ADK source: one settings module that reads the provider and per-role model names and imports nothing heavy; one factory module that alone imports `google.adk.models` and `litellm`, returns `str | BaseLlm`, applies the LiteLLM flags once, and validates readiness offline before any call (token present, model name resolves to the intended class, sampling parameters accepted).
- Streaming weakens fallback: once the first chunk is out, a failure propagates. Agents whose output is consumed only when complete can run non-streamed to keep fallback effective.

### Gaps
- No Python documentation for `FallbackModel` exists on adk.dev; the source docstring is the only specification, and the feature is experimental.
- How `FallbackModel` behaves when the primary is a Copilot model and LiteLLM itself has retried was not traced beyond `adk_review`'s measurement.

- A Gemini default of `gemini-2.5-flash` will silently become a different, smaller model on 2026-12-01. New defaults should be `gemini-3.8-flash` for cost and `gemini-4-hydrogen` for general work, with the name in configuration.
- On Gemini 4, `ContextCacheConfig` does nothing, so the "static instruction for prefix caching" argument in the owner's documents applies to Gemini 2.5 and 3 only, and on 2.14.1 the cache manager has no Gemini 4 handling at all. Implicit caching by the provider may still reward a stable prefix, but that is outside ADK.
- Because output schema with tools is native only on the Cloud backend, the AI Studio arm and a Copilot Claude model share the `set_model_response` path, while the Cloud arm and Copilot GPT models share the native path. The parity matrix is by mechanism, not by provider.
- The owner's skeleton attaches `BuiltInPlanner(thinking_config=types.ThinkingConfig(thinking_budget=2048))` on the Gemini arm. Google's current page speaks only of thinking levels, and thinking cannot be switched off on Gemini 4 or `gemini-3.8-flash`. Reasoning control should be expressed as a level per role and mapped by the factory (to `thinking_level` on Gemini, to `reasoning_effort` on Copilot), and "thinking off for formatting steps" should not be assumed available.

### Gaps
- Google's guidance on temperature for Gemini 3 and later was not found on the pages read on 2026-11-21 (the model overview and the thinking page do not mention temperature). The owner's statement that Gemini 3 models may loop below temperature 1.0 is recorded in `adk_review` as Google's advice and is unconfirmed here.
- Whether a numeric `thinking_budget` is still accepted, mapped or rejected on Gemini 3.8 and Gemini 4 is not stated on the pages read.
- `gemini-3.5-flash`, named in ADK's source, does not appear in the list read from Google's model page; its status is unconfirmed.
- Per-model output limits and feature tables (thinking, structured output, caching) are on Google pages that were not read.

## Designing so prompts and tools behave the same on both providers

### Takeaway
The differences that matter are mechanical and known in advance: strict-schema rewriting, two ways of combining schema and tools, sampling parameters that reasoning models refuse, system-message handling on Copilot, context sizes from 128K to 1M, and different error and retry shapes. Each can be fenced by one factory, one offline readiness check and a two-arm test matrix.

### Cited Findings
- On the LiteLLM path ADK rewrites an output schema for OpenAI strict mode: `additionalProperties: false` on every object and every property listed as required; `$ref` nodes lose sibling keywords. 2.15.0 additionally inlines a root `$ref` for recursive models, which 2.14.1 did not. — [google-adk 2.15.0 files (`google/adk/utils/_schema_utils.py`)](https://pypi.org/project/google-adk/2.15.0/#files); [google-adk 2.14.1 files (`google/adk/models/lite_llm.py`)](https://pypi.org/project/google-adk/2.14.1/#files)
- ADK validates a schema-bound reply and `adk_review` found that an invalid or truncated reply raised and ended the whole workflow until a plugin turned it into that agent's own error. — `/Users/emrec/Projects/playground/adk_review/adk_review/judge/plugins.py`
- Tool descriptions are limited by `_MAX_TOOL_DESCRIPTION_LENGTH = 1024` on the LiteLLM path. — [google-adk 2.15.0 files (`google/adk/models/lite_llm.py`)](https://pypi.org/project/google-adk/2.15.0/#files)
- LiteLLM converts the system message to an assistant message for Copilot by default. — [litellm 1.110.2 files (`litellm/llms/github_copilot/chat/transformation.py`)](https://pypi.org/project/litellm/1.110.2/#files)
- Context limits differ by an order of magnitude: 128,000 input tokens for `github_copilot/claude-haiku-5.5` and `gpt-5.3-codex`, 200,000 for Copilot's Claude Sonnet and Opus, against 1M for Gemini 4. — [litellm 1.110.2 files (`litellm/model_prices_and_context_window_backup.json`)](https://pypi.org/project/litellm/1.110.2/#files); [Google, Gemini models](https://aistudio.google.com/docs/models)
- Copilot bills by tokens, and long-context tiers double the input price above 200K or 272K input tokens (above 100K for Claude Haiku 5.5, at five times the price). — [GitHub docs, models and pricing](https://docs.github.com/en/copilot/reference/copilot-billing/models-and-pricing)
- Error shapes differ: google-genai raises `APIError` with `code`; LiteLLM errors carry `status_code`, and two of them report 500 for failures that never reached the service. — [google-adk 2.15.0 files (`google/adk/models/_fallback_model.py`)](https://pypi.org/project/google-adk/2.15.0/#files)
- `adk_review` strips LiteLLM's wrapping from Copilot errors ("RateLimitError: 429: RateLimitError: Github_copilotException - Sorry, ...") to show the provider's own words, and stops sending calls after the first unrecoverable 429. — `/Users/emrec/Projects/playground/adk_review/adk_review/judge/config.py`, `/Users/emrec/Projects/playground/adk_review/adk_review/judge/plugins.py`
- `adk_review` filters bearer tokens out of LiteLLM log lines because "`adk web -v` ... printed the Copilot token whole", and sets `LITELLM_LOCAL_MODEL_COST_MAP=True` so LiteLLM uses the price map shipped with the pinned version. — `/Users/emrec/Projects/playground/adk_review/adk_review/judge/config.py`

### Inferences
- Write output models for the strictest arm: every field present, optional values as nullable types, no free-form dictionaries, no recursion unless 2.15.0 is the floor, short property names, enums rather than patterns. Validate with Pydantic after every call and treat a mismatch as that agent's recoverable error.
- Keep tool names to letters, digits and underscores, descriptions under 1024 characters, and parameters as flat JSON-schema objects with primitive types. Do not depend on built-in Gemini tools in shared agents.
- Decide sampling per model in the factory: no temperature for reasoning models (or `drop_params=True`), and expect Claude with thinking to lose a non-1 temperature. Do not promise determinism across arms.
- Set `litellm.disable_copilot_system_to_assistant = True` so instructions arrive as a system turn on both arms, and keep untrusted content fenced in the user turn.
- Budget context from the smallest model a role may run on. The owner's two-tier knowledge loader should take its threshold from the active model's limit, which for Copilot must come from LiteLLM's map or configuration, and fall back to a conservative default for models the map lacks.
- Agents that both call tools and return a schema should be written to tolerate the `set_model_response` mechanism: the final answer arrives as a tool call, so instructions must not forbid tool use at the end, and tool-choice forcing must not exclude that tool.
- Normalize errors in one place: map both providers to a small set (rate limited, quota spent, model not available, auth, timeout, schema mismatch, refusal or truncation) and decide retry, fallback or stop there. Add 408 to fallback only together with an overall deadline.
- Run the evaluation suite on at least four cells: Gemini with an AI Studio key, Gemini on Google Cloud, a Copilot GPT (Responses) model and a Copilot Claude model.

### Gaps
- Provider refusal behavior (content filters on Copilot, safety blocks on Gemini) and how each surfaces through ADK was not examined in source beyond finish-reason mapping.
- Copilot's content filter for "public code matching" may alter or block output for code-generation agents; its effect through this route is undocumented.
