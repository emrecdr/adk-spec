## 1. In the current default ("core") profile, which commands or skills does a person run for one change, in what order, which are required, and how many?

### Takeaway
Status: answered with sources. The minimum is three agent requests per change (`propose`, then `apply`, then `archive`), four with the optional `explore` first, plus a human review between `propose` and `apply` that is not a command. The core profile installs six skills; `update` and `sync` are on-demand extras, and `sync` is normally absorbed by `archive`. None of the requests has to be typed as a command: plain-language prompts trigger the same skills.

### Cited Findings
- The core set is fixed in code: `CORE_WORKFLOWS = ['propose', 'explore', 'apply', 'update', 'sync', 'archive']`, with the comment "These provide the streamlined experience for new users." All twelve workflows: `propose, explore, new, continue, apply, update, ff, sync, archive, bulk-archive, verify, onboard`. — [src/core/profiles.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/profiles.ts)
- "The `core` profile installs six workflows, covering the whole loop from idea to archive"; "Six more workflows are available beyond the core set. Three of them (`new`, `continue`, `ff`) create a change proposal artifact by artifact, instead of all at once like `propose`." Any selection that is not exactly the core six is saved as `custom`. — [docs-lab/customize/profiles.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/customize/profiles.md)
- Skill names in 2.x: `openspec-explore`, `openspec-propose`, `openspec-apply-change`, `openspec-update-change`, `openspec-sync-specs`, `openspec-archive-change` (core); `openspec-new-change`, `openspec-continue-change`, `openspec-ff-change`, `openspec-verify-change`, `openspec-bulk-archive-change`, `openspec-onboard` (optional). — [docs-lab/reference/skills.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/skills.md)
- The quickstart teaches one loop: "Every change moves through the same five steps: you think the idea through with your agent, it drafts a plan, you correct the plan before any code exists, the agent builds from it, and archiving updates your specs with what shipped." The five boxes are Explore, Propose, Review, Apply, Archive. Review is a human step with no skill of its own. — [docs-lab/start/quickstart.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/start/quickstart.md); same content live at [openspec.dev/docs/quickstart](https://openspec.dev/docs/quickstart)
- Explore is skippable: "Starting cold, when the change is clear in your head, ask directly." The README says the same: "Not sure what to build yet? Start with `/openspec-explore`"; "Already know what you want? Go straight to `/openspec-propose <what-you-want-to-build>`." — [docs-lab/start/quickstart.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/start/quickstart.md); [README.md](https://github.com/Fission-AI/OpenSpec/blob/main/README.md)
- Legacy FAQ, "What's the simplest possible flow?": "`/opsx:explore (optional)   then   /opsx:propose <what you want>   then   /opsx:apply   then   /opsx:archive`". — [docs/faq.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/faq.md) (legacy)
- No typed command is needed: "Every prompt below goes in your AI chat, the same place you ask for code. The examples use plain language so they work across tools. You can also invoke a skill directly; the syntax varies by tool". Quickstart prompts are sentences such as "Propose a change to add rate limiting." and "Apply the add-rate-limiting change." — [docs-lab/start/quickstart.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/start/quickstart.md)
- Typed spelling varies by tool: `/openspec-propose` in Claude Code and most tools, `$openspec-propose` in Codex. — [docs-lab/start/setup.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/start/setup.md)
- `sync` is optional in the loop: "Do I need to run `/opsx:sync`? Usually not. Sync merges a change's delta specs into your main specs, and `/opsx:archive` will offer to do it for you." — [docs/faq.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/faq.md) (legacy). The archive skill confirms it: it "first syncs outstanding delta specs" with approval and "When `openspec-sync-specs` is installed, it runs that workflow. Otherwise, it merges the delta specs into the main specs itself." — [docs-lab/reference/skills.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/skills.md)
- `sync` is nevertheless forced into any profile that has archive: for a custom profile containing `archive` or `bulk-archive` without `sync`, the code inserts `sync`. — [src/core/profiles.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/profiles.ts)
- `update` is for revisions only: "Revise a change proposal's existing planning artifacts and keep them coherent with each other"; it "writes it only after you confirm, one artifact at a time." — [docs-lab/reference/skills.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/skills.md)
- A fresh session before apply is recommended, which adds a non-OpenSpec action to the loop: "Start a fresh chat session, since implementation goes better on a clean context window." — [docs-lab/start/quickstart.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/start/quickstart.md)
- One-time terminal setup is a single command, `openspec init`; its summary ends with the next step: "Getting started: Start your first change: /openspec-propose \"your idea\"". — [docs-lab/reference/cli.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md)
- Conflict between marketing and the default install: the homepage workflow lists five skills in order, `/openspec-explore`, `/openspec-propose`, `/openspec-apply-change`, `/openspec-verify-change`, `/openspec-archive-change`, although `verify` is not in the core profile. — [openspec.dev](https://openspec.dev/) (vendor page); contradicted by [docs-lab/customize/profiles.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/customize/profiles.md)
- Conflict inside the legacy docs: the workflows page draws the typical core flow as "/opsx:explore ──► /opsx:propose ──► /opsx:apply ──► /opsx:sync ──► /opsx:archive", with sync as a step, while the FAQ says sync is usually not needed. — [docs/workflows.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/workflows.md) (legacy); [docs/faq.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/faq.md) (legacy)
- Independent users report the same count. A first-hand walkthrough on a real project ran explore, propose, apply, archive. Another lists `/opsx-propose`, review and edit, `/new`, `/opsx-apply`, `/new`, `/opsx-archive` (three OpenSpec commands plus two context resets; the fetch tool's own total of "6 invocations" does not match the sequence it listed). A third lists propose, apply, archive. — [dev.to/mousius](https://dev.to/mousius/spec-driven-development-with-openspec-1fmb); [martinlwx.github.io](https://martinlwx.github.io/en/when-opencode-meet-openspec-sdd-in-practice/); [recca0120.github.io](https://recca0120.github.io/en/2026/03/08/openspec-sdd)

### Inferences
- Counted honestly, one change costs a person three required requests (propose, apply, archive), one optional request (explore), one unnamed human step (review), and usually one session reset. The "six core skills" figure overstates daily use: `update` and `sync` are corrective tools, not steps.
- The project presents three different counts in three places: five steps (quickstart, with review as a step), five skills including verify (homepage), six skills (profile). A tool that wants to look simple should publish one number.
- Because skills are matched on their description, the user-facing surface is closer to "three verbs said in chat" than to "six commands". The command names matter mostly as a fallback and as documentation anchors.

### Gaps
- No usage data shows how often people actually run `explore`, `update` or `sync` per change. Telemetry exists (command names and version) but no figures are published in the sources read.

## 2. What does `propose` create in one pass, where is a human expected to review or edit, how do `new-change`, `continue-change` and `ff-change` differ, and why are they optional?

### Takeaway
Status: answered with sources. `propose` creates the change folder and every planning artifact in one run (proposal, delta specs, design when warranted, tasks), asks questions only about material ambiguity, then stops and requires a new user request before any code. The one expected human review sits between `propose` and `apply`; it is conversational and not recorded. `new` (scaffold only), `continue` (one artifact per run) and `ff` (all artifacts, no clarification step) are the older stepwise path; they were demoted to optional in v1.2.0 because the project judged the split "unnecessary steps" for most users.

### Cited Findings
- Contract: `openspec-propose` creates "`openspec/changes/<name>/` with every artifact the schema defines, in dependency order (spec-driven: proposal, spec deltas, design, tasks). Never code." Response: "The created artifacts, ready for review, and the next step. Stops there; implementation waits for `openspec-apply-change`." — [docs-lab/reference/skills.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/skills.md)
- The folder a person sees after propose: `proposal.md` ("why, and what changes"), `specs/` ("what \"done\" means, as testable requirements"), `design.md` ("technical decisions (only when the change needs one)"), `tasks.md` ("the implementation checklist"). "No code yet. Propose stops at the plan." — [docs-lab/start/quickstart.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/start/quickstart.md)
- Inside one propose run the agent makes many CLI calls the user never types: `openspec list --json` (project check), `openspec context --json`, `openspec new change "<name>"`, `openspec status --change "<name>" --json`, then per artifact `openspec instructions <artifact-id> --change "<name>" --json` followed by a status re-check, and a final `openspec status --change "<name>"`. — [skills/openspec-propose/SKILL.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-propose/SKILL.md)
- Questions before writing are limited: "If the request contains ambiguity that would materially affect scope, externally observable behavior, compatibility, or acceptance criteria, ask the user before creating the change. For minor details, make a reasonable assumption and record it in the planning artifacts." — [skills/openspec-propose/SKILL.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-propose/SKILL.md)
- The hard stop is prompt text: "This workflow creates planning artifacts only. The user request that selected or triggered this workflow authorizes planning only, even if it asks to build or fix something... Do not start implementation in the same response, even if the initial request asks for it. Wait for a new user request after the artifacts are presented". Closing line to the user: "The plan is ready for review. When you're ready, ask me to apply it." — [skills/openspec-propose/SKILL.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-propose/SKILL.md)
- Review guidance (quickstart step 3): read `proposal.md` ("is this the right problem, at the right size?"), then `specs/` ("the highest-value read. Would you accept these requirements as done?"), then `tasks.md` ("do the tasks cover the specs, and nothing more?"). To fix: "Edit the file yourself. The artifacts are plain markdown, and the files are the plan." or "Tell your agent what's wrong". `design.md` is not in the reading list. — [docs-lab/start/quickstart.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/start/quickstart.md)
- Later human touch points: apply "Unclear tasks or errors: pauses and asks"; archive "Warns and asks before archiving with incomplete artifacts or tasks, and asks whether to sync when delta specs exist"; update "writes it only after you confirm". — [docs-lab/reference/skills.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/skills.md)
- Manual edits are picked up because the skills re-read files: "always re-read them from disk, even if you saw them earlier in the conversation (the user may have edited them)". — [skills/openspec-propose/SKILL.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-propose/SKILL.md)
- The review gate leaves no trace on disk; status cannot tell "drafted" from "approved". — earlier internals notes, citing [skills/openspec-propose/SKILL.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-propose/SKILL.md)
- `openspec-new-change`: runs `openspec new change`, shows status and the first artifact's template, then "STOP and wait for user direction"; guardrail "Do NOT create any artifacts yet - just show the instructions". Its description still calls itself "the experimental artifact workflow". — [skills/openspec-new-change/SKILL.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-new-change/SKILL.md)
- `openspec-continue-change`: "Pick the FIRST artifact with `status: \"ready\"`", write it, "STOP after creating ONE artifact"; guardrail "Create ONE artifact per invocation". — [skills/openspec-continue-change/SKILL.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-continue-change/SKILL.md)
- `openspec-ff-change` runs the same artifact loop as propose. A line-by-line comparison of the two skill files shows propose adds four things ff lacks: the planning-boundary block, the "clarify material ambiguity" step, the "Load project context" step (`openspec context --json` plus reading `config.yaml` `context`), and the schema-selection step. ff's stance is "If context is critically unclear, ask the user - but prefer making reasonable decisions to keep momentum". — [skills/openspec-ff-change/SKILL.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-ff-change/SKILL.md); [skills/openspec-propose/SKILL.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-propose/SKILL.md)
- Invocation counts for the default schema follow from those contracts: propose is one request; `new` plus `continue` is one request plus one per artifact (four artifacts, three if design is skipped); `new` plus `ff` is two. — [docs-lab/reference/skills.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/skills.md)
- Why propose exists, in the project's own design document: "Propose Workflow = New + FF Combined. Single workflow that creates a change and generates all artifacts in one step. **Rationale:** Most users want to go from idea to implementation-ready. Separating `new` (creates folder) and `ff` (generates artifacts) adds unnecessary steps. Power users who want control can use `new` + `continue` via custom profile." — [openspec/changes/simplify-skill-installation/design.md](https://github.com/Fission-AI/OpenSpec/blob/main/openspec/changes/simplify-skill-installation/design.md)
- Why the stepwise skills were kept at all: listed non-goal "Removing any existing workflows (all remain available via custom profile)". The lead maintainer on the value of stepping: "giving users who care about reliability a way to step through file creations instead of creating them all at once." — [openspec/changes/simplify-skill-installation/design.md](https://github.com/Fission-AI/OpenSpec/blob/main/openspec/changes/simplify-skill-installation/design.md); [Discussion #111](https://github.com/Fission-AI/OpenSpec/discussions/111) (reply dated 20 January 2026)
- When to pick which (legacy guide): "If you can describe the full scope upfront, use `/opsx:ff`. If you're figuring it out as you go, use `/opsx:continue`." — [docs/workflows.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/workflows.md) (legacy)
- The docs team records the two-path explanation as unowned: the row "How do we explain the standard flow (propose drafts every artifact in one step) vs the iterative flow (new creates the change, continue drafts the next artifact, fast-forward catches up)?" has status "Gap". — [docs-lab/message-map.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/message-map.md)
- A known failure of the one-pass design: until a 1.7-series fix, "`/opsx:propose` and `/opsx:ff` no longer finish a change with no spec written" because "`status` marks an artifact `done` as soon as a matching file exists, so writing `tasks.md` early satisfied the loop". — [CHANGELOG.md](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)

### Inferences
- `propose` and `ff` are near-duplicates; `ff` survives mainly for people on the stepwise path who want to "catch up". A new tool can drop one of them without losing a capability.
- Three "pacing" skills (`new`, `continue`, `ff`) exist to solve one need, reviewing artifacts one at a time. The same need could be met by an option on a single plan command (for example "pause after each artifact") instead of three extra commands.
- The single review point works only because propose is forbidden to implement. That boundary is the load-bearing rule of the flow, and it is enforced by prompt text alone.

### Gaps
- `openspec-update-change`, `openspec-sync-specs` and `openspec-bulk-archive-change` were not re-read line by line in this round; their contracts come from the skills reference.
- No measurement of how long one propose run takes or how many tokens it uses was found.

## 3. How did the flow change from the pre-1.0 commands to the 1.0 "OPSX" system and to 2.x, and what reasons did the project give?

### Takeaway
Status: answered with sources. The surface went 3 commands (pre-1.0), then 10 (1.0, January 2026), then a default of 4 with the rest optional (1.2.0, February 2026, after complaints of "too many skills"), then crept back to 5 (1.4.0, sync) and 6 (1.6.0, update); 2.0 (November 2026) kept the six but deleted the duplicate command files and renamed everything to skills. The stated reasons are, in order: rigidity of the linear flow, new-user overwhelm, requested missing actions, and maintenance cost of duplicated files.

### Cited Findings
- Pre-1.0 flow as documented then: (1) "Draft the Proposal" with `/openspec:proposal`, which "Scaffolds openspec/changes/add-profile-filters/ with proposal.md, tasks.md, spec deltas"; (2) "Verify & Review" in the terminal with `openspec list`, `openspec validate add-profile-filters`, `openspec show add-profile-filters`; (3) "Refine the Specs" by chat; (4) "Implement the Change" with `/openspec:apply`; (5) "Archive the Completed Change" with `/openspec:archive`, where the AI "Runs: openspec archive add-profile-filters --yes". — [README_OLD.md](https://github.com/Fission-AI/OpenSpec/blob/main/README_OLD.md)
- Why OPSX replaced it (legacy page): "The legacy OpenSpec workflow works, but it's **locked down**: **Instructions are hardcoded** — buried in TypeScript, you can't change them; **All-or-nothing** — one big command creates everything, can't test individual pieces; **Fixed structure** — same workflow for everyone, no customization; **Black box** — when AI output is bad, you can't tweak the prompts". Also: "You're \"in planning phase\", then \"in implementation phase\", then \"done\". But real work doesn't work that way... Linear phases fight against how work actually happens." and "**The key insight:** work isn't linear. OPSX stops pretending it is." — [docs/opsx.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/opsx.md) (legacy)
- OPSX grew as experimental commands before 1.0: `/opsx:ff` in 0.18.0, `/opsx:explore` in 0.19.0 ("A new thinking partner mode"), `/opsx:verify` in 0.20.0, `/opsx:bulk-archive` in 0.23.0. — [CHANGELOG.md](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- v1.0.0 (published 26 January 2026): "OPSX replaces the old phase-locked `/openspec:*` commands with an action-based system"; "**Old commands removed** — `/openspec:proposal`, `/openspec:apply`, and `/openspec:archive` no longer exist"; "**Before:** Linear workflow — proposal → apply → archive. Couldn't easily go back or iterate. **Now:** Flexible actions on a change. Edit any artifact anytime." The 1.0 command table has ten entries: explore, new, continue, ff, apply, verify, sync, archive, bulk-archive, onboard. — [CHANGELOG.md](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md); date from [release v1.0.0](https://github.com/Fission-AI/OpenSpec/releases/tag/v1.0.0)
- 1.0 made the first step two commands. Legacy mapping: "`/openspec:proposal` → `/opsx:propose` (default) or `/opsx:new` then `/opsx:ff` (expanded)". A user in the roadmap thread (4 February 2026) said the new flow adds steps and asked "having to fill the proposal document: is it necessary?"; the lead maintainer answered on 20 February 2026: "You should get back the old workflow after this new change." — [docs/migration-guide.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/migration-guide.md) (legacy); [Discussion #111](https://github.com/Fission-AI/OpenSpec/discussions/111)
- v1.2.0 (published 23 February 2026), changelog: "**Profile system** — Choose between `core` (4 essential workflows) and `custom` (pick any subset)"; "**Propose workflow** — New one-step workflow creates a complete change proposal with design, specs, and tasks from a single request — no need to run `new` then `ff` separately". — [CHANGELOG.md](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md); date from [release v1.2.0](https://github.com/Fission-AI/OpenSpec/releases/tag/v1.2.0)
- The reason for 1.2.0, from the project's own change proposal: "Users have complained that there are too many skills/commands (currently 10) and new users feel overwhelmed. We want to simplify the default experience while preserving power-user capabilities and backwards compatibility. The goal: **get users to an \"aha moment\" in under a minute**." The timeline it sketches runs init at 0:00, `/opsx:propose` at 0:15, artifacts at 0:45, `/opsx:apply` at 1:00. — [openspec/changes/simplify-skill-installation/proposal.md](https://github.com/Fission-AI/OpenSpec/blob/main/openspec/changes/simplify-skill-installation/proposal.md)
- Same change, design document: "OpenSpec currently installs 10 workflows (skills + commands) for every user, overwhelming new users. The init flow asks multiple questions (profile, delivery, tools) creating friction before users can experience value." Core was "propose, explore, apply, archive (4)"; "**Rationale:** Core covers the essential loop". Alternative rejected: "Three tiers (core/extended/custom): Extended is redundant". Accepted trade-off: "Core profile has only 4 workflows → Acceptable: These cover the main loop." — [openspec/changes/simplify-skill-installation/design.md](https://github.com/Fission-AI/OpenSpec/blob/main/openspec/changes/simplify-skill-installation/design.md)
- The lead maintainer said the same to a confused user on 6 April 2026: "A lot of people complained that there were too many skills."; the team "decided to make the core skills the default" and users "can choose to install additional ones if they wish." — [Issue #898](https://github.com/Fission-AI/OpenSpec/issues/898)
- The proposal also wanted propose to teach as it runs: "This teaches as it goes - no separate onboarding needed for most users." — [openspec/changes/simplify-skill-installation/proposal.md](https://github.com/Fission-AI/OpenSpec/blob/main/openspec/changes/simplify-skill-installation/proposal.md)
- v1.4.0 (published 1 June 2026): "Include the sync workflow in the default core profile so new installs generate `/opsx:sync` skills and commands by default." Background: on the four-skill core, archive could offer "Sync now" although the sync skill was not installed (Issue #913, 3 April 2026, 9 reactions). — [CHANGELOG.md](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md); [release v1.4.0](https://github.com/Fission-AI/OpenSpec/releases/tag/v1.4.0); [Issue #913](https://github.com/Fission-AI/OpenSpec/issues/913) (title and counts only)
- v1.6.0 (published 10 July 2026) added `/opsx:update` and put it in core. Reason: "OPSX names **four** first-class actions — \"create, implement, **update**, archive — do any of them anytime\"... Three ship as commands. **`update` does not exist.** The only mechanism offered is *\"edit the files manually\"*... Worse, the manual workaround lets the agent edit **code** when the user only wanted to revise the **plan**"; "This is the most-requested missing capability in the tracker." It was added to core by "maintainer call on the PR". — [openspec/changes/archive/2026-10-19-add-update-workflow/proposal.md](https://github.com/Fission-AI/OpenSpec/blob/main/openspec/changes/archive/2026-10-19-add-update-workflow/proposal.md); date from [release v1.6.0](https://github.com/Fission-AI/OpenSpec/releases/tag/v1.6.0)
- The update skill was kept deliberately thin: "Per the steer to introduce as little code as possible, and only when there is a defined need, this change does **not** add: a reverse-dependency graph API, content digests / staleness signals... an `openspec reconcile` write op, a drift report". — [openspec/changes/archive/2026-10-19-add-update-workflow/proposal.md](https://github.com/Fission-AI/OpenSpec/blob/main/openspec/changes/archive/2026-10-19-add-update-workflow/proposal.md)
- The two-tier split produced a run of defects where one skill pointed at another that was not installed: the init welcome screen "listed `/opsx:new` and `/opsx:continue`, which the default `core` profile never generates, so users were told to run commands that did not exist" (PR #1410); "On the default `core` profile, the update workflow told agents to hand off to `/opsx:continue`... and to `/opsx:new`... neither of which `core` generates" (PR #1775); "`openspec init` and `openspec update` now name the workflows your profile left out and how to add them, so a command that was never installed no longer reads as a broken setup" (PR #1779). — [CHANGELOG.md](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- The original 1.2.0 design had chosen generic next-step wording to avoid exactly this ("Conditional cross-referencing... adds significant complexity... For now, simplicity wins."); the later fix reversed it: "Every cross-workflow handoff is now decided at generation time against the installed workflow set". — [openspec/changes/simplify-skill-installation/design.md](https://github.com/Fission-AI/OpenSpec/blob/main/openspec/changes/simplify-skill-installation/design.md); [CHANGELOG.md](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- Why verify and onboard were added (both now optional). Verify: "Users need a way to validate that their implementation actually matches what was requested before archiving a change"; "A user requested: \"Can we get a :verify that will ensure that the implementation matches what was requested?\"". Onboard: "Users who run `openspec init` are left with files but no clear path to actually using the system. There's a gap between \"I have OpenSpec set up\" and \"I understand the workflow.\"" — [add-verify-skill proposal](https://github.com/Fission-AI/OpenSpec/blob/main/openspec/changes/archive/2026-02-17-add-verify-skill/proposal.md); [add-opsx-onboard-skill proposal](https://github.com/Fission-AI/OpenSpec/blob/main/openspec/changes/archive/2026-02-17-add-opsx-onboard-skill/proposal.md)
- v2.0.0 (11 November 2026): "**Skills only.** OpenSpec no longer writes `/opsx:*` command files. Each command has a skill with the same instructions. For example, `/opsx:propose` becomes `openspec-propose`"; "**One shared copy.**"; "**`delivery` is retired.**" Reasons: "OpenSpec 1.x writes every workflow twice: a skill and a tool-specific command file." and "A project set up for four tools holds four copies of every skill, and tools that read both `.agents/skills` and their own folder load some of them twice". — [CHANGELOG.md](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md); [Issue #2022](https://github.com/Fission-AI/OpenSpec/issues/2022); [share-skills-in-agents-folder proposal](https://github.com/Fission-AI/OpenSpec/blob/main/openspec/changes/share-skills-in-agents-folder/proposal.md)
- v2.1.0 (17 November 2026): skills install once per machine by default, "so we can spend less time maintaining installer code and more time improving the skills themselves"; "Teams that commit OpenSpec skills update every repository when the CLI changes." — [CHANGELOG.md](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md); [install-skills-globally proposal](https://github.com/Fission-AI/OpenSpec/blob/main/openspec/changes/install-skills-globally/proposal.md)
- Stated next steps, not shipped: step 5 of the 2.x plan is "A router skill with references, then slimmer skills that point to it.", with the risk noted "Slimmer skills may work less well." and "Measured first". Separately the lead maintainer opened "Exploration: OpenSpec without archive" (24 September 2026): "Today the specs are updated when a change is archived, which happens after the work is done."; some users expected specs to update with the code "without an extra step to think about." — [Issue #2022](https://github.com/Fission-AI/OpenSpec/issues/2022); [Issue #1968](https://github.com/Fission-AI/OpenSpec/issues/1968)
- The current head of `main` contains no archive-free mode: a search of `src/`, `docs-lab/`, `schemas/` and the changelog found none, and commits on #1968 titled "keep specs current by default and stop after planning" are cross-references from a maintainer's fork. — [Issue #1968](https://github.com/Fission-AI/OpenSpec/issues/1968); [commits on main](https://github.com/Fission-AI/OpenSpec/commits/main/)

### Inferences
- The count history is 3, 10, 4, 5, 6. Each addition after 1.2.0 fixed a real gap (sync needed by archive, update requested by users), which shows how hard it is to hold a small default once actions are separate skills. The cheapest gap-closers were the ones folded into an existing step (archive performing the sync itself when the sync skill is absent).
- Hiding commands behind a profile was cheaper than deleting them but created a second-order cost: every skill and every CLI hint had to learn which siblings exist. A design with one fixed set avoids that whole class of defect.
- The 2.0 rename made the typed form longer (`/opsx:apply` became `/openspec-apply-change`) while the project simultaneously leaned on plain-language prompts; the bet is that people will stop typing command names.
- The maintainers' own open explorations (router skill, no-archive flow, issue #2033 on dropping the deterministic merge from the earlier internals notes) all point toward fewer user-visible steps, not more.

### Gaps
- Release dates for the 1.7 to 1.13 line were not collected, so the handoff fixes above are placed by changelog version only.
- Whether the pre-1.0 `/openspec:proposal` prompt itself ran `openspec validate --strict` was not confirmed; only the README's human "Verify & Review" step and a task line documenting "`openspec validate [change] --strict`" in agent instructions were seen.
- The `simplify-skill-installation` change still sits under `openspec/changes/` rather than `archive/` on `main`, although its content shipped in 1.2.0; archive folder dates in that repository therefore do not date features.

## 4. Is verification required before archive, and is validation automatic or a separate step a person must remember?

### Takeaway
Status: answered with sources. Neither is required in the default skill flow. `verify` is an optional, report-only skill that is not in the core profile and cannot block archive. Structural validation (`openspec validate <change>`) is not called by any of the twelve skills; the only validation the skill path runs is `openspec validate --specs` on the main specs after a merge. The terminal command `openspec archive` does validate the change first, but the archive skill does not call it.

### Cited Findings
- Verify is optional and advisory: listed as "Optional"; "It changes nothing and does not archive." Skill text: "Verification is advisory... `Not verified` describes a limit of this report, not a new archive prerequisite. Archive retains its own checks and user-confirmation behavior." — [docs-lab/reference/skills.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/skills.md); [skills/openspec-verify-change/SKILL.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-verify-change/SKILL.md)
- The current guide says so plainly: "Before archiving, check that the code does what the scenarios describe. The optional verify skill can help find gaps." and "**Archiving does not enforce these checks.** If passing results are required for release, enforce that in your CI or release process." It also warns: "A checked task or an agent's summary alone does not prove the test passed." — [docs-lab/guides/review-the-plan.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/guides/review-the-plan.md)
- The only nudge at the end of apply is one sentence returned by the CLI when all tasks are checked: "All tracked tasks are complete.\nReview or verify the change as appropriate before archiving." It was added in 1.14.1: "Apply no longer calls a change ready to archive too early". — [src/commands/workflow/instructions.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/commands/workflow/instructions.ts); [CHANGELOG.md](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- Archive does not block on incomplete work: "**If incomplete tasks found:** Display warning showing count of incomplete tasks; Ask the user to confirm they want to proceed; Proceed if user confirms"; guardrail "Don't block archive on warnings - just inform and confirm". — [skills/openspec-archive-change/SKILL.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-archive-change/SKILL.md)
- Where validation appears in the shipped skills (a text search of all twelve `SKILL.md` files for "openspec validate"): zero mentions in propose, ff, new, continue, apply, update, verify, explore and onboard; two in sync-specs ("Run `openspec validate --specs` with the same selected-root flags used earlier."); one each in archive and bulk-archive, only for the fallback where the agent merges inline because the sync skill is missing ("After the merge, run `openspec validate --specs`... and treat a failure as a failed sync"). — [skills/](https://github.com/Fission-AI/OpenSpec/tree/main/skills); [skills/openspec-sync-specs/SKILL.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-sync-specs/SKILL.md)
- The default schema's artifact instructions mention `openspec validate` only to describe what it would reject (for example "`openspec validate` rejects a change with zero deltas unless..."), not as a step to run. — [schemas/spec-driven/schema.yaml](https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/schema.yaml)
- The quickstart names no validation step in the loop; its only validate mention is `openspec validate --archived` in the pruning section. — [docs-lab/start/quickstart.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/start/quickstart.md)
- The deterministic CLI path does validate: "Archive validates the change first and refuses one that fails" unless `--no-validate`; "Incomplete tasks warn but don't block." — [docs-lab/reference/cli.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md)
- The archive skill does not use that path: it checks status and task counts, runs the agent-driven sync, then `mkdir -p` and `mv`. A user reported this as a bug on 20 March 2026 ("this skill does not invoke `openspec archive` at all"; 17 thumbs-up); it was closed as not planned on 6 August 2026 and moved to a discussion without an explanation in the thread. — [skills/openspec-archive-change/SKILL.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-archive-change/SKILL.md); [Issue #863](https://github.com/Fission-AI/OpenSpec/issues/863)
- The onboarding walkthrough is the exception: it archives with the terminal command, "`openspec archive \"<name>\" --yes`", so a first-time user sees the validating path and later uses the non-validating one. — [skills/openspec-onboard/SKILL.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-onboard/SKILL.md)
- Validate itself warns that passing is not sufficient: "This check does not run archive's later merged-spec validation or retirement checks. A clean report does not guarantee that archive will succeed." — [docs-lab/reference/cli.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md)
- Pre-1.0, validation was a visible human step: "2. Verify & Review" with `openspec validate add-profile-filters` typed in the terminal. — [README_OLD.md](https://github.com/Fission-AI/OpenSpec/blob/main/README_OLD.md)
- Legacy 1.x guidance recommended, but did not require, the longer ending: "The recommended completion flow: `/opsx:apply ──► /opsx:verify ──► /opsx:archive`" in expanded mode. — [docs/workflows.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/workflows.md) (legacy)
- What validate checks is structural only (ERROR / WARNING / INFO, `--strict` fails on warnings); nothing deterministic compares code with specs. — earlier internals notes, citing [src/core/validation/validator.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/validation/validator.ts)
- Users have asked for checking to be built in rather than remembered: "Cross-artifact quality review between propose/ff and apply" (opened 1 March 2026, 16 comments), whose author adds "I'm aware of the concern about skill count growth."; "/opsx:validate command to check code against the living specs" (26 March 2026, 8 thumbs-up); "Adversarial review skill" (28 August 2026, 3 thumbs-up); and a roadmap-thread request for "A function to validate and correct the work at each task phase" (20 January 2026). — [Issue #783](https://github.com/Fission-AI/OpenSpec/issues/783); [Issue #880](https://github.com/Fission-AI/OpenSpec/issues/880); [Issue #1741](https://github.com/Fission-AI/OpenSpec/issues/1741) (title and counts only); [Discussion #111](https://github.com/Fission-AI/OpenSpec/discussions/111)

### Inferences
- In the default flow a structurally broken change is caught late or not at all: propose does not validate, apply does not validate, and the archive skill validates only the merged main specs. The person must remember `openspec validate` in a terminal, or wire it into CI.
- OpenSpec keeps the step count low by making every check optional. That is the cheap way to be simple. The alternative that keeps the count equally low is to run checks inside the steps people already run (validate at the end of plan, verify at the start of archive) and report the result, with no extra command.
- Offering verification as a separate optional skill shows the cost of that choice in the feedback: users request more review skills, and the requester of one of them apologises for skill-count growth.

### Gaps
- `src/core/archive.ts` and `src/commands/validate.ts` were not read in full; CLI archive behaviour is taken from the CLI reference.
- Whether the instructions returned at run time by `openspec instructions <artifact>` ever tell the agent to run validate was checked only through the schema file and the skill files, not by running the command.
- No data on how many users run `verify` or `validate` before archiving.

## 5. How is an existing codebase handled?

### Takeaway
Status: answered with sources. There is no brownfield step. `openspec init` in a repository with code creates an empty `openspec/` tree and a mostly commented-out `config.yaml`; it detects installed AI tools and old OpenSpec files but does not read the code. Code reading happens inside the normal steps: `propose` is instructed to inspect relevant code, tests, config and docs read-only before drafting, and `explore` does the same on request. Specs accumulate only for what each change touches; generating a baseline is officially discouraged and remains an open, much-requested feature.

### Cited Findings
- What init writes: `openspec/config.yaml`, `openspec/specs/` ("empty for now"), `openspec/changes/` and `changes/archive/`, plus the skills. "Re-running init is safe". — [docs-lab/start/setup.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/start/setup.md)
- What init looks at: existing AI-tool folders, to preselect tools ("`openspec init` now scans your project for existing tool directories (`.claude/`, `.cursor/`, etc.) and pre-selects detected tools"), and legacy OpenSpec artifacts for cleanup. The init source shows detection only for tools and legacy files. — [CHANGELOG.md](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md); [src/core/init.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/init.ts)
- The generated `config.yaml` holds `schema: spec-driven` and comments; `context` is written only when `--language` is passed. The comment block reads: "# Project context (optional) / # Add only constraints that should guide OpenSpec artifacts and workflows. / # Include constraints an agent cannot infer by reading the code. / # Keep general project documentation and discoverable codebase facts out." — [src/core/config-prompts.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/config-prompts.ts); [src/core/init.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/init.ts)
- What belongs in `context`: "Use `context` for facts and constraints that should shape workflow output. Keep durable project documentation in the project's documentation files, and leave out anything the agent can learn by reading the code." It is injected into "every artifact, `apply`, `archive`", capped at 50KB, and "Keep rules short. Everything here lands in the agent's context, and verbose rules can make the output worse." — [docs-lab/customize/project-config.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/customize/project-config.md)
- This reverses the pre-1.0 approach, where init printed a prompt to have the agent fill in a project description: "Please read openspec/project.md and help me fill it out with details about my project, tech stack, and conventions". The stated reason for dropping it: "The old `project.md` was passive—agents might read it, might not, might forget what they read. We found reliability was inconsistent." Because config context is always injected, "you'll want to be concise." — [README_OLD.md](https://github.com/Fission-AI/OpenSpec/blob/main/README_OLD.md); [docs/migration-guide.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/migration-guide.md) (legacy)
- Propose reads the code before writing: "**Inspect the relevant project before drafting**: Read `context` and `rules` first, then inspect relevant implementation, nearby tests, configuration, and documentation outside `openspec/`. Keep inspection read-only and proportional to the change"; "Ground scope, approach, and tasks in what you find. Distinguish observed behavior from assumptions and proposed additions; surface conflicts with existing specs instead of silently deciding which is correct."; "Do this discovery now, rather than leaving generic \"explore the codebase\" or \"make a plan\" tasks for implementation." — [skills/openspec-propose/SKILL.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-propose/SKILL.md)
- That instruction arrived in 1.12.0: "Guide propose and fast-forward workflows to inspect relevant project code, tests, and documentation before drafting artifacts, so plans reflect the existing implementation instead of deferring basic discovery to implementation tasks." A request titled "Proposal command should explore entire codebase by default" dates from 25 November 2025. — [CHANGELOG.md](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md); [Issue #339](https://github.com/Fission-AI/OpenSpec/issues/339) (title only)
- Propose also consults existing specs: the proposal instruction says to run `openspec list --specs` and `openspec show "<spec-id>" --type spec --json --no-scenarios` before filling in capabilities. — earlier internals notes, citing [schemas/spec-driven/schema.yaml](https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/schema.yaml)
- Explore: "You may read files, search code, investigate the codebase, and run read-only commands or tools without confirmation, but you must NEVER write code or implement features."; "Before asking a factual question, follow the context discovery below and inspect relevant OpenSpec artifacts, source, tests, docs, and configuration. Do not ask the user to repeat facts you can verify." It lists changes and specs and reads `config.yaml` context. Output: "Nothing by default"; on request it captures insights into a change. — [skills/openspec-explore/SKILL.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-explore/SKILL.md); [docs-lab/reference/skills.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/skills.md)
- Onboard (optional, about 15 to 20 minutes, eleven phases) scans the code for a small starter task: "TODO/FIXME comments", "Missing error handling", "Functions without tests", "Type issues", "Debug artifacts", "Missing validation", plus `git log --oneline -10`; then walks explore, new, each artifact, apply and archive with pauses. It has a "Scope Guardrail" for tasks that are too large. — [skills/openspec-onboard/SKILL.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-onboard/SKILL.md)
- The adoption rule (legacy guide, released with v1.6.0): "**You do not document your whole codebase to start. You write specs only for what you're about to change.**"; "Resist the urge to back-fill everything. Writing specs for code you aren't changing feels productive and usually isn't. Those specs go stale, because nothing forces them to track reality."; existing PRDs are "source material for exploration, not as specs to convert." Its "thirty-second version" is init, then optional explore, propose, apply, archive. — [docs/existing-projects.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/existing-projects.md) (legacy)
- The current-site page for this topic is still headings only ("Start with a change", "Specs for existing code", "Working from a PRD", "Organizing specs as they grow"). — [docs-lab/guides/existing-codebases.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/guides/existing-codebases.md)
- Maintainer answers to users: "simply create your first change proposal using OpenSpec" (23 January 2026); "Propose the checkout work you were going to do anyway" (23 July 2026); "You write specs only for what each change touches, and your specs fill in over time" (28 July 2026, closing a 2025 question on baselining). — [Issue #510](https://github.com/Fission-AI/OpenSpec/issues/510); [Discussion #199](https://github.com/Fission-AI/OpenSpec/discussions/199)
- Demand for a baseline persists: "Reverse-engineer specs from existing implementations (code-first workflow)" is open since 18 February 2026 with 17 thumbs-up on the body and 13 on a supporting comment, labelled `design-review`; an automated triage comment there recommended "A new `opsx:discover` skill as an 11th workflow module". "How can I use OpenSpec in a large existing project" drew 11 thumbs-up. Community discussions on code-to-spec tooling drew 18 and 9 votes. A roadmap comment asking for a baseline command for brownfield projects drew 8 votes (27 December 2025). — [Issue #724](https://github.com/Fission-AI/OpenSpec/issues/724); [Issue #510](https://github.com/Fission-AI/OpenSpec/issues/510); [Discussions sorted by top](https://github.com/Fission-AI/OpenSpec/discussions?discussions_q=sort%3Atop) (#739, #634); [Discussion #111](https://github.com/Fission-AI/OpenSpec/discussions/111)
- Independent caution: delta specs assume the agent understands the unchanged code, so poorly documented projects risk invented context; one evaluator saw OpenSpec add "rationale to decisions you didn't make". — earlier comparison notes, citing [ypyl.github.io](https://ypyl.github.io/programming/2026/06/03/openspec-vs-spec-kit-sdd.html) and [ranthebuilder.cloud](https://ranthebuilder.cloud/blog/i-tested-three-spec-driven-ai-tools-here-s-my-honest-take/)

### Inferences
- OpenSpec's brownfield answer costs zero extra commands: the code is read just in time by the planning step, scoped to the change. That is the main reason the flow is the same three requests on a new and an old repository.
- The price is that nothing persistent is learned about the codebase between changes except what lands in specs; each propose re-discovers the surroundings. The steady demand for a baseline (issue #724, discussions #199, #634, #739) shows that some users want a one-time "learn this repo" action even if the vendor advises against it.
- Moving project context from a file the agent may read (`project.md`) to text that is always injected (`config.yaml` `context`) shifted the design goal from completeness to brevity. The guidance "leave out anything the agent can learn by reading the code" is a useful rule for any always-injected context.

### Gaps
- `init.ts` was searched, not read in full (it is about 1,500 lines); the statement that init does not read project code rests on that search and on the documented outputs.
- No measurement was found of how well propose's just-in-time inspection works on large repositories.
- Discussions #634 and #739 were seen only as list entries.

## 6. What does the `openspec` CLI itself expose, how is its help organised, and how terse is its output?

### Takeaway
Status: answered from the CLI reference and source; the JSON contract rests on the earlier internals notes; real `--help` output was not observed because nothing was executed. The CLI has 22 documented top-level commands in five groups plus two deprecated noun forms, and most of them are meant for the agent, not the person. A person normally types `init`, `update`, sometimes `config profile`, `list`, `view` or `validate`. There is no CLI command for propose, apply or verify. Human output is short and ends with one "Next:" line; nearly every command has `--json`; there is no quiet flag.

### Cited Findings
- Documented groups: "Set up" (`init`, `update`, `config`); "Changes and specs" (`list`, `show`, `view`, `validate`, `archive`); "Workflows and schemas", headed "Your agent runs most of these during the workflow." (`new`, `status`, `instructions`, `templates`, `schemas`, `schema`); "Multi-repo (beta)" (`store`, `doctor`, `context`, `workset`); "Utilities" (`version`, `install`, `feedback`, `completion`); "Deprecated" (`change`, `spec`). That is 22 plus 2. — [docs-lab/reference/cli.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md)
- The source registers the same commands and two hidden ones (`experimental`, an alias of init, and `__complete`). The only custom help text is an "after" block on `init` listing tool ids; a search of the CLI source found no help grouping calls. — [src/cli/index.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/cli/index.ts)
- Global options: "Every command takes `-h, --help`. The bare `openspec` command also takes: `-V, --version`... `--no-color`". A search of the CLI reference for `--quiet`, `--silent` or `-q` found nothing; the only verbosity switch is `--verbose` on `completion install`. — [docs-lab/reference/cli.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md); [src/cli/index.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/cli/index.ts)
- `--json` is declared on `version`, `update` (with `--dry-run`), `list`, `show`, `validate`, `archive`, `status`, `instructions`, `templates`, `schemas` and `new change`; the CLI reference mentions `--json` 68 times. — [src/cli/index.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/cli/index.ts); [docs-lab/reference/cli.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md)
- JSON discipline: "every --json failure leaves exactly one JSON document on stdout (the command's null-shape plus a status array)"; first-run notices go to stderr and are deferred on JSON runs; the completion tip is deferred when stderr is not a terminal because "pipes and the agent-driven runs that dominate this CLI's usage would otherwise burn the user's one-shot tip into a log nobody opens." Since 1.3.1, "Spinner progress text no longer leaks into stderr when `--json` is passed". — [src/cli/index.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/cli/index.ts); [CHANGELOG.md](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- Non-interactive switches: `--no-interactive` on `show` and `validate` ("Never prompt: a missing or ambiguous name becomes an error."); `-y, --yes` on `archive`; `archive --json` "Needs `--yes`". Outside a terminal, commands exit 1 and print the flags to use instead of prompting. — [docs-lab/reference/cli.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md)
- Terse human output, as documented. `list`: one row per change, e.g. "add-rate-limit     No tasks      just now". `validate --all`: "✓ change/add-rate-limit / ✓ spec/api / Totals: 2 passed, 0 failed (2 items)". `status`: a four-line header, one line per artifact (`[x]`, `[ ]`, `[-]`), then one line "Next: openspec instructions design --change \"add-rate-limit\" --json". `init`: about six lines ending in "Getting started: Start your first change: /openspec-propose \"your idea\"". `archive`: about eight lines including "Totals: + 1, ~ 0, - 0, → 0". — [docs-lab/reference/cli.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md)
- The "Next:" line is a deliberate resume aid: "The `Next:` line names the one command that moves the change forward, so `openspec status` is enough to pick a change back up in a fresh session." — [docs-lab/reference/cli.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md)
- A rough edge: `status` with neither `--change` nor `--all` "exits 1 and lists the available changes, even when only one exists". — [docs-lab/reference/cli.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md)
- `validate --report findings` exists to cut bulk output: it "returns only items with errors, warnings, or information while keeping full-run totals and exit codes." — [CHANGELOG.md](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- Skills are pre-approved to call the CLI so the user is not prompted on each call: every `SKILL.md` carries `allowed-tools: Bash(openspec:*)` (since 1.6.0). — [CHANGELOG.md](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- The split between the two surfaces is the project's most common confusion by its own account: "Where do I type `/opsx:propose`? In your AI assistant's chat, not your terminal. This is the single most common point of confusion, so it has its own page". — [docs/faq.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/faq.md) (legacy)
- A name collision between the surfaces: `openspec update` (terminal, refreshes skills) versus the `update` workflow (chat, revises a plan). The changelog notes "`openspec update` itself is deliberately left unclaimed: it is a real CLI command that refreshes generated files, unrelated to the update-change workflow, which claims \"openspec update change\" instead." — [CHANGELOG.md](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- The machine contract (one JSON document per call, diagnostic envelope `{severity, code, message, target?, fix?}`, stable snake_case codes) and the prompt assembly done by `openspec instructions`. — earlier internals notes, citing [docs/agent-contract.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/agent-contract.md)
- The skills themselves are long: the six core `SKILL.md` files total about 1,360 lines and all twelve about 2,860 (propose 174, explore 355, apply 205, update 108, sync 289, archive 227; onboard alone is 551), and each repeats the same "Store selection" and "Project check" paragraphs. — [skills/](https://github.com/Fission-AI/OpenSpec/tree/main/skills)

### Inferences
- The CLI is two tools under one name: a small human tool (set up, look, check) and an instruction server for agents (`status`, `instructions`, `context`, `new change`). The documented help groups reflect this; the runtime `--help` probably does not, since no grouping is configured in source.
- 24 top-level commands is a large surface for something marketed as lightweight; roughly a third are beta multi-repo or deprecated. A person can ignore most of them, but `--help` shows them all.
- Terseness is handled per command rather than by a global mode: short defaults, `--json` everywhere, a findings-only report for bulk validation, and notices kept off stdout. That is enough for agents; there is no way to make the human output quieter still.
- Two verbs meaning different things on the two surfaces (`update`, `archive`) is avoidable confusion; `archive` is worse because the two paths also behave differently (see question 4).

### Gaps
- `openspec --help` and per-command help were not run, so the actual help layout, ordering and length are unverified.
- Output examples are the documentation's; real output length on a large project was not observed.

## 7. What do users say about the flow?

### Takeaway
Status: partly answered. The strongest first-hand signal is the one the maintainers themselves acted on: people complained there were too many skills (ten), which produced the four-skill core and `propose` in February 2026. Since then feedback pulls both ways: some users want even fewer, merged or automatic steps (one routed skill, one opinionated flow, archive that always syncs, no archive at all), others want more control (step-by-step apply, review and validation steps, the stepwise planning skills back). The two-tier split and the two surfaces (chat skills versus terminal CLI) are recurring sources of confusion. Reddit, Discord and Hacker News were not reached.

### Inferences
- The complaint that moved the project was about the number of installed skills, not about the number of steps in a change: ten skills overwhelmed new users even though a change needed three or four of them. What a tool shows by default matters as much as what a change requires.
- Reaction counts on flow topics are small (single or low double digits) against roughly 75,000 stars. The most-reacted flow items are about trust in one step (archive not using the CLI, 17; code-first baseline, 17) rather than about the count of steps. The qualitative pattern is clearer than the numbers.
- Requests split into "fold it in" (routed single skill, archive always syncs, no archive, autopilot) and "let me slow down" (apply one task at a time, stepwise planning, review skills). Both can be served by options on a few commands; OpenSpec instead served the second group with extra skills and then had to hide them.
- Every forgotten-step report concerns the last step: archive or sync is forgotten, skipped by the agent, or fails. A flow that ends with a step whose only purpose is bookkeeping should expect it to be skipped, which is the maintainers' own motive for exploring a flow without archive.
- Flow-level requests are routinely closed as "not planned" and moved to Discussions, where the two examples read had no replies. Absence of maintainer argument against simplification proposals should not be read as agreement or rejection.
