## 1. Per tool: minimal user steps for one change, what is automatic, where the human gate sits, and shorter paths added after launch

### Takeaway
By November 2026 every tool looked at has converged on the same everyday shape: one prompt, clarifying questions asked up front, all planning artefacts generated without stops in between, at most one human approval before code is written, and review of the result at the end. Kiro and BMAD both started with multi-gate, multi-document flows and added (Kiro) or switched to (BMAD) a one-session path during 2026, each giving "too much process for the problem" or "human attention is the bottleneck" as the reason; the plan modes of Claude Code, Cursor and Copilot had the one-gate shape from the start.

### Cited Findings

Kiro (spec mode, Quick Spec, bugfix path):
- [vendor docs] A spec is three files: `requirements.md` (or `bugfix.md`), `design.md`, `tasks.md`, produced in three phases (requirements or bug analysis, design, tasks). Tasks can be run "individually or all at once"; with "Run all Tasks" Kiro builds a dependency graph and runs independent tasks in waves ("Waves execute sequentially; tasks within a wave execute concurrently."). Feature Specs, Bugfix Specs and Quick Spec are available in the IDE, CLI, Web and Mobile. — [Kiro docs: Specs](https://kiro.dev/docs/specs/)
- [vendor docs] Standard Feature Spec flow: choose Feature, choose Requirements-First (requirements, design, tasks) or Design-First (design, requirements, tasks), with a setting to fix a default workflow and skip that choice; Kiro generates the first artefact; "Analyze Requirements" is an optional step before design; then design and tasks follow. The docs page does not spell out the approval step; it is implied by the Quick Spec page ("no approval gates between phases") and stated in the vendor blog and in a first-hand review ("You review requirements, approve the design, then watch the implementation."). — [Kiro docs: Feature Specs](https://kiro.dev/docs/specs/feature-specs/); [Kiro blog, 12 May 2026](https://kiro.dev/blog/faster-smarter-specs/); [aimadetools review, 20 March 2026](https://www.aimadetools.com/blog/kiro-one-week-review/)
- [vendor docs] Quick Spec (page updated 4 August 2026): "Quick Spec is a session mode that auto-generates requirements, design, and tasks in a single pass." Kiro first asks clarifying questions on scope, constraints and edge cases, which the page calls "the key interaction point"; there are "no approval gates between phases"; the user then reviews the finished task list or starts implementing, and can edit any artefact afterwards and regenerate with Sync Files. Recommended for well-understood features and rapid prototyping; for compliance-sensitive, high-stakes or unfamiliar work a standard Feature Spec is "usually the better fit." Quick Spec differs from Vibe mode, which saves no artefacts. — [Kiro docs: Quick Spec](https://kiro.dev/docs/specs/quick-spec/)
- [vendor claim] Shorter path added after launch, with the reason: IDE version 0.12 (6 May 2026) added "Quick Plan", "A new Spec session mode for when you already know what you want to build.", promising "Same traceability and correctness that Specs provide, with a tighter feedback loop." The blog post of 12 May 2026 gives the reason that, for well-understood features, "the current step-by-step approval flow can feel like more process than the problem requires", and says the team "started questioning the assumption that structure and quality imply slowness." No user data is cited. The docs now call the feature Quick Spec; the changelog and blog call it Quick Plan. — [Kiro changelog 0.12](https://kiro.dev/changelog/ide/0-12/); [Kiro blog, 12 May 2026](https://kiro.dev/blog/faster-smarter-specs/)
- [vendor claim] The same release made "Run all Tasks" concurrent ("For specs with 4+ independent tasks, this can cut execution time by up to 4x."); the blog's anecdotal figure is large specs going from "over an hour" (a graphic says 60 to 90 minutes) to about 15 minutes. Not independently verified. — [Kiro changelog 0.12](https://kiro.dev/changelog/ide/0-12/); [Kiro blog, 12 May 2026](https://kiro.dev/blog/faster-smarter-specs/)
- [vendor docs] Bugfix Spec flow (page updated 4 August 2026): choose Bug Fix on the "Let's build" screen, describe the bug (reproduction steps, expected result, code that must not change); Kiro writes `bugfix.md` (current, expected and unchanged behaviour in WHEN/THEN form), then explores the code "to root cause the issue" and writes `design.md` (root cause, proposed fix, properties to test), then generates tasks including property-based tests. The page lists three user actions and does not state where approval is required. Recommended for complex bugs, critical code paths, compliance needs, or when earlier fixes caused regressions. — [Kiro docs: Bugfix Specs](https://kiro.dev/docs/specs/bugfix-specs/)
- [vendor claim] (earlier notes) The Bugfix Spec and the design-first variant were added on 18 February 2026 because "the current flow was not flexible enough for these types of tasks." — [Kiro blog, 18 February 2026](https://kiro.dev/blog/specs-bugfix-and-design-first/)
- [first-hand] Kiro CLI (tested 31 July 2026, CLI 2.15.2 in v3 mode): `/spec new <name>`, then a new description step, then a choice of Build a Feature, Fix a Bug or Quick Spec; requirements were drafted straight from the description with no question sequence (the earlier Quick Spec flow asked about five questions). In Plan mode the agent asks clarifying questions, produces an Implementation Plan, and after the user approves, execution starts at once; the changelog line quoted is "In Plan mode, approving a plan now kicks off execution immediately." Previously the user had to press Shift+Tab to switch modes by hand. — [DevelopersIO, 31 July 2026](https://dev.classmethod.jp/articles/kiro-cli-specnew-step/)

BMAD method:
- [measured] (earlier notes) In February 2026 tests (BMAD v6.0.3) the full method used twelve agents and took 2 days of planning plus 4 days of implementation for one backend feature; BMAD Quick was two steps and one document and scored higher (3.74 versus 3.65). — [ranthebuilder.cloud, 13 April 2026](https://ranthebuilder.cloud/blog/i-tested-three-spec-driven-ai-tools-here-s-my-honest-take/)
- [vendor docs] Current docs (footer "2026", no version on page) describe four stages (Clarify, Plan, Build and verify, Learn and adjust) and four sizes of work (Trivial, One-session, Epic-sized, Project-sized) instead of the old Quick Flow / BMad Method / Enterprise tracks. For "An obvious, low-risk edit" the routing table says: "Your agent, directly. No skill is needed." The entry point is "Run `bmad` and describe what you have."; it "recommends the smallest one that fits." Stages are described as kinds of help, not a sequence to complete. — [BMAD docs: How BMad works](https://docs.bmad-method.org/start/how-bmad-works/)
- [vendor docs] One-session change: a single skill, `bmad-build`. The page's rule is "Use the smallest amount of BMad that safely fits the change." (about one goal, roughly 500 changed lines excluding tests). Automatic: investigate the codebase and upstream documents (clear requests proceed without a clarification turn); route on three facts (intent gaps, irreversible actions, footprint); clean designs take a "light path" with a minimal plan and implementation in the same session, flagged designs get "a full written plan first"; implement; review by independent reviewers (three lenses: Blind Hunter, Edge Cases Hunter, Verification Gap Finder); triage and fix; commit locally; present a short summary. Human touch points: start a fresh chat, state intent, answer open questions when they appear, approve the plan when asked (full-plan path only), review the result (diff or walkthrough), optionally ask for a push and PR. — [BMAD docs: Build a Change](https://docs.bmad-method.org/build/build-a-change/)
- [vendor claim] Reasons given on the same page: human attention is "by far the most expensive resource, and the productivity bottleneck in AI-backed software development."; "fixing the plan is cheaper than fixing the code."; and plain "Plan mode and code" skips the review and triage that `bmad-build` automates. — [BMAD docs: Build a Change](https://docs.bmad-method.org/build/build-a-change/)
- [vendor docs] Consolidation history from the changelog (first 100,000 characters read): v6.1.0 (12 March 2026) shipped "An experimental preview of the new Quick Dev"; v6.2.2 (25 March 2026) rewrote `bmad-help` "from procedural 8-step execution to outcome-based skill design (~50% shorter)"; v6.3.0 (9 April 2026) removed the Quick Flow persona and merged three personas into one, and removed `bmad-init`; v6.7.0 (17 May 2026) turned the product brief from "a five-stage scripted workflow" into a single skill; v6.10.0 (3 July 2026) retired `bmad-investigate` because it "reached the same conclusions as plain investigation at higher cost."; v6.11.0 (9 August 2026): "Quick Dev becomes Build, the one official way BMad implements code.", with the stated reason "The skill catalog gets a lot smaller.", core reduced to eight skills, the story-creation and story-development skills deprecated, and "The post-implementation acceptance-criteria checkbox ritual is gone."; v6.12.0 (3 September 2026, latest release): "Simple changes now get a two-section spec and finish in one session.", and Build decides how much ceremony a change needs after investigating it. — [BMAD CHANGELOG](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/CHANGELOG.md)

Tessl:
- [vendor docs] Tessl's current overview describes "an open platform for managing agentic development across your organization" with six components (registry and package manager, governance, evals, observability, context and findings, and the Tessl Agent, "open beta"). The overview page describes no requirements, plan, implement, verify workflow and no per-change command sequence. — [Tessl docs](https://docs.tessl.io/)
- [opinion, third-party profile dated June 2026] The spec-driven Framework is still closed beta; the Registry has been in open beta since September 2025 and lists 3,000+ skills; specs have three parts (description, capabilities linked to tests, API definition) with `@generate` and `@describe` tags; no development-loop review gate is described. — [rywalker.com](https://rywalker.com/research/tessl)

- [first-hand, October 2025] (earlier notes) One spec per code file, generated code marked do-not-edit, non-repeatable regeneration. — [martinfowler.com](https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)

Claude Code plan mode:
- [vendor docs] "Plan mode tells Claude to research and propose changes without making them." Enter with Shift+Tab, by prefixing one prompt with `/plan`, or with `claude --permission-mode plan`; edits "stay blocked until you approve the plan". One approval prompt with three choices: "Yes, and use auto mode" (or "Yes, auto-accept edits"), "Yes, manually approve edits", "No, keep planning". Ctrl+G opens the plan in a text editor; plan files live in `~/.claude/plans/` or a configured directory. — [Claude Code docs: permission modes](https://code.claude.com/docs/en/permission-modes); [Claude Code docs: common workflows](https://code.claude.com/docs/en/common-workflows)
- [vendor docs] The current best-practices page (read November 2026) no longer prescribes a planning step for every task. It opens with "in most cases, your first plain prompt in a fresh session already does the right thing", and for unclear work suggests a no-command spec path: "Interview me until you could write the spec, then write it to SPEC.md.", then "start a fresh session to build from it". — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)
- [first-hand, 17 December 2025] Armin Ronacher inspected plan mode and found it is a prompt plus a file: "A plan in Claude Code is effectively a markdown file that is written into Claude's plans folder by Claude in plan mode."; "There is no other enforcement from what I can tell." He prefers a hand-off file he edits himself and asks "Why do I have to switch the user interface into a different mode?"; he notes that pi has no plan mode "and Amp is removing theirs". (The docs now say edits are blocked until approval, so the enforcement detail may be out of date.) — [lucumr.pocoo.org](https://lucumr.pocoo.org/2025/12/17/what-is-plan-mode/)

Cursor plan mode:
- [vendor docs] Flow: Shift+Tab (or the mode picker; Cursor "also suggests it automatically when you type keywords that indicate complex tasks"); "Agent asks clarifying questions"; it researches the codebase; it writes a plan as a Markdown file with file paths and code references; the user edits through chat or the file; "Click to build the plan when ready." GitHub Copilot (plan agent in VS Code; cloud agent):
- [vendor docs] In VS Code: `/plan` followed by the outcome, constraints and verification approach (or select Plan mode). "The agent researches your project, asks clarifying questions, and creates a plan for you to review before implementation."; the plan lists "implementation steps, relevant files, and verification steps". Review happens in a plan card and an editable plan file with inline comments; pending feedback "disables approval until you submit or clear it." Choices on the card: Implement Plan, Approve Plan Only, Implement with Autopilot, Reject. "Approving a plan and approving tool actions are separate decisions." Guidance: "Use a separate planning step when the approach is uncertain or a change spans multiple parts of your project."; "For a small, well-defined edit, you can ask an agent to implement it directly." - [vendor docs] Cloud agent: started from the Copilot home page, panel, or a repository's Agents tab; "Copilot can research a repository, plan changes, and implement them in the background."; it "can open one pull request per task"; "You can review the proposed changes and ask for refinements before creating a pull request, or request a pull request in your prompt." No separate plan-approval step is described. Gates are the pull-request ones: the agent pushes to a single branch, "cannot mark its pull requests as "Ready for review" and cannot approve or merge a pull request", the requester cannot approve it, and "By default, workflows are not triggered until Copilot cloud agent's code is reviewed". — [GitHub docs: about the agent](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent); [GitHub docs: risks and mitigations](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)

### Inferences
- Minimal user steps for one change, derived from the docs above (counts are my reading, not vendor-stated):

| Tool and path | User actions (minimum) | Automatic | Human gate |
| --- | --- | --- | --- |
| Kiro standard Feature Spec | pick type and workflow, describe, approve requirements, approve design, start tasks | each document, task dependency graph, parallel task waves | between phases (2), then final review |
| Kiro Quick Spec | pick mode, describe, answer questions, start tasks | all three documents in one pass | none between phases; questions up front, task list at the end |
| Kiro Bugfix Spec | pick Bug Fix, describe bug, follow through | bug analysis, root cause, fix design, property-based tests | not stated in docs |
| BMAD `bmad-build` (light path) | state intent, review result | investigate, route, minimal plan, implement, multi-lens review, triage, local commit | result review only |
| BMAD `bmad-build` (flagged design) | state intent, answer open questions, approve plan, review result | same, plus full written plan | plan approval, result review |
| Claude Code plan mode | prompt in plan mode, choose one of three approval options | research, plan file, then implementation | one plan approval |
| Cursor plan mode | prompt, answer questions, click Build | research, plan file, implementation | one (Build) |
| Copilot plan agent (VS Code) | `/plan` prompt, answer questions, choose Implement Plan | research, plan, implementation | one plan approval, tool approvals separate |
| Copilot cloud agent | prompt or assign, review pull request | branch, changes, tests and linters in a sandbox, security checks | pull-request review and merge |
| OpenSpec core profile | propose, apply, archive | all planning artefacts in one step | none enforced (earlier notes) |

- The shortening always took one of three forms: (a) merge several generation steps into one pass and move the human interaction to clarifying questions at the start (Kiro Quick Spec, OpenSpec propose); (b) let the tool decide after investigating how much plan a change needs, so the plan gate appears only when a risk signal fires (BMAD Build since v6.12); (c) make approval itself start the next step (Kiro CLI, Claude Code's approval prompt that also sets the permission mode).
- Both spec-first tools that kept a heavy path now present it as the exception chosen by risk (Kiro: compliance, high stakes, unfamiliar; BMAD: multi-system, unclear scope, team documentation), not as the default.
- BMAD's direction of travel across 2026 is steady reduction of named things the user must know (personas merged, skills retired, one build skill, a single `bmad` entry point). That is first-party evidence that a large command and persona catalogue did not survive use.

## 2. What users name as heavy, and what they praise as simple (dated 2025 and 2026 reports)

### Takeaway
Across reports the heaviest thing is the human time spent reading generated documents and waiting through a fixed ceremony that does not shrink for small changes; repeated approvals come second and are well measured (users approve 93 to 97 percent of prompts, so the prompts add delay without adding checking). The count of commands as such is rarely the complaint; the complaints are about the count of documents, agents or personas, and phases, and about a tool that does not say what to do next. What is praised as simple: one sentence in, a short list of small tasks out, a tool that picks the next step, and an escape to plain prompting for small fixes.

### Cited Findings

Fixed ceremony that does not scale down (the most frequent complaint):
- [first-hand, 5 August 2026] Ricardo Gil on Kiro: "The spec workflow adds friction to simple tasks."; "If I need to rename a field across three files, generating a spec for that is overkill."; "right now you feel the spec overhead even on medium-sized changes."; "If your workflow is 70% small changes and 30% feature builds, Kiro costs you time on the majority of your work." — [ricardogil.com](https://ricardogil.com/blog/kiro-review-spec-driven-agentic-ide)
- [first-hand, 20 March 2026, updated 13 November 2026] One week with Kiro: five steps (discuss, spec, design, tasks, build), "It sounds heavy. It is, a little."; spec mode was "painful for quick fixes."; "You don't need a requirements document for that". — [aimadetools](https://www.aimadetools.com/blog/kiro-one-week-review/)
- [first-hand, 18 December 2025] Peter McAree on Kiro: "For small tweaks, the full spec workflow can feel like overkill - especially with re-generating tasks." — [petermcaree.com](https://petermcaree.com/posts/kiro-agentic-ide-hype-hope-and-hard-truths/)
- [first-hand, 8 February 2026] A developer building a to-do macOS app with BMAD: "After 2 days of prompting through BMAD workflows" he had PROJECT.md, REQUIREMENTS.md, ROADMAP.md, ARCHITECTURE.md and several epic and story files and "Zero lines of actual code."; "By the time you're ready to code, you've lost momentum."; "For a small project, it's overkill". He moved to a lighter tool: "Less markdown files, more code." BMAD version not stated. — [guillim.github.io](https://guillim.github.io/ai/development/2026/02/08/bmad-method-disappointment.html)

- [first-hand, 18 December 2025] Kiro: "Each task typically took 5-15 minutes for the agent to complete." — [petermcaree.com](https://petermcaree.com/posts/kiro-agentic-ide-hype-hope-and-hard-truths/)

Repeated approvals:
- [vendor measurement, 25 March 2026] Anthropic: "in practice users accept 93% of them anyway."; "Over time that leads to approval fatigue, where people stop paying close attention to what they're approving." No method published. — [Anthropic engineering](https://www.anthropic.com/engineering/claude-code-auto-mode)
- [vendor measurement, 7 August 2026] "users approve 97% of permission prompts in Claude Code."; this "suggests many users are clicking through reflexively rather than reviewing each command." - [vendor docs, read November 2026] Manual mode: "Safe, but after the tenth prompt you start approving without reading, and nothing moves while you're away from the keyboard." — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)
- [vendor measurement, 10 November 2026] Kiro CLI, one-week sample: Kiro asked permission for 15.8% of tool calls and users approved 97.1% of those; 13.4% of sessions started with `trust-all-tools` on. - [opinion, 27 April 2026] On phase approvals: "The whole point of the approval gate is that it's a gate, not a formality."; a rubber-stamped spec is "worse than no spec at all, because the team reviews it, sees the structure, and assumes the content is solid." — [DoiT](https://www.doit.com/blog/spec-driven-development-with-kiro-ai-code-ownership)

Not knowing what to run next:
- [measured scoring, February 2026 tests] (earlier notes) OpenSpec was credited because it "always suggests the next step" and tracks status; Spec Kit was marked down for "no status or help command" (workflow visibility 4 versus 2). — [ranthebuilder.cloud](https://ranthebuilder.cloud/blog/i-tested-three-spec-driven-ai-tools-here-s-my-honest-take/)
- [first-hand guide, 2026] (earlier notes) OpenSpec commands "appear to do nothing" when typed in a terminal instead of the assistant chat. — [glukhov.org](https://glukhov.org/ai-devtools/openspec/)
- [vendor docs] BMAD made a "what next" helper its main entry: `bmad-help` was "Elevated as the primary on-ramp across all documentation" (v6.0.2), and the current docs say "Run `bmad` and describe what you have." — [BMAD CHANGELOG](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/CHANGELOG.md); [BMAD docs](https://docs.bmad-method.org/start/how-bmad-works/)

Cost as a source of hesitation:
- [first-hand, 5 August 2026] Kiro: "A full spec-driven feature build costs roughly 15–25 credits depending on complexity."; "When every interaction costs credits, you start second-guessing whether to use the full spec flow or just inline-edit."; "That cognitive overhead is real". — [ricardogil.com](https://ricardogil.com/blog/kiro-review-spec-driven-agentic-ide)
- [first-hand, 16 August 2025, preview-era] Kiro spec mode hit chat-context limits "almost immediately, and exclusively in Spec Mode", including on "the first task after going through building the requirements, design and task list". — [AI Leverage](https://aileverage.substack.com/p/comparing-kiro-with-cursor-after)

- [first-hand, 5 August 2026] "Kiro handles simple edits inline without forcing the full spec flow"; "you can pause, resume, or hand off mid-feature without losing context." — [ricardogil.com](https://ricardogil.com/blog/kiro-review-spec-driven-agentic-ide)
- [first-hand, 20 March 2026] "Use spec mode for features, vibe mode for fixes."; "The spec gave it enough context to get things right on the first pass." — [aimadetools](https://www.aimadetools.com/blog/kiro-one-week-review/)
- [measured scoring] (earlier notes) BMAD Quick, two steps and one document, outscored the full method. — [ranthebuilder.cloud](https://ranthebuilder.cloud/blog/i-tested-three-spec-driven-ai-tools-here-s-my-honest-take/)
- [first-hand, 17 December 2025] A plan as an ordinary file on disk the user can open and edit feels more natural than a separate mode. — [lucumr.pocoo.org](https://lucumr.pocoo.org/2025/12/17/what-is-plan-mode/)
- [analyst, November 2026] Thoughtworks Radar Vol. 35 put a small skills collection in Trial because the skills are "explicitly designed to be small, easy to adapt, and composable", while cautioning against "adopting entire skill libraries without evaluating them". — [Thoughtworks Radar, Tools](https://www.thoughtworks.com/radar/tools)

### Inferences
- Ranking the five candidate causes of heaviness by weight of evidence: (1) number and length of files to review, the only one with repeated first-hand measurement; (2) fixed ceremony for small changes, the most often repeated first-hand complaint; (3) repeated approvals, measured by two vendors and one survey; (4) waiting time, reported but mostly tolerated when the user is not blocked; (5) raw command count, almost never named. Where "too many" appears it refers to documents, agents, personas and phases. A tool can therefore feel heavy with three commands and light with six; what counts is how many things the user must read and decide per change.
- "Not knowing what to run next" shows up as a positive differentiator (the tool that always prints the next step wins on developer experience) more than as an explicit complaint; it is cheap to fix and the evidence says it is noticed.
- Approval prompts that are accepted more than nine times in ten carry almost no information. The same logic applies to phase gates: a gate people pass without reading costs time and, per the DoiT argument, adds false assurance.
- Reviewers consistently want two speeds in one tool and name the missing fast path as the main defect when it is absent.

### Gaps
- No report was found that measures command count against satisfaction, or that compares two tools differing only in number of commands.
- First-hand BMAD reports after the August 2026 consolidation (v6.11 and later) were not found; the heavy-BMAD reports describe versions from early 2026 or are undated.
- The approval-rate figures are vendor-published without method; the Kiro sample is one week.
- Reddit and Discord sentiment was not reachable.

## 3. What command-line design guidance says about command count and output, and how well-known tools split everyday commands from the rest

### Takeaway
The guidance does not set a number; it says to make the default right for most users, show the common commands first, keep success output brief while stating what changed and what to run next, and move advanced material to a second level reached on request. git, gh, cargo and uv all present a short everyday set first (roughly 12 to 24 commands) and push the remainder behind a second listing or a named lower-level interface.

### Cited Findings

Command Line Interface Guidelines (clig.dev; authors Aanand Prasad, Ben Firshman, Carl Tashian, Eva Parish; no date on the page):
- Help: when run with no arguments, "display concise help text", which should include only a description, "One or two example invocations.", "Descriptions of flags, unless there are lots of them.", and "An instruction to pass the `--help` flag for more information." "Lead with examples." "Display the most common flags and commands at the start of the help text.", with git's grouped common-command list as the model. "If you've got loads of examples, put them somewhere else". — [clig.dev](https://clig.dev/)
- Output: "Display output on success, but keep it brief."; "it's usually best to err on the side of less."; offer `-q` to suppress non-essential output; do not print by default what only the tool's authors understand, "only in verbose mode."; "If you change state, tell the user."; "Make it easy to see the current state of the system."; "A command is saying too much when it dumps pages and pages of debugging output"; "A command is saying too little when it hangs for several minutes and the user starts to wonder if it's broken." — [clig.dev](https://clig.dev/)
- Next step: "Suggest commands the user should run. When several commands form a workflow, suggesting to the user commands they can run next helps them learn how to use your program and discover new functionality." — [clig.dev](https://clig.dev/)
- Defaults: "Make the default the right thing for most users."; "If it's not the default, you're making the experience worse for most of your users." — [clig.dev](https://clig.dev/)
- Subcommands: subcommands reduce complexity for a sufficiently complex tool; "Be consistent across subcommands."; "Don't have ambiguous or similarly-named commands." (example: "update" and "upgrade"); "Don't have a catch-all subcommand"; aliases "should be explicit and remain stable." — [clig.dev](https://clig.dev/)
- Prompts and danger: "Confirm before doing anything dangerous.", scaled by three levels (mild, moderate, severe); "Never require a prompt."; "Only use prompts or interactive elements if `stdin` is an interactive terminal (a TTY)."; `--no-input` disables prompts. — [clig.dev](https://clig.dev/)
- Responsiveness: "Responsive is more important than fast."; "Print something to the user in <100ms."; "Show progress if something takes a long time." — [clig.dev](https://clig.dev/)
- Stability: "Subcommands, arguments, flags, configuration files, environment variables: these are all interfaces, and you're committing to keeping them working."; "Keep changes additive where you can." — [clig.dev](https://clig.dev/)
- The page does not use the term "progressive disclosure". — [clig.dev](https://clig.dev/)

Progressive disclosure (Jakob Nielsen, Nielsen Norman Group, 3 December 2006; older source, still the standard definition):
- It "defers advanced or rarely used features to a secondary screen." "Initially, show users only a few of the most important options."; "Offer a larger set of specialized options upon request." It "improves 3 of usability's 5 components: learnability, efficiency of use, and error rate." The split must be right: everything frequently needed goes up front, and "the initial display can't contain confusing features". Designs beyond two levels "typically have low usability" because "users often get lost when moving between the levels." Staged disclosure (wizards) is the linear variant and becomes a problem when users must move back and forth between steps. — [NN/g](https://www.nngroup.com/articles/progressive-disclosure/)

git (porcelain versus plumbing):
- "We divide Git into high level ("porcelain") commands and low level ("plumbing") commands." The plumbing interfaces "are meant to be a lot more stable than Porcelain level commands, because these commands are primarily for scripted use. The interface to Porcelain commands on the other hand are subject to change in order to improve the end user experience." Internal helpers: "end users typically do not use them directly." — [git manual](https://git-scm.com/docs/git)
- `git help` with no arguments prints "the synopsis of the git command and a list of the most commonly used Git commands"; `--all` prints every command; `--guides` adds concept guides. — [git-help manual](https://git-scm.com/docs/git-help)
- The default list is introduced with "These are common Git commands used in various situations:" under five task headings: "start a working area", "work on the current change", "examine the history and state", "grow, mark and tweak your common history", "collaborate". — [git source: help.c](https://github.com/git/git/blob/master/help.c)
- Counts from git's command list on the master branch (counted by the page reader, November 2026): 24 commands carry a common-group tag and so appear in the default help (2 init, 4 worktree, 6 info, 9 history, 3 remote); 46 commands are classed main porcelain; 45 are plumbing manipulators or interrogators, with further sync and helper categories on top. — [git source: command-list.txt](https://github.com/git/git/blob/master/command-list.txt)
- The manual has a page titled "A useful minimum set of commands for Everyday Git" ("Everyday Git With 20 Commands Or So"); for a standalone developer it lists 12 commands as "essential for anybody who makes a commit". — [giteveryday](https://git-scm.com/docs/giteveryday)

gh (GitHub CLI):
- The manual groups commands under three headings: "Core commands" (12: auth, browse, codespace, discussion, gist, issue, org, pr, project, release, repo, skill), "GitHub Actions commands" (3: cache, run, workflow) and "Additional commands" (19, including alias, api, config, extension, search, secret, status). Counts by the page reader, November 2026. — [gh manual](https://cli.github.com/manual/gh)

cargo:
- The `cargo --help` template lists 16 commands (build, check, clean, doc, new, init, add, remove, run, test, bench, update, search, publish, install, uninstall) and ends with "See all commands with --list" and "See 'cargo help <command>' for more information on a specific command." — [cargo source: cli.rs](https://github.com/rust-lang/cargo/blob/master/src/bin/cargo/cli.rs)
- The full manual groups about 36 commands under Build, Manifest, Package, Publishing, Report and General headings, and third-party tools join as external subcommands. — [cargo manual](https://doc.rust-lang.org/cargo/commands/cargo.html)

uv:
- The documentation's features page groups commands by job: Python versions, Scripts, Projects (init, add, remove, sync, lock, run, tree, build, publish), Tools, "The pip interface", Utility. The pip interface is described as "intended to be used in legacy workflows or cases where the high-level commands do not provide enough control." — [uv docs: features](https://docs.astral.sh/uv/getting-started/features/)

Same principle stated by an agent vendor about enforced rules:
- "Whatever the scope, keep the enforced set small. Every hook and deny rule will occasionally fire when it shouldn't, and someone has to maintain each one." — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)

### Inferences
- The four tools show the same two-level pattern in three variants: (a) one binary, default help shows a curated subset and a flag lists everything (git 24 of well over 100, cargo 16 of about 36 plus external); (b) headed groups in help with the everyday group first (gh: 12 core, the rest under "Additional"); (c) a named lower-level namespace for control and legacy use (uv's `uv pip`, git plumbing). All stay within Nielsen's two levels.
- The everyday set people are expected to hold in their head is about a dozen even in git (giteveryday's 12 for a solo developer). A spec tool whose whole job is one workflow should sit well below that; the tools in question 1 expose three to six everyday commands (OpenSpec core: six, of which three form the main path) or one (BMAD Build).
- git's stability rule is a useful design constraint for a tool that agents and scripts also call: the human-facing commands may change to improve the experience, the machine-facing ones must stay stable. Separating the two lets the human surface stay small without breaking automation.
- For output, the guidance converges on four things per command: a brief success line, what changed (files written), the current state, and the next command to run; everything else behind a verbose flag. The "print something within 100 ms and show progress" rule matters more for model-backed commands, where a silent wait of minutes is normal.
- The same sources argue against hiding the main verb (no catch-all subcommand) and against look-alike command names, both relevant when collapsing several steps into one command.

### Gaps
- clig.dev gives no numeric guidance on how many commands is too many; no published guideline with a number was found.
- The root `--help` output of uv and gh was not captured directly (no local commands were run); the gh grouping is from the manual page and the uv grouping is from the docs features page, which may differ in detail from terminal output.
- Command counts for git, gh and cargo were produced by the page reader from the sources and may be off by one or two.
- Other style guides (Heroku CLI style guide, "12 Factor CLI Apps", Primer CLI guidelines) were not opened.

## 4. One pass with a single review versus step by step with a review after each artefact; where human review matters most

### Takeaway
No controlled comparison of one-pass planning against gated step-by-step planning was found. The available evidence is indirect but points one way: vendors that began with a gate after each artefact added or defaulted to one-pass generation with questions asked first, while first-hand reports say generation quality benefits from separate small steps inside the tool. So the supported pattern is staged generation, single human checkpoint. Practitioners place that checkpoint early, on intent and design (a short document of about 200 lines), and treat the task list as something to skim.

### Cited Findings

Evidence on one pass versus gated steps:
- [vendor behaviour, 2026] Kiro kept the gated flow but added a one-pass mode in May 2026 and describes the clarifying questions as "the key interaction point"; it recommends the gated flow where "review gates add value" (unfamiliar territory, requirements that need iteration, compliance-sensitive or high-stakes work). A reviewer notes the earlier Quick Spec asked about five questions. — [Kiro docs: Quick Spec](https://kiro.dev/docs/specs/quick-spec/); [DevelopersIO, 31 July 2026](https://dev.classmethod.jp/articles/kiro-cli-specnew-step/)
- [vendor behaviour, 2026] Kiro's one-pass artefacts stay individually editable with scoped regeneration: changing a task regenerates only tasks, changing the design rebuilds design and tasks, changing scope reruns the whole pipeline. — [Kiro blog, 12 May 2026](https://kiro.dev/blog/faster-smarter-specs/)
- [vendor behaviour, 2026] OpenSpec's default profile uses the one-step `/opsx:propose`; the artefact-by-artefact commands are opt-in. BMAD since v6.12.0 lets Build decide the amount of plan after investigation and asks for plan approval only on flagged designs. — [OpenSpec docs](https://github.com/Fission-AI/OpenSpec/blob/main/docs/commands.md); [BMAD CHANGELOG](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/CHANGELOG.md); [BMAD docs](https://docs.bmad-method.org/build/build-a-change/)
- [measured scoring, single evaluator, February 2026] (earlier notes) BMAD Quick (two steps, one document) scored 3.74 against 3.65 for the full multi-document method with the same elicitation quality. — [ranthebuilder.cloud](https://ranthebuilder.cloud/blog/i-tested-three-spec-driven-ai-tools-here-s-my-honest-take/)
- [first-hand, 2026 talk, via third-party summary] HumanLayer reports the opposite problem on the generation side: its single planning prompt carried 85+ instructions, and "about 50% of the time" agents skipped the design questions and wrote the full plan immediately. Its fix was to split the work into separate prompts of under 40 instructions each, each started in a fresh context, on the principle "don't use prompts for control flow if you can use control flow for control flow." The speaker cites research that frontier models reliably follow roughly 150 to 200 instructions. — [ZenML LLMOps Database](https://www.zenml.io/llmops-database/evolving-ai-coding-agent-workflows-from-research-plan-implement-to-crispy)
- [measured, small pilot, 10 September 2026] (earlier notes) Writing the spec and then implementing in a separate fresh step roughly doubled pass rate for a weak model (about 45% versus 23.8%, n = 4, p about 0.18, confounded by the second pass), while writing spec and code in a single prompt gave no gain. This concerns spec-then-code staging, not staging among planning artefacts. — [InfoQ](https://www.infoq.com/articles/when-spec-driven-development-pays-off/)
- [vendor docs] Two vendors advise restarting from the plan instead of patching by follow-up: Cursor says reverting, sharpening the plan and re-running is "often faster than fixing an in-progress agent, and produces cleaner results"; Claude Code says after two failed corrections to clear the session and write a better prompt. — [Cursor docs](https://cursor.com/docs/agent/plan-mode); [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)
- [academic, conceptual] A 2026 paper on spec-driven development for agent teams is a conceptual analysis of grey literature with no measurements; a 2026 course report found agent use "increased implementation throughput" but encouraged students to proceed "without fully understanding the code" (abstract only, sample size not seen). A study of 36,710 repositories found only 85 committed plan files in 10 repositories, most often containing implementation steps, concrete files and locations, and testing information. None compares one-pass with gated planning. — [arXiv 2609.00252](https://arxiv.org/abs/2609.00252); [arXiv 2608.30572](https://arxiv.org/abs/2608.30572); [arXiv 2608.04661](https://arxiv.org/abs/2608.04661)

Where practitioners say review matters most:
- [first-hand, August 2025] HumanLayer's original claim: "A bad line of code is… a bad line of code."; "But a bad line of a plan could lead to hundreds of bad lines of code."; "And a bad line of research... could land you with thousands of bad lines of code."; "When you review the research and the plans, you get more leverage than you do when you review the code."; "I can't read 2000 lines of golang daily. But I can read 200 lines of a well-written implementation plan." First-hand numbers: 35k lines shipped in 7 hours on a 300k-line Rust codebase (about 3 hours on research and plans, 4 on implementation). — [HumanLayer, ace-fca.md](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/ace-fca.md)
- [first-hand, 2026 revision, via third-party summary] After about six months the same team moved the main human checkpoint earlier and made it shorter: a design discussion document of about 200 lines (current state, desired end state, patterns, decisions, open questions), then a structure outline of about two pages; the detailed plan is spot-checked, and engineers read and own the code. The speaker reversed the earlier advice not to read generated code after having to replace parts of systems built without proper review. The "5x better leverage" figure for the 200-line document is the summariser's wording. — [ZenML LLMOps Database](https://www.zenml.io/llmops-database/evolving-ai-coding-agent-workflows-from-research-plan-implement-to-crispy)
- [snippet only] The speaker's revised position is quoted in search results as "Don't read the plans. Please read the code."; not found on the page that was opened. — [LinearB](https://linearb.io/blog/dex-horthy-humanlayer-rpi-methodology-ralph-loop)
- [opinion, 27 April 2026] Design is "the phase where the real architectural arguments should happen."; requirements "get reviewed and approved by a human before anything else happens."; the task list is not singled out. — [DoiT](https://www.doit.com/blog/spec-driven-development-with-kiro-ai-code-ownership)
- [vendor docs and claims] Kiro: clarifying questions are "the key interaction point". Cursor: "The hard part is often figuring out what change should be made." BMAD: "fixing the plan is cheaper than fixing the code." — [Kiro docs](https://kiro.dev/docs/specs/quick-spec/); [Cursor docs](https://cursor.com/docs/agent/plan-mode); [BMAD docs](https://docs.bmad-method.org/build/build-a-change/)
- [first-hand] A real catch at design level: "the design.md flagged a conflict between my proposed API contract" and existing behaviour (5 August 2026); requirements-level value: the spec process "forced me to think deeper about requirements" (18 December 2025). — [ricardogil.com](https://ricardogil.com/blog/kiro-review-spec-driven-agentic-ide); [petermcaree.com](https://petermcaree.com/posts/kiro-agentic-ide-hype-hope-and-hard-truths/)
- [measured, 13 observed developers and 99 surveyed, December 2025, revised August 2026] Experienced developers keep control of design and implementation and steer agents with their own expertise rather than delegating fully. — [arXiv 2512.14012](https://arxiv.org/abs/2512.14012)
- [measured pilot] (earlier notes) A retained spec baseline did not help reviewers find more defects (recall 0.525 versus 0.518) but made findings attributable to a requirement (0.81 versus 0.00) at nearly double the review time. — [InfoQ](https://www.infoq.com/articles/when-spec-driven-development-pays-off/)

### Inferences
- Two different questions are often merged: how many steps the tool takes internally, and how many times it stops for the human. The evidence supports many small internal steps (HumanLayer's instruction-budget finding, the InfoQ staging result, fresh context per stage) and few human stops (Kiro, OpenSpec, BMAD all moving that way). One command can run a staged pipeline and present one combined review.
- The human checkpoint with the most support is early and short: answers to clarifying questions plus a brief statement of intent and design decisions. Evidence that reviewing a long task list or detailed plan pays off is absent, and one team that tried it at scale abandoned it.
- A single review after one-pass generation is only safe if a wrong early answer is cheap to correct. Kiro's scoped regeneration (edit one artefact, regenerate only what depends on it) is the mechanism that makes one pass acceptable; without it, one pass turns a requirements mistake into three wrong documents.
- A gate is worth its cost when it is tied to a risk signal (irreversible action, large footprint, intent gap, compliance), which is how BMAD Build and Kiro's guidance now decide. An unconditional gate after every artefact is the design the vendors moved away from.
- Front-loaded questions are themselves a cost: Kiro later let the description replace the question sequence in its CLI. A small fixed number of questions, skipped when the request is clear, matches where BMAD and Kiro ended up.

### Gaps
- No controlled or repeated-run comparison of one-pass versus gated planning exists in what was found; everything is vendor behaviour, single-team experience or small pilots.
- The HumanLayer revision was read only through a third-party summary of a talk; the original talk and its date were not verified.
- No source isolates the value of reviewing the task list specifically.
- Kiro has published no data on how often users choose Quick Spec over the gated flow, or on defect rates for each.

## 5. How tools that verify or gate keep those steps from feeling like extra ceremony

### Takeaway
Three techniques recur: make verification automatic and run by a different agent or a deterministic check, so the human sees only exceptions; fold approval into an action the user takes anyway (approving the plan starts the build, archiving runs the completeness check, merging the pull request is the final sign-off); and reserve separate human steps for the few irreversible or high-risk points. Where a verify step is a separate advisory command, practitioners skip it.

### Cited Findings

Automatic (the human sees exceptions only):
- [vendor docs] BMAD `bmad-build` runs review by independent reviewers and triages the findings itself inside the same session, fixes problems in the current change, defers unrelated pre-existing issues, and regenerates from the plan if the plan was the fault; v6.11.0 added an intent-alignment auditor to the unattended variant and removed the manual acceptance-criteria checkbox step. The user can tell it to skip review. — [BMAD docs](https://docs.bmad-method.org/build/build-a-change/); [BMAD CHANGELOG](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/CHANGELOG.md)
- [measured scoring] (earlier notes) BMAD's adversarial review "caught issues a standard review would miss", and only the BMAD flows added a missing permission check. — [ranthebuilder.cloud](https://ranthebuilder.cloud/blog/i-tested-three-spec-driven-ai-tools-here-s-my-honest-take/)
- [vendor docs] Kiro's Bugfix Spec generates property-based tests for the bug, the fix and the unchanged behaviour as ordinary tasks, so regression checking is part of implementation, not a later step. "Analyze Requirements" is optional and uses automated reasoning to find contradictions, ambiguities and gaps "that are hard to catch in a read-through." — [Kiro docs: Bugfix Specs](https://kiro.dev/docs/specs/bugfix-specs/); [Kiro changelog 0.12](https://kiro.dev/changelog/ide/0-12/)
- [vendor measurement, 10 November 2026] Kiro "Approve for me": permission rules apply first, an LLM reviewer handles the rest; "Kiro auto-approves the routine ones, blocks ones it judges unsafe, and asks you when it isn't sure." In one week of internal use about 70% of actions were settled by rules and about 30% went to LLM review, of which about 97% were auto-approved, about 2% went to the user and under 1% were blocked; median review under a second; after three consecutive blocks it returns to asking. Off by default, paid plans. — [Kiro blog](https://kiro.dev/blog/introducing-approve-for-me/)
- [vendor measurement, 25 March 2026] Claude Code auto mode: read-only tools and in-project file edits run without a classifier call; everything else goes to a two-stage classifier. Evaluated on about 10,000 real internal tool calls: 0.4% of benign actions blocked; 17% of 52 real overeager actions missed ("The 17% false-negative rate on real overeager actions is the honest number."); 5.7% of 1,000 synthetic exfiltration attempts missed. After 3 consecutive or 20 total denials it escalates to the human. "It is not a drop-in replacement for careful human review on high-stakes infrastructure." — [Anthropic engineering](https://www.anthropic.com/engineering/claude-code-auto-mode)
- [vendor docs] Claude Code frames verification as a check the agent runs itself: "Give Claude something it can run that comes back pass or fail. Once it has that, it can keep going on its own and you don't have to watch." Enforcement levels run from a line in the prompt, to a goal condition checked by a separate model, to a Stop hook that blocks the turn from ending, to a review "in a fresh subagent that never saw your conversation." It advises asking for evidence ("the command it ran and its output") and warns that a reviewer told to find problems "will always find something", so the review prompt should exclude style. — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)

### Inferences
- Verification that depends on the user remembering to run a separate, non-blocking command is the pattern with first-hand evidence of failure (OpenSpec sync and verify). Verification that runs inside the implementing command, or as a side effect of the closing command, has no such reports.
- The stable division of labour across tools is: machine-run checks and an independent reviewer agent during the build; one human decision before code (plan or intent) only when risk warrants; one human decision at the end where the result becomes hard to undo (merge, archive into the durable spec). Everything else is automatic or reported as an exception.
- Classifier-based approval removes about 97% of prompts but misses a measurable share of bad actions (17% in Anthropic's own evaluation). Automatic gating reduces ceremony; it does not replace the final human sign-off, and both vendors say so.
- For a command-line spec tool this argues for verification as part of `apply` (or its equivalent) with a pass or fail result and evidence printed, the completeness and drift check as part of the closing command and blocking only on critical findings, and at most one explicit approval, which also starts the next step.

### Gaps
- No measurement was found of how often users run optional verify or analyse steps (OpenSpec verify, Kiro Analyze Requirements) when they are separate.
- Independent evaluations of Kiro's property-based tests, of BMAD's reviewer lenses after v6.11, and of Kiro's "Approve for me" were not found; the figures are vendor-reported.
- No evidence was found comparing a blocking verify step with an advisory one on defect rates or on user drop-off.
