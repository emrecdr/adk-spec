## 1. What is the canonical command order today, which commands are strictly required, and what does the README's minimal flow list? Counts (required, typical, full)

### Takeaway
Status: answered from primary sources. One feature costs 5 chat commands on the documented "shorter path" (specify, plan, tasks, implement, converge) and 8 on the "full path" (adding clarify, checklist, analyze), plus a one-time constitution; the helper scripts hard-enforce only the 4-command chain specify, plan, tasks, implement. Loops raise the real number of invocations: the README tells users to repeat implement and converge until converge reports `Converged`.

### Cited Findings
- Canonical order, nine commands: `/speckit.constitution -> /speckit.specify -> /speckit.clarify -> /speckit.plan -> /speckit.checklist -> /speckit.tasks -> /speckit.analyze -> /speckit.implement -> /speckit.converge`. — [docs/reference/agentic-sdd.md](https://github.com/github/spec-kit/blob/main/docs/reference/agentic-sdd.md)
- What the docs call required: "The commands are designed to run in order, but only `/speckit.specify` is strictly required before `/speckit.plan`. The clarify, checklist, and analyze commands are quality gates you add for anything with meaningful ambiguity." — [docs/reference/agentic-sdd.md](https://github.com/github/spec-kit/blob/main/docs/reference/agentic-sdd.md)
- README minimal flow, six lines in Copilot skills syntax: `/speckit-constitution`, `/speckit-specify`, `/speckit-plan`, `/speckit-tasks`, `/speckit-implement`, `/speckit-converge`. "Create a constitution once per project and repeat the remaining steps for each feature. Run these skills in your agent's chat, not your terminal, one at a time, reviewing each result before continuing." "Repeat implement and converge until convergence reports `Converged`. For clarification, checklists, and consistency analysis, see the SDD walkthrough." — [README.md](https://github.com/github/spec-kit/blob/main/README.md)
- Quickstart names two paths. "**Shorter path** — for smaller features": specify, plan, tasks, implement, converge (5). "**Full path** — for production features, adding `/speckit-clarify`, `/speckit-checklist`, and `/speckit-analyze` as quality gates": constitution (once per project), specify, clarify, plan, checklist, tasks, analyze, implement, converge (9 listed, 8 per feature). "Establish a constitution once per project with `/speckit-constitution` before starting either path." — [docs/quickstart.md](https://github.com/github/spec-kit/blob/main/docs/quickstart.md)
- What the scripts actually enforce (earlier notes, section 3): `setup-tasks` hard-fails if `plan.md` or `spec.md` is missing; implement, analyze and converge require `tasks.md`; checklist fails with "plan.md not found" before a plan exists. Nothing checks that clarify, checklist, analyze or converge were run. — [scripts/bash/setup-tasks.sh](https://github.com/github/spec-kit/blob/main/scripts/bash/setup-tasks.sh); [scripts/bash/check-prerequisites.sh](https://github.com/github/spec-kit/blob/main/scripts/bash/check-prerequisites.sh)
- Loops that add invocations: clarify "Run it as many times as needed before planning"; analyze "re-run `/speckit.analyze` until it comes back clean"; implement "For a large feature, work in stages ... scope each run with an argument"; converge "Each pass finds fewer items; repeat until it reports converged." — [docs/reference/agentic-sdd.md](https://github.com/github/spec-kit/blob/main/docs/reference/agentic-sdd.md)
- The existing-project guide lists a third variant: constitution, specify, clarify, plan, tasks, analyze, implement, converge (8, no checklist). — [docs/how-to/existing-projects.md](https://github.com/github/spec-kit/blob/main/docs/how-to/existing-projects.md)
- A single terminal command can run part of the chain: the bundled `speckit` workflow ("Full SDD Cycle", version 1.0.2, "Runs specify → plan → tasks → implement with review gates") has steps `specify` → gate `review-spec` → `plan` → gate `review-plan` → `tasks` → `implement`; gates offer `approve` or `reject` with `on_reject: abort`. It contains no constitution, clarify, checklist, analyze or converge step, and it passes the same `{{ inputs.spec }}` text as the arguments of all four commands. — [workflows/speckit/workflow.yml](https://github.com/github/spec-kit/blob/main/workflows/speckit/workflow.yml)
- The other two first-party processes are separate entry points with their own counts: bug fixing is 3 commands (`/speckit-bug-assess`, `-fix`, `-test`) and idea assessment is 5 (`-intake`, `-research`, `-define`, `-shape`, `-decide`); "These are independent entry points, not mandatory phases." Each needs `specify extension add bug` or `assess` first. — [README.md](https://github.com/github/spec-kit/blob/main/README.md)
- Whole first-party command surface if every bundled extension is installed (earlier notes, section 3): 9 core commands plus git (5: feature, validate, remote, initialize, commit), agent-context (1), bug (3), assess (5), github (1: taskstoissues). — [extensions/](https://github.com/github/spec-kit/tree/main/extensions)
- Users and reviewers count the flow differently, which shows the number is not obvious: "current 6-step workflow (`constitution → specify → clarify → plan → tasks → implement`)" (May 2026), "seven manual slash-command steps" (May 2026), "a ninth step" for converge (project newsletter, June 2026). — [issue #2673](https://github.com/github/spec-kit/issues/2673); [issue #2625](https://github.com/github/spec-kit/issues/2625); [newsletters/2026-June.md](https://github.com/github/spec-kit/blob/main/newsletters/2026-June.md)

### Inferences
- Counts for one feature, excluding the one-time constitution: hard-enforced minimum 4 (specify, plan, tasks, implement); documented minimum 5 (adds converge); full 8. Counting the first feature in a new project adds 1 (constitution) and one terminal command (`specify init`). A realistic full run with one clarify, one analyze re-run and one converge loop is about 11 invocations (my arithmetic: 8 + 1 analyze re-run + 1 implement + 1 converge).
- Converge has an odd status: it is in the README's minimal flow and is not labelled optional in the command table, yet nothing depends on it and the bundled workflow leaves it out. Treat it as "recommended, not enforced".
- The docs' sentence that only specify is strictly required before plan understates the script preconditions (tasks needs plan and spec; implement needs tasks). The honest minimum is a 4-step chain.
- The project already has a one-command path (`specify workflow run speckit`), but it runs in the terminal, needs an agent CLI, and covers 4 of the 9 steps, so the chat flow remains command-by-command.

### Gaps
- Not checked: whether `specify init` prints a "next steps" list and what it contains today (the changelog shows such a list exists: "fix(init): show hyphenated /speckit-<name> in Next Steps for Forge projects (#3642)").
- No telemetry or survey on how many commands users really run per feature was found; the counts above are documentation counts.

## 2. What does each command write (how many files, roughly how long), where is a human expected to review, and which steps are pure quality gates?

### Takeaway
Status: file list and review guidance answered from primary sources; measured output volume rests on the earlier local notes plus tracker reports read in this round. The shorter path leaves 7 Markdown files plus a `contracts/` folder per feature (the plan command alone writes four files and a folder), a human is told to review after every command, and three commands (clarify, checklist, analyze) are documented as optional quality gates, while converge is a fourth check that is recommended but not enforced.

### Cited Findings
- Per-command output, from the docs and prompts (file list from the earlier notes, sections 2 and 3, re-checked against the reference page):
  - constitution: one file, `.specify/memory/constitution.md`; run "once up front and update it whenever your principles change".
  - specify: `spec.md`, the built-in `checklists/requirements.md`, and the pointer `.specify/feature.json`; at most three clarification questions.
  - clarify: no new file; "Asks up to five targeted questions ... and encodes your answers back into `spec.md`".
  - plan: `plan.md`, `research.md`, `data-model.md`, `quickstart.md`, `contracts/`.
  - checklist: one `checklists/<domain>.md` per run or domain, reviewer-owned.
  - tasks: `tasks.md`.
  - analyze: no file; "It never edits files — it produces a report".
  - implement: code, task check-offs in `tasks.md`.
  - converge: "its only possible write is adding tasks to `tasks.md`".
  — [docs/reference/agentic-sdd.md](https://github.com/github/spec-kit/blob/main/docs/reference/agentic-sdd.md); [templates/plan-template.md](https://github.com/github/spec-kit/blob/main/templates/plan-template.md); [templates/commands/specify.md](https://github.com/github/spec-kit/blob/main/templates/commands/specify.md)
- Template and prompt sizes measured in the local clone (line counts): templates spec 131, plan 113, tasks 252, checklist 45, constitution 50; command prompts analyze 275, checklist 379, clarify 291, constitution 179, converge 279, implement 222, plan 170, specify 349, tasks 224 (2,368 lines for the nine prompts). — [templates/](https://github.com/github/spec-kit/tree/main/templates); [templates/commands/](https://github.com/github/spec-kit/tree/main/templates/commands)
- Prompt size in tokens, two first-hand measurements: about 18.6k tokens for nine commands in Claude Code's `/context` (December 2025: checklist 4.2k, specify 3.1k, implement 3.1k, clarify 2.8k, analyze 1.8k, tasks 1.5k, constitution 1.2k, plan 690, taskstoissues 218); 23,703 tokens for nine templates with the o200k_base tokenizer (June 2026: checklist 4,460, specify 3,824, clarify 3,638, implement 2,810, tasks 2,326, analyze 2,282, constitution 1,764, plan 1,635, taskstoissues 964). — [issue #1401](https://github.com/github/spec-kit/issues/1401); [issue #2943](https://github.com/github/spec-kit/issues/2943)
- Measured output volume, first-hand, from the earlier notes (critique file, section 2): 2,577 lines of Markdown for 689 lines of code and about 3.5 hours of review for one feature, with the plan phase alone about 2,030 lines across five documents; a second small increment 2,262 lines of Markdown for about 300 lines of code (Scott Logic, November 2025); 8 files in one spec folder (Thoughtworks author on martinfowler.com, October 2025); 8 files and about 1,300 lines for a feature that displays the current date (Marmelab, November 2025). — [Scott Logic](https://blog.scottlogic.com/2025/11/26/putting-spec-kit-through-its-paces-radical-idea-or-reinvented-waterfall.html); [martinfowler.com](https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html); [Marmelab](https://marmelab.com/blog/2025/11/12/spec-driven-development-waterfall-strikes-back)
- Output volume reported by users on the tracker (first-hand, read this round): adding one button gave "30 files changed, < 20 actual LOC"; a "delete project" capability "generated 35 tasks in 3 phases! I was expecting ~10 tasks in one phase"; "Spec kit genrated 4 lines of doc for every actual code". — [issue #1174](https://github.com/github/spec-kit/issues/1174)
- Task counts in 2026 field reports (page-reader summaries): 129 tasks in seven phases for a greenfield Go app on Spec Kit 1.0.8 (September 2026); 50 tasks plus 2 convergence tasks for one .NET feature (June 2026). — [tauceti.blog](https://www.tauceti.blog/posts/spec-driven-development-with-spec-kit/); [achrafbenalaya.com](https://achrafbenalaya.com/2026/06/28/i-tried-github-spec-kit-an-honest-field-report/)
- Spec size does not track change size: a user reports `spec.md` "almost always lands somewhere around 13–20 functional requirements" regardless of scope (May 2026); the maintainer replied that the specify command gives no guidance on how many requirements to generate, suggested a local preset that prepends sizing guidance ("Prefer fewer precise requirements over many thin ones."), and asked for test results before deciding whether it belongs in core. — [discussion #2738](https://github.com/github/spec-kit/discussions/2738)
- Where a human is told to review: after every command ("one at a time, reviewing each result before continuing"; "Invoke each `/speckit-*` skill separately in your agent's chat and review the result before moving to the next step"); on plan, "verify that the proposed design reuses the existing architecture, dependencies, and test conventions"; on implement, "review code and artifact changes together"; on a converged result, "proceed to review or open a PR". — [README.md](https://github.com/github/spec-kit/blob/main/README.md); [docs/quickstart.md](https://github.com/github/spec-kit/blob/main/docs/quickstart.md); [docs/how-to/existing-projects.md](https://github.com/github/spec-kit/blob/main/docs/how-to/existing-projects.md)
- The only artifacts a human must act on, not just read: custom checklists ("mark an item `[x]` only when the reviewer determines that requirement-quality criterion is satisfied"), which implement then reads as a gate and "asks before proceeding if any checklist items are unchecked". In the terminal workflow the two human points are the `review-spec` and `review-plan` gates. — [docs/quickstart.md](https://github.com/github/spec-kit/blob/main/docs/quickstart.md); [workflows/speckit/workflow.yml](https://github.com/github/spec-kit/blob/main/workflows/speckit/workflow.yml)
- Which steps are gates and whether they are optional: the command table labels clarify "(optional quality gate; formerly `/quizme`)", analyze "(optional quality gate)" and checklist "(optional quality gate)". Converge is described as an assessment ("Assess implementation against the artifacts and append remaining work") without the word optional. — [docs/reference/agentic-sdd.md](https://github.com/github/spec-kit/blob/main/docs/reference/agentic-sdd.md)
- Fresh sessions between stages are supported: the maintainer says "Starting a fresh session between `specify`, `plan`, `tasks`, and `implement` is therefore perfectly valid." (September 2026). — [discussion #4655](https://github.com/github/spec-kit/discussions/4655)

### Inferences
- Minimum durable output for one feature on the shorter path is 7 files plus contracts (spec, requirements checklist, plan, research, data-model, quickstart, tasks). Most of the volume and most of the review time comes from the plan command, which is one command but five artifacts.
- The four checking steps differ in kind: clarify is an interview that edits the spec, checklist produces a human-owned file, analyze and converge are agent-run audits (one before coding, one after). A simpler tool could fold analyze into tasks and converge into implement without losing a human decision, because neither asks the human for anything except to read a report.
- The docs put a human review after each of 5 to 8 commands; the measurements in the earlier notes show that this review, not agent time, dominates cost.

### Gaps
- No measurement of generated Markdown per feature for Spec Kit 1.x was found; all line counts are from late 2025 versions or from users' rough reports.
- I did not run the tool, so the file list comes from prompts and docs, not from an observed run.

## 3. What exactly does the `lean` preset replace, how many commands remain with it, and why does it exist?

### Takeaway
Status: answered from primary sources. `lean` is a bundled, opt-in preset (since v0.6.1, 2026-04-10) that swaps five core prompts (specify, plan, tasks, implement, constitution) for 19 to 33 line prompts that each write exactly one artifact, with no hooks, scripts, templates, validation loops or sibling design files; the pipeline it describes is 4 commands per feature, and the other four core commands stay installed unchanged. The project's stated reason was that core prompts carry "significant boilerplate" and users who wanted "just create the artifact" had no built-in option.

### Cited Findings
- What it replaces: `preset.yml` lists five `type: "command"` entries, each with `replaces:` set to `speckit.specify`, `speckit.plan`, `speckit.tasks`, `speckit.implement`, `speckit.constitution`. Preset version 1.0.0, `requires: speckit_version: ">=0.6.0"`, description "Minimal core workflow commands - just the prompt, just the artifact". — [presets/lean/preset.yml](https://github.com/github/spec-kit/blob/main/presets/lean/preset.yml)
- Its own description: "Use Lean when you want the structured specify → plan → tasks → implement pipeline without the ceremony of the full templates. Each command produces a single focused Markdown file with no boilerplate sections to fill in." "Lean overrides the five core workflow commands with self-contained prompts that produce each artifact directly — no separate template files involved." Outputs: `spec.md`, `plan.md`, `tasks.md`, code, `constitution.md`. — [presets/lean/README.md](https://github.com/github/spec-kit/blob/main/presets/lean/README.md)
- Size, measured in the local clone: lean prompts are 23 (specify), 19 (plan), 19 (tasks), 22 (implement) and 33 (constitution) lines, 116 in total, against 349, 170, 224, 222 and 179 lines (1,144 in total) for the five core prompts they replace. — [presets/lean/commands/](https://github.com/github/spec-kit/tree/main/presets/lean/commands); [templates/commands/](https://github.com/github/spec-kit/tree/main/templates/commands)
- Lean specify, in full: "**Ask the user** for the feature directory path (e.g., `specs/my-feature`). Do not proceed until provided."; write `.specify/feature.json`; write `spec.md` with "Overview, functional requirements, user scenarios, success criteria", "Every requirement must be testable", "Make informed defaults for unspecified details". There is no quality checklist, no numbering logic and no clarification question. — [presets/lean/commands/speckit.specify.md](https://github.com/github/spec-kit/blob/main/presets/lean/commands/speckit.specify.md)
- Lean plan writes only `plan.md` ("Technical context: tech stack, dependencies, project structure"; "Design decisions, architecture, file structure"), so no `research.md`, `data-model.md`, `quickstart.md` or `contracts/`. Lean tasks writes `tasks.md` with "`- [ ] [TaskID] Description with file path`" lines "Organized by phase: setup, foundational, user stories in priority order, polish". Lean implement executes tasks in order, marks them `[x]`, "Halt on failure and report the issue", then "Verify all tasks are completed and the implementation matches the spec"; it has no checklist gate. — [presets/lean/commands/speckit.plan.md](https://github.com/github/spec-kit/blob/main/presets/lean/commands/speckit.plan.md); [presets/lean/commands/speckit.tasks.md](https://github.com/github/spec-kit/blob/main/presets/lean/commands/speckit.tasks.md); [presets/lean/commands/speckit.implement.md](https://github.com/github/spec-kit/blob/main/presets/lean/commands/speckit.implement.md)
- Lean constitution keeps the scope guard (it must not run feature work) and its outline is one step: "Create or update the project constitution ... Project name, guiding principles, non-negotiable rules. Derive from user input and existing repo context (README, docs)". — [presets/lean/commands/speckit.constitution.md](https://github.com/github/spec-kit/blob/main/presets/lean/commands/speckit.constitution.md)
- Why it exists, from the pull request that added it (by the lead maintainer, merged 2026-04-10): "The core commands include significant boilerplate: extension hooks, script dependencies, git branching, template resolution, validation loops, and multi-artifact generation. Users wanting a simpler "just create the artifact" workflow had no built-in option." "Each produces exactly one artifact — no hooks, no scripts, no git branching, no templates". It was tested end to end as "specify → plan → tasks → implement producing a working Spring Boot MVC app". — [PR #2161](https://github.com/github/spec-kit/pull/2161)
- How the project described it afterwards: "a lighter-weight alternative to the full SDD ceremony"; the lean preset and other changes "reflect ongoing work to reduce ceremony and improve the onboarding experience. Multiple external articles (Torber, XB Software) noted SDD overhead as a barrier." — [newsletters/2026-April.md](https://github.com/github/spec-kit/blob/main/newsletters/2026-April.md)
- The maintainer's caveat (2026-09-24): "The bundled `lean` preset provides a separate, opt-in reduction across skills-based and command-based integrations. It shortens five core workflows **when invoked** ... Its simplified prompts omit some core scripts and hooks, so it is not a behavior-equivalent replacement for the full workflow." — [issue #1401](https://github.com/github/spec-kit/issues/1401)
- Positioning in current docs: the project "ships the `lean` preset to demonstrate an alternative way of shaping core SDD guidance". Install with `specify preset add lean` (bundled, no download) or at init with `--preset lean`. — [docs/guides/agentic-sdlc.md](https://github.com/github/spec-kit/blob/main/docs/guides/agentic-sdlc.md); [presets/lean/README.md](https://github.com/github/spec-kit/blob/main/presets/lean/README.md); [PR #2161](https://github.com/github/spec-kit/pull/2161)
- Discoverability: a search of the local clone finds `lean` named only in the preset's own files, the preset catalog, `docs/presets/overview.md` (as the example in `specify preset info lean` / `add lean` / `remove lean`) and `docs/guides/agentic-sdlc.md`; the README and the quickstart do not mention it. The project's newsletter concedes that "discoverability of these options remains an opportunity" (May 2026). — [docs/presets/overview.md](https://github.com/github/spec-kit/blob/main/docs/presets/overview.md); [newsletters/2026-May.md](https://github.com/github/spec-kit/blob/main/newsletters/2026-May.md)
- Unverified external measurement (title only, page returned HTTP 403): a Medium post of 2026-09-13 is titled "GitHub Spec Kit Ships an 18,799-Token Workflow. One Preset Collapses It to 863", described by the project newsletter as measured against the bundled `lean` preset. — [newsletters/2026-September.md](https://github.com/github/spec-kit/blob/main/newsletters/2026-September.md)

### Inferences
- With lean the per-feature flow is 4 commands and 3 files (spec, plan, tasks), down from 5 commands and 7 or more files. Lean does not remove clarify, checklist, analyze or converge: presets replace named commands, and only five are named, so the other four core commands remain installed in full form. A lean project therefore still shows 9 commands in the agent's list.
- Lean cuts prompt text by about 90 percent (116 versus 1,144 lines) but does it by dropping guardrails wholesale (precondition scripts, the spec self-check, the three-question limit, the checklist gate), not by merging steps. It is "same number of main steps, each much thinner".
- Lean adds one interaction that the core flow does not have: the user must type a feature directory path, because deterministic numbering was removed with the scripts.
- The project treats lean as a demonstration of the preset mechanism rather than as the recommended small-change path; it is absent from the README and quickstart, where the "shorter path" is still the 5 full-size commands.

### Gaps
- Not verified: whether the unchanged core clarify, checklist, analyze and converge commands work correctly on lean-shaped artifacts.
- No usage numbers for the lean preset were found.
- The Medium token measurement could not be opened.

## 4. How did the command set grow from "Specify, Plan, Tasks, Implement" to today's list, what reasons were given, and was anything merged or removed to simplify?

### Takeaway
Status: dates answered from commit history and the changelog; reasons found for implement, converge, lean, the git extraction and the taskstoissues removal; reasons for constitution, clarify, analyze and checklist were not found. Core grew from 3 command files (August 2025) to 9 within two months, reached 10 with converge (June 2026) and is back to 9 after taskstoissues was moved to an extension (November 2026). Nothing in core was ever merged to shorten the flow: every request for a shorter or single-command path was redirected to an extension, a preset, the workflow engine or documentation.

## 5. What is the documented path for an existing project: exact steps, what init does and does not do, and constitution guidance?

### Takeaway
Status: answered from the primary doc read in this round; init internals from the earlier local notes. The documented path is one terminal command (`specify init --here --force --integration <key>` on a branch), a constitution written from rules that are already true, and then the normal per-feature flow on one bounded change; init adds only Spec Kit's own files and "does not rewrite your application or infer specifications for existing behavior".

### Cited Findings
- Opening position: "You do not need to recreate an existing system from specifications before using Spec Kit. Initialize the repository in place, capture the rules that matter, and use the workflow for the next bounded change." — [docs/how-to/existing-projects.md](https://github.com/github/spec-kit/blob/main/docs/how-to/existing-projects.md)
- Step 1, "Start from a Reviewable Baseline": "commit or stash existing work and create a branch for the adoption", then from the repository root run `specify init --here --force --integration <key>`. "`--force` allows initialization in a non-empty directory and may replace files at conflicting managed paths, so use it only after creating a reviewable baseline. It does not delete the rest of your application." "Review the resulting diff before continuing." — [docs/how-to/existing-projects.md](https://github.com/github/spec-kit/blob/main/docs/how-to/existing-projects.md)
- What init does and does not do: "Initialization adds the shared `.specify/` project files and the command or skill files required by your selected integration. It does not rewrite your application or infer specifications for existing behavior." Git is untouched: "Git initialization and feature branches are optional and are managed by the **git** extension." — [docs/how-to/existing-projects.md](https://github.com/github/spec-kit/blob/main/docs/how-to/existing-projects.md)
- Init details from the earlier notes (section 2): an existing `.specify/memory/constitution.md` is preserved; a hash manifest lets later upgrades overwrite untouched managed files and keep edited ones. — [src/specify_cli/command_init.py](https://github.com/github/spec-kit/blob/main/src/specify_cli/command_init.py); [src/specify_cli/shared_infra.py](https://github.com/github/spec-kit/blob/main/src/specify_cli/shared_infra.py)
- Step 2, "Capture Project Guardrails": "Run `/speckit-constitution` with principles that are already true for the repository or that the team has explicitly agreed to adopt". Example: "Preserve public API compatibility. Follow the existing service boundaries. Every database migration must include a rollback plan. Run the repository's established unit and integration test suites." "Use the repository's README, architecture decisions, contribution guide, and CI configuration as evidence. Do not invent standards merely to fill the constitution template. The constitution governs later planning and analysis, so unrealistic rules create noise instead of useful constraints." — [docs/how-to/existing-projects.md](https://github.com/github/spec-kit/blob/main/docs/how-to/existing-projects.md)
- Step 3, "Choose a Bounded First Change": "Start with a feature or modernization slice that can be reviewed independently. Do not make "document the entire existing system" your first feature unless that inventory is itself the intended deliverable." The specify prompt should state "both the requested outcome and the compatibility boundaries that must remain intact". "The codebase remains implementation context. The new `spec.md` defines the change you intend to make, not a retroactive specification of every existing behavior." — [docs/how-to/existing-projects.md](https://github.com/github/spec-kit/blob/main/docs/how-to/existing-projects.md)
- Step 4, "Plan Against the Repository": clarify ("to resolve uncertain behavior and compatibility requirements"), plan ("verify that the proposed design reuses the existing architecture, dependencies, and test conventions"), tasks then analyze, implement ("review code and artifact changes together"), converge ("If it adds tasks, repeat implementation and convergence until the feature is complete"). — [docs/how-to/existing-projects.md](https://github.com/github/spec-kit/blob/main/docs/how-to/existing-projects.md)
- Step 5, "Decide How Specs Will Age": agree what feature artifacts to keep, "including retiring completed feature artifacts under the constitution-only model". — [docs/how-to/existing-projects.md](https://github.com/github/spec-kit/blob/main/docs/how-to/existing-projects.md)
- The SDD steps are not mandatory in an existing repository: "If your first task is a repair, you can instead follow the bug-fixing quickstart after initialization; to evaluate a proposal, use the idea assessment quickstart. Neither process requires completing the SDD steps below first." — [docs/how-to/existing-projects.md](https://github.com/github/spec-kit/blob/main/docs/how-to/existing-projects.md)
- Understanding the existing code is left to the agent and to community add-ons: "Community extensions for architecture discovery and brownfield bootstrapping are listed in the extension catalog." The maintainer's own brownfield demos extend a roughly 307,000-line .NET CMS and a roughly 420,000-line Java runtime with 180 Maven modules "with no prior specs or constitution". — [docs/how-to/existing-projects.md](https://github.com/github/spec-kit/blob/main/docs/how-to/existing-projects.md); [docs/community/walkthroughs.md](https://github.com/github/spec-kit/blob/main/docs/community/walkthroughs.md)
- The lean constitution prompt is the only first-party prompt that tells the agent to read the repository for it: "Derive from user input and existing repo context (README, docs)". — [presets/lean/commands/speckit.constitution.md](https://github.com/github/spec-kit/blob/main/presets/lean/commands/speckit.constitution.md)
- Demand signals, from the earlier notes (section 9): "Reverse Engineering Command" proposing spec, plan and tasks from existing code (38 thumbs-up), "How to use it for existing project" (24), discussion "Recommended approach for brownfield development" (17 upvotes, unanswered). A community "Brownfield Bootstrap" extension proposal drew 23 thumbs-up and was added to the community catalog in April 2026. — [issue #264](https://github.com/github/spec-kit/issues/264); [issue #164](https://github.com/github/spec-kit/issues/164); [discussion #331](https://github.com/github/spec-kit/discussions/331); [issue #1436](https://github.com/github/spec-kit/issues/1436); [newsletters/2026-April.md](https://github.com/github/spec-kit/blob/main/newsletters/2026-April.md)

### Inferences
- First feature in an existing repository, as documented: 1 terminal command plus 8 chat commands (constitution, specify, clarify, plan, tasks, analyze, implement, converge). The brownfield guide is heavier than the README's minimal flow: it writes clarify and analyze into the numbered steps.
- Core has no "understand this repository" step. The constitution is written by the user from evidence they gather, and nothing scans the code, so the quality of brownfield output depends on the agent reading code during plan. The demos' "no prior specs or constitution" claim shows the constitution is optional in practice even though the guide makes it step 2.
- The guidance worth copying is the framing: adopt in place, capture only true rules, spec the next bounded change, never start with "document everything".

### Gaps
- The guide's claims were not tested; I did not run init in a repository.
- Which community brownfield extensions exist today and what they do was not examined.

## 6. How do the commands appear to a GitHub Copilot user (skills by default since August 2026): invocation and documented friction?

### Takeaway
Status: documentation answered from primary sources; user-reported friction only partly reached. A Copilot user gets nine skills under `.github/skills/speckit-<command>/SKILL.md`, typed in chat as `/speckit-specify` and so on (hyphen, where the reference docs use a dot), each of which the model may also invoke on its own unless an opt-out flag is set. Documented friction is mostly about that model invocation, mixed layouts after upgrades, and spelling; field evidence on Copilot specifically is thin.

### Cited Findings
- Layout and invocation: "Skills are installed as `.github/skills/speckit-<command>/SKILL.md`. Invoke them in the agent's chat as `/speckit-specify` or `/speckit-bug-assess` for the installed bug extension. These are agent skills, not terminal commands. Generated skills are both user- and model-invocable by default." — [docs/integrations/copilot.md](https://github.com/github/spec-kit/blob/main/docs/integrations/copilot.md)
- When it became the default: "feat(copilot): default integration to skills (#3976)" in v0.16.0 (2026-08-05); the pull request keeps "the commands layout supported through `--integration-options="--commands"`" and "preserves historical command-layout projects during use and upgrade". — [CHANGELOG.md](https://github.com/github/spec-kit/blob/main/CHANGELOG.md); [PR #3976](https://github.com/github/spec-kit/pull/3976)
- The older layout, still available: `.agent.md` files under `.github/agents/`, companion `.prompt.md` files under `.github/prompts/`, and a merge into `.vscode/settings.json`; "Without an explicit layout flag, existing managed command installations retain their layout on upgrade or activation; a fresh installation defaults to skills." — [docs/integrations/copilot.md](https://github.com/github/spec-kit/blob/main/docs/integrations/copilot.md)
- Spelling differs by agent and between docs and product: the reference pages use dotted `/speckit.specify`; Copilot's default mode uses `/speckit-specify`; Codex and others `$speckit-specify`; Kimi `/skill:speckit-specify`. — [docs/integrations/cli.md](https://github.com/github/spec-kit/blob/main/docs/integrations/cli.md)
- Documented friction 1, the model can run a step unasked: the opt-out `--integration-options="--no-model-invocation"` "writes `disable-model-invocation: true` into the core command skills", but the docs record that Copilot CLI's documentation does not list the field, that it was verified only by "a manual check with Copilot CLI 1.0.70", and that "it is not a hard block". Extension skills "stay model-invocable, because mandatory extension hooks rely on the model invoking them", and the option is silently reverted by commands that install, remove or update presets until `specify integration upgrade copilot --force` is run. — [docs/integrations/copilot.md](https://github.com/github/spec-kit/blob/main/docs/integrations/copilot.md)
- Documented friction 2, chat versus terminal: the README, quickstart, existing-project guide and CLI reference each repeat that these are run "in your agent's chat, not your terminal". — [README.md](https://github.com/github/spec-kit/blob/main/README.md); [docs/quickstart.md](https://github.com/github/spec-kit/blob/main/docs/quickstart.md)
- Documented friction 3, automation needs a second product: "Workflow steps require Copilot CLI separately from the IDE setup", and "Headless dispatch adds `--yolo` by default, allowing tools, paths, and URLs without interactive approval." The integration is also "not declared multi-install safe". — [docs/integrations/copilot.md](https://github.com/github/spec-kit/blob/main/docs/integrations/copilot.md)
- What skills changed for context cost (maintainer, 2026-08-31): "In skills mode, the full command bodies are **not** loaded into every session. Only skill metadata is initially available; the relevant `SKILL.md` is loaded when invoked." — [issue #1401](https://github.com/github/spec-kit/issues/1401)
- Next-step affordance before skills: command frontmatter `handoffs` gave UI buttons in VS Code (added in 0.0.80, November 2025), but users noted "the user still needs to manually click/invoke each transition". — [CHANGELOG.md](https://github.com/github/spec-kit/blob/main/CHANGELOG.md); [issue #1966](https://github.com/github/spec-kit/issues/1966)
- Copilot-related issues found by title only (not read): "[Bug]: Speckit skills are not interactive" (opened 2026-09-14, closed 2026-09-28, 4 comments); "[Bug]: specify init writes speckit.manifest.json without the speckit-converge skill it just installed" (opened 2026-08-21, open); "[Feature]: Add artifact, optional, and handoffs to the command manifest schema" (opened 2026-08-19, open). — [issue #4582](https://github.com/github/spec-kit/issues/4582); [issue #4273](https://github.com/github/spec-kit/issues/4273); [issue #4209](https://github.com/github/spec-kit/issues/4209)
- One first-hand Copilot field report (VS Code, Spec Kit 1.0.8, post dated 2026-09-15 and updated 2026-11-09, via page reader): during implement the agent "got slower and slower over time" and the author restarted VS Code and resumed from the task checklist; the initial build including specs, code and docs used about 7,000 credits on a GitHub Pro Plus plan; he estimates Spec Kit adds roughly 20 to 30 percent more tokens than plan mode but has no measurement. — [tauceti.blog](https://www.tauceti.blog/posts/spec-driven-development-with-spec-kit/)
- Cost pressure specific to Copilot (user comment, 2026-06-06): "June 1st change to GH Copilot pricing will bring increased visibility to this issue." — [issue #1401](https://github.com/github/spec-kit/issues/1401)

### Inferences
- For a Copilot user the surface is nine slash entries in a picker that also holds every other skill, with no ordering, numbering or "next" indicator; order lives only in the docs. The four-fold repetition of "chat, not terminal" suggests new users do try the terminal.
- Model-invocable skills mean a quality gate or even implement can start without the user typing it; the opt-out is documented as soft. A tool with fewer, broader commands has less of this exposure.
- The dot-versus-hyphen split means every reference page shows a spelling a Copilot user cannot type as written.

### Inferences
- Three distinct complaints hide under "ceremony": (a) fixed weight regardless of change size (the strongest and most repeated), (b) having to type and wait for each step (pipeline, speckit.go, self-automate requests), and (c) not knowing what to run next or where to go back to (diagram thread, #295). A design with few commands addresses (b) and (c) directly; (a) needs scaling of output to the change, which command count alone does not fix.
- Votes say users do not want less process everywhere: the top requests are for missing steps after implementation (revise, fix, review). The lesson is fewer commands on the way in, with the post-implementation loop built in, not a smaller tool.
- The maintainers have never rejected the diagnosis; they reject changing core. Their fixes are all opt-in and, by their own account, hard to discover. A new tool can make the light path the default and the heavy path the opt-in.
- The 2026 field reports are milder than the 2025 critiques (authors keep using the tool) but repeat the same two points: Markdown review is tiring and the flow is not worth it for small work.
