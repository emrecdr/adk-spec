## What this shows

- **The gate is not passed.** No Copilot model has answered through this stack on this seat. The model defaults in
  `adk_spec/orchestration/settings.py` stay provisional, and the Copilot default is known not to work here.
- **The login and the request path work.** Each request reached Copilot and came back with Copilot's own refusal, read
  correctly. The fault is in which models this seat is served through this route, not in the transport.
- **`mcp` did what the offline probe predicted.** With it installed, the two GPT requests reached Copilot; without it
  they fail before leaving the machine. But neither model answered, so there is no live evidence that adding `mcp`
  buys a working model. It was not added: the experiment branch was deleted.
- **Moving LiteLLM would not change how the request identifies itself.** Read from source, not run: LiteLLM 1.106.2
  and 1.110.2 both send `copilot-integration-id: vscode-chat` and `editor-version: vscode/1.95.0`. Two of the
  refusals name that integrator. So lifting the LiteLLM hold is unlikely to fix this by itself.

### What this decides

- **The Copilot arm answers, on macOS.** `DEFAULTS["copilot"]` in `adk_spec/orchestration/settings.py` is now
  `gpt-4.1`, the first to answer. `gpt-4o` is a second that works, and five times as fast on this one request.
- **`policy.state=enabled` is not a promise.** `claude-haiku-4.5` is enabled and was refused. Only a request tells.
- **`mcp` stays out.** The two enabled models that would need it are the newest GPT ones, and one of them was
  refused with it installed in the first round. A default that works needs no new dependency. This is worth another
  look if a seat is served Responses models only.
