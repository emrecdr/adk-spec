# Models draft the specs; code decides

OpenSpec and GitHub Spec Kit are both small deterministic cores wrapped in prompt text, and a hybrid built on Google ADK should take OpenSpec's change folder and living per-capability spec as its backbone, add Spec Kit's constitution, bounded clarification and cross-artifact analysis as its quality layer, and then do the one thing neither can do because neither owns its runtime: make the gates real in code. OpenSpec's code validates structure and merges requirement deltas into a living spec; Spec Kit's code resolves paths, checks that prerequisite files exist and, optionally, runs a workflow with review gates; in both, the planning boundary, approval, consistency analysis and the check of code against spec are instructions a model is asked to follow. The hybrid adds three things both lack: **stable requirement IDs with base fingerprints, approval and status recorded as data, and ceremony tiers chosen by risk**. Hands-on runs on google-adk 2.15.0 and 2.14.1 under Python 3.14 confirm the ADK mechanics the plan needs: function-node workflows with routes and bounded loops, a human gate that resumes across processes, and an LLM step replaced by Python with the workflow and the downstream node unchanged. Under the owner's three-day cooldown the baseline on 21 November 2026 is still adk_review's pair, **google-adk 2.14.1 and LiteLLM 1.106.2**; google-adk 2.15.0 becomes eligible on 23 November, and the evidence supports keeping the LiteLLM hold, which remains the owner's decision. Version 1 should let models write every artifact and make every judgement while Python owns files, IDs, structural validation, approval gates and the spec merge; later versions move one stage at a time to Python, in an order set by measured cost and failure, each swap proven by replay on recorded inputs. The owner's existing roadmap is right in direction, but its version table cannot be locked under the owner's own rule, its default Copilot model was retired in June, its read-only tool control does nothing in ADK 2.15.0, and most of its Phase 0 and Phase 1 scope, the UI workbench included, should wait. Nothing in this evidence base has run on Windows or against a live model, so the first step is confirmation, not construction.

## OpenSpec enforces a merge, Spec Kit enforces a sequence, and neither checks the code

### OpenSpec: a change folder, a delta grammar and a CLI that serves instructions

OpenSpec 2.1.1 (19 November 2026, npm `@fission-ai/openspec`, Node 22.20 or later) keeps all state in plain files under one `openspec/` root: `specs/<capability>/spec.md` is the source of truth for how the system behaves, and each unit of work is a folder `changes/<name>/` holding `proposal.md`, delta specs, an optional `design.md`, `tasks.md` and a small `.openspec.yaml` ([package.json](https://github.com/Fission-AI/OpenSpec/blob/main/package.json); [spec-driven schema reference](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/schemas/spec-driven/index.md)). A main spec is Markdown with `## Purpose`, `## Requirements`, `### Requirement: <name>` blocks carrying SHALL or MUST, and at least one `#### Scenario:` with WHEN and THEN bullets; a delta spec groups requirement blocks under `## ADDED`, `MODIFIED`, `REMOVED` or `RENAMED Requirements` ([schema.yaml](https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/schema.yaml)). The workflow is twelve re-entrant skills, six of them core (explore, propose, apply, update, sync, archive), and every skill is a thin procedure that calls `openspec status --json` and `openspec instructions <artifact> --json`: **the CLI decides what is next and assembles the prompt from project context, per-artifact rules, an instruction, a template and the paths of dependency files, and the model writes the files** ([propose skill](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-propose/SKILL.md); [instructions.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/commands/workflow/instructions.ts)). The artifact set is a four-node dependency graph declared in YAML (proposal, then specs and design, then tasks, then an apply step that tracks `tasks.md`), with `design.md` written only when a change is cross-cutting, adds a dependency, carries security or migration complexity, or needs technical decisions before coding ([schema.yaml](https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/schema.yaml)).

Two things are real code. `openspec validate` classifies findings as ERROR, WARNING or INFO: a change with no deltas (unless `skip_specs: true`), a requirement without a scenario, duplicate or conflicting operations and a MODIFIED block that drops a scenario the current spec still has are errors, while a missing SHALL or MUST, a scenario without WHEN or THEN and requirement text over 500 characters are warnings that fail only under `--strict` ([validator.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/validation/validator.ts)). `openspec archive` then merges deltas into the main spec deterministically, applying RENAMED, REMOVED, MODIFIED and ADDED in that order, keyed on the exact requirement name and replacing whole blocks ([specs-apply.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/specs-apply.ts)). Everything else is prompt text. The planning boundary is a sentence ("Do not edit project code"), completion is file existence ("`status` is file-existence only"), and the apply skill says of its own guarantees: "These are prompt-level behavior contracts, not enforceable checks" ([propose skill](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-propose/SKILL.md); [apply skill](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-apply-change/SKILL.md)). The default archive skill does not call `openspec archive` at all: the agent merges the specs itself and moves the folder with `mv`, so there are two merge implementations kept in agreement by prose ([archive skill](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-archive-change/SKILL.md); [sync skill](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-sync-specs/SKILL.md)). The claim-by-claim check adds that no planning or apply skill tells the agent to run `openspec validate` on a change, that `verify` is advisory and outside the core profile, and that incomplete tasks warn but do not block archive ([validation: OpenSpec claims](../research_notes/Spec%20driven%20framework%20on%20Google%20ADK/validation_openspec_claims.md)).

### Spec Kit: nine prompts around six scripts, with an optional coded workflow

Spec Kit 1.4.3 (19 November 2026) is a Python CLI, `specify`, installed with `uv tool install specify-cli`, that writes an agent-neutral `.specify/` tree (constitution, templates, one script variant in Bash, PowerShell or Python, a hash manifest for upgrades) plus command or skill files in the coding agent's own folder; per-feature artifacts live in `specs/<NNN>-<short-name>/` and are located through a pointer file, `.specify/feature.json` ([pyproject.toml](https://github.com/github/spec-kit/blob/main/pyproject.toml); [core reference](https://github.com/github/spec-kit/blob/main/docs/overview/core.md)). The core flow is nine prompts (constitution, specify, clarify, plan, checklist, tasks, analyze, implement, converge), of which "only `/speckit.specify` is strictly required before `/speckit.plan`"; clarify, checklist and analyze are optional quality gates ([command reference](https://github.com/github/spec-kit/blob/main/docs/reference/agentic-sdd.md)). Each prompt runs one script that returns paths as JSON and then leaves the content to the model. The templates are where Spec Kit is strongest: `spec.md` is built from prioritised, independently testable user stories with Given/When/Then scenarios, numbered `FR-###` requirements and `SC-###` success criteria, and at most three `[NEEDS CLARIFICATION]` markers; `tasks.md` uses a line grammar, `- [ ] T012 [P] [US1] Create User model in src/models/user.py`, grouped into phases per user story ([spec template](https://github.com/github/spec-kit/blob/main/templates/spec-template.md); [tasks prompt](https://github.com/github/spec-kit/blob/main/templates/commands/tasks.md)). Clarify is a bounded interview over a ten-category taxonomy, at most five questions, one at a time, each with a recommended answer; analyze is a read-only report in six passes with CRITICAL to LOW severities, capped at 50 findings; converge re-audits the code against spec, plan and tasks on the rule that "completion claims are not evidence" and may only append remediation tasks ([clarify prompt](https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md); [analyze prompt](https://github.com/github/spec-kit/blob/main/templates/commands/analyze.md); [converge prompt](https://github.com/github/spec-kit/blob/main/templates/commands/converge.md)).

Spec Kit's code enforces little of this. The scripts hard-fail when `plan.md`, `spec.md` or `tasks.md` is missing and name the command to run next, and a workflow engine can run specify, plan, tasks and implement with two coded review gates, but that bundled workflow omits clarify, checklist, analyze and converge ([check-prerequisites.sh](https://github.com/github/spec-kit/blob/main/scripts/bash/check-prerequisites.sh); [speckit workflow](https://github.com/github/spec-kit/blob/main/workflows/speckit/workflow.yml)). Feature numbering, the constitution gate ("ERROR if violations unjustified"), counting unchecked checklist items before implement, marking tasks done and even dispatching extension hooks are instructions to the model; the hook text itself warns that "Emitting the block alone does not run the hook" ([plan prompt](https://github.com/github/spec-kit/blob/main/templates/commands/plan.md); [implement prompt](https://github.com/github/spec-kit/blob/main/templates/commands/implement.md)). After delivery Spec Kit takes no position: its docs describe four persistence models and state "None is the default, and none is required by Spec Kit", its own repository gitignores `specs/`, and core "has no dedicated command that automatically reconciles differences among `spec.md`, `plan.md`, and `tasks.md`" ([persisting specs](https://github.com/github/spec-kit/blob/main/docs/how-to/persisting-specs.md); [evolving specs](https://github.com/github/spec-kit/blob/main/docs/how-to/evolving-specs.md)).

| Concern | OpenSpec 2.1.1 | Spec Kit 1.4.3 |
|---|---|---|
| Enforced in code | Structural `validate` with three severities; deterministic delta merge in `openspec archive`; state computed from files; prompt assembly | Path resolution and required-file checks; template layering; hash-manifest upgrades; optional workflow engine with two review gates |
| Asked of the model only | Planning boundary, task check-off, the skill-driven merge and folder move, verify, design-when-needed | Feature numbering, constitution gate, clarify and marker limits, checklist counting, analyze, converge, hook dispatch |
| Is approval recorded? | No; the review between propose and apply is conversational | Only inside the optional workflow engine |
| Identity of a requirement | Its header text; no stable IDs | `FR-###`, `SC-###`, `T###` by prompt convention; no script validates them |
| Spec after delivery | Deltas fold into one living spec per capability | Per-feature folder; persistence is a team convention |
| Code checked against spec | LLM `verify`, report-only | LLM `converge`, appends tasks |

Sources for the table: [OpenSpec validator](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/validation/validator.ts), [OpenSpec requirement parser](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/parsers/requirement-blocks.ts), [OpenSpec verify skill](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-verify-change/SKILL.md), [Spec Kit common.sh](https://github.com/github/spec-kit/blob/main/scripts/bash/common.sh), [Spec Kit extension API](https://github.com/github/spec-kit/blob/main/docs/extensions/api.md), [validation: Spec Kit claims](../research_notes/Spec%20driven%20framework%20on%20Google%20ADK/validation_speckit_claims.md).

### Field reports: both fail at the hand-back after implementation

The one structured head-to-head (same backend feature, same codebase, tests run in February 2026 on Spec Kit 0.1.6 and OpenSpec 1.2.0) scored **OpenSpec 4.00 and Spec Kit 2.77 out of 5**, with OpenSpec ahead on specification quality, review checkpoints and mid-feature correction, and the author noting that OpenSpec "sometimes assumes context and adds rationale to decisions you didn't make" ([Kdosha on ranthebuilder.cloud](https://ranthebuilder.cloud/blog/i-tested-three-spec-driven-ai-tools-here-s-my-honest-take/)). Both tools have since had major releases, so version-specific complaints are dated; the structural findings are not. Spec Kit's measured failure is volume that does not scale with the change: **2,577 lines of Markdown and about 3.5 hours of review for 689 lines of code**, against 8 minutes of agent time and 24 minutes of review and testing without specs ([Scott Logic](https://blog.scottlogic.com/2025/11/26/putting-spec-kit-through-its-paces-radical-idea-or-reinvented-waterfall.html)). Its per-feature folders also go stale: each "is only true for the week it was written", and the most-upvoted issue in the project's history asks for a way to update existing specs ([Perez](https://dev.to/alfredoperez/living-specs-in-speckit-3a3j); [spec-kit issue #1191](https://github.com/github/spec-kit/issues/1191)). OpenSpec has the right structure but a manual fold-back that practitioners skip ("skipping it is how the record dies"), and its own lead maintainer has an open issue stating that "a deterministic merge isn't realistic to support well" on name-keyed blocks, after 46 fix commits to the merge code since June ([Perez](https://dev.to/alfredoperez/living-specs-in-speckit-3a3j); [OpenSpec issue #2033](https://github.com/Fission-AI/OpenSpec/issues/2033)). Thoughtworks moved OpenSpec to Trial in November 2026 for its spec-anchored workflow while cautioning that keeping the persistent spec current takes discipline; Spec Kit sat in Assess in April 2026 with cautions about verbose Markdown and context rot ([Thoughtworks Radar: OpenSpec](https://www.thoughtworks.com/radar/tools/openspec); [Thoughtworks Radar: Spec Kit](https://www.thoughtworks.com/radar/languages-and-frameworks/github-spec-kit)). The only controlled measurement of what a retained spec buys is a small pilot: a spec baseline did not help reviewers find more drift (recall 0.525 against 0.518) and nearly doubled review time (48.4 against 26.7 minutes), but it made findings attributable to a stated requirement (0.81 against 0.00) ([InfoQ](https://www.infoq.com/articles/when-spec-driven-development-pays-off/)). A retained spec pays in accountability, not in defect count, which argues for keeping it small.

## The hybrid keeps OpenSpec's backbone and Spec Kit's quality layer, and adds what both lack

### What to adopt from each, and what to design around

From OpenSpec the hybrid takes the change folder as the unit of work, delta specs that fold into one living spec per capability, the "status says what is next, instructions return the prompt" pattern, the three-level severity policy with fix-oriented messages, and explicit escape hatches (`skip_specs`, design only when its conditions apply) ([OpenSpec CLI reference](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md)). From Spec Kit it takes the constitution read at run time by pointer and never copied into templates, bounded interaction budgets (three markers, five questions, three validation rounds, fifty findings), numbered identifiers, the task line grammar, the read-only analysis passes and the principle that checked boxes are not evidence ([constitution prompt](https://github.com/github/spec-kit/blob/main/templates/commands/constitution.md); [specify prompt](https://github.com/github/spec-kit/blob/main/templates/commands/specify.md)). The weaknesses to design around are shared or complementary: requirement names as primary keys (OpenSpec cannot rename a scenario without the old name reading as dropped), approval that exists nowhere on disk, lifecycle state encoded as directory position, cross-artifact and code-against-spec checking that is LLM-only and advisory, and one workflow size for every change ([OpenSpec issue #1697](https://github.com/Fission-AI/OpenSpec/issues/1697); [OpenSpec issue #1683](https://github.com/Fission-AI/OpenSpec/issues/1683); [Böckeler on martinfowler.com](https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)). Three corrections to the owner's earlier comparison belong here because the design leans on them: Spec Kit's clarify taxonomy has **ten categories, not seven**; its constitution is amendable and versioned, not immutable; and OpenSpec's silent loss of scenarios on parallel archives was closed in version 1.6.0, leaving, by a reading of the code that was not run, a narrower residual risk when a stale MODIFIED block keeps every scenario name but overwrites changed text ([validation: Spec Kit claims](../research_notes/Spec%20driven%20framework%20on%20Google%20ADK/validation_speckit_claims.md); [validation: OpenSpec claims](../research_notes/Spec%20driven%20framework%20on%20Google%20ADK/validation_openspec_claims.md)).

### Artifacts and formats

The owner's design already names the planning root `.spec/` and the product `adk-spec`; the table keeps those names and trims the artifact set to what the evidence supports for a first version.

| Artifact | Format and content | Taken from | Why |
|---|---|---|---|
| `.spec/constitution.md` | Short, versioned, amendable; scope, domain context, technology versions, coding standards, repository structure; each rule with its reason | Spec Kit | The contents Thoughtworks teams found useful; loaded live, never copied |
| `.spec/config` | Strictly loaded: context, per-artifact rules, default tier, per-stage mode (`llm` or `python`) | OpenSpec, adk_review | OpenSpec ignores a misspelled schema field without reporting it; adk_review refuses unknown keys |
| `.spec/specs/<capability>/spec.md` | `## Purpose`, `## Requirements`, `### REQ-<CAP>-NNN: <name>`, one SHALL or MUST sentence, `#### Scenario:` with WHEN and THEN | OpenSpec plus stable IDs | The living truth; IDs remove rename and typo fragility |
| `changes/<id>/change` (state file) | Tier, status, approvals (who, when, SHA-256 of approved files), base fingerprint per modified requirement, `skip_specs` | New | Records what neither framework records |
| `changes/<id>/brief.md` | Why, what changes, non-goals, capabilities touched, impact, assumptions, at most three `[NEEDS CLARIFICATION]` | Both | OpenSpec's proposal with Spec Kit's marker budget |
| `changes/<id>/specs/<capability>/spec.md` | ADDED, MODIFIED, REMOVED, RENAMED by requirement ID; bugfix changes add "unchanged behaviour" clauses | OpenSpec, Kiro | Deltas say what changes; the clause says what must not |
| `changes/<id>/design.md` | Context, goals and non-goals, decisions with alternatives, risks; only when OpenSpec's four conditions apply | OpenSpec | Conditional by rule, not by habit |
| `changes/<id>/tasks.md` | `- [ ] T001 [P] [REQ-...] description, file path, how to verify`; tests inside each group | Both | Spec Kit's grammar with OpenSpec's per-task verification |
| `changes/<id>/reports/` | Generated `check.md` and `verify.md` | Spec Kit | Findings persist instead of living in chat |

Sources: [Thoughtworks Radar: Spec Kit](https://www.thoughtworks.com/radar/languages-and-frameworks/github-spec-kit), [OpenSpec schema reference](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/schemas/schema-yaml.md), [adk_review reference notes](../research_notes/Spec%20driven%20framework%20on%20Google%20ADK/adk_review_reference_setup.md), [Kiro blog](https://kiro.dev/blog/specs-bugfix-and-design-first/), [OpenSpec schema.yaml](https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/schema.yaml).

Markdown stays the format of record because it is what reviewers read in a pull request, but requirement-bearing files follow a small strict grammar that Python both renders and parses. Agents return typed objects and Python renders them, so model output never needs repair by regex; the parser exists for hand edits and for the merge. The owner's design makes the five EARS sentence patterns mandatory; the checks show EARS is a writing discipline by Alistair Mavin (Rolls-Royce, 2009), not a Kiro invention, and nothing verified shows it compiles to tests, so it belongs in the template as guidance and in the validator as a warning at most ([EARS](https://alistairmavin.com/ears/); [validation: standards and UI claims](../research_notes/Spec%20driven%20framework%20on%20Google%20ADK/validation_standards_and_ui_claims.md)).

### Lifecycle, gates and keeping specs alive

The lifecycle is propose (triage, brief, bounded clarification, delta specs), plan (design when needed, tasks), check, approve, implement, verify and archive. What differs from both sources is who enforces each gate.

| Gate | Enforced by | Blocks? |
|---|---|---|
| Structure of specs, deltas and tasks; ID uniqueness; every changed requirement has a scenario | Python validator, ERROR, WARNING and INFO as in OpenSpec | Errors always; warnings under `--strict` |
| Clarification budget (three markers, five questions) | Python counts; a model words the questions | Yes |
| Cross-artifact analysis (duplication, ambiguity, gaps, contradiction, constitution) | Model in version 1, written to `reports/check.md` | CRITICAL findings block approval |
| Approval of the plan | A recorded fact: approver, time, hash of each approved file; the next stage's first node compares hashes | Yes; any edit after approval voids it |
| Verification of the implementation | Model judges the diff per requirement; Python keeps only findings that quote real diff lines | A missing or failed check never reads as a pass |
| Archive | Python compares base fingerprints, merges by ID, validates the merged spec, records status | Yes; on a fingerprint mismatch it stops and asks for the delta to be refreshed |

Specs stay alive because the fold-back is a coded step with a recorded outcome, not a habit: archive is the only way a change reaches `archived` status, and a CI check can fail when a change is `verified` but not folded. The fingerprint (SHA-256 of the LF-normalised requirement block captured when the delta was drafted) is the idea a production OpenSpec user proposed in the maintainer's own issue, and it closes the residual overwrite case that name-only matching leaves open ([OpenSpec issue #2033](https://github.com/Fission-AI/OpenSpec/issues/2033)). The owner's roadmap goes further, to a three-way `diff3` merge with a conflict-resolving agent; because the original data-loss bug no longer exists upstream, stopping on mismatch is enough for a first version and the three-way merge can wait for evidence that conflicts are frequent.

### Right-sizing: three tiers and a way out

The reference critique of first-generation tools names one workflow for every size as a root failure; Kiro added a separate bugfix path after launch because its single flow "was not flexible enough", and Spec Kit ships a `lean` preset that replaces five commands with short prompts ([Böckeler](https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html); [Kiro blog](https://kiro.dev/blog/specs-bugfix-and-design-first/); [lean preset](https://github.com/github/spec-kit/blob/main/presets/lean/README.md)). The owner's design has `lean`, `standard` and `strict` profiles but gives no criteria for choosing one. The criteria that recur across practitioners are change size, ambiguity of intent, regression risk, number of components touched, lifetime of the behaviour and whether an audit trail is owed ([O'Reilly Radar](https://www.oreilly.com/radar/when-ai-writes-the-code-specifications-need-an-exit-strategy/); [InfoQ](https://www.infoq.com/articles/when-spec-driven-development-pays-off/)).

| Tier | Use when | Artifacts | Gates |
|---|---|---|---|
| None | Typo, cosmetic change, throwaway prototype | No change folder; triage says so and exits | None |
| `lean` | One small, well-understood change or bug in one capability | A brief with its delta inline (bugfix: current, expected and unchanged behaviour) and a short task list | Structure, one approval |
| `standard` (default) | A feature touching one or a few capabilities, or any ambiguity | Brief, delta specs, tasks; design when its conditions apply | Clarify, check, approval, verify |
| `strict` | Many capabilities, high regression risk, or an owed audit trail | Standard plus mandatory design and a reviewer-owned checklist | Zero critical findings; second approver |

Version 1 implements `lean` and `standard`; `strict` waits until a real change needs it.

### Layout: a pure core, one I/O layer, one ADK layer

What transfers from adk_review nearly verbatim is the toolchain (`pyproject.toml` structure, `exclude-newer`, uv workspace, Ruff and Pyrefly settings, the three-OS CI file with actions pinned by commit, Dependabot with a three-day cooldown and separate pull requests for ADK and LiteLLM), the package-root pattern (an `__init__.py` that imports nothing, `agent.py` exporting both `app` and `root_agent`, no nested `agent.py`, builders that build nothing at import), the settings and model-factory split, the login command, the plugin roster and the fake-model test harness ([adk_review reference notes](../research_notes/Spec%20driven%20framework%20on%20Google%20ADK/adk_review_reference_setup.md)). What does not transfer is everything a spec framework must do that a read-only reviewer never does: write tools, command execution, human pauses, persistent sessions. Each of those needs its own evidence, which is why the hands-on runs matter.

The owner's design asks for a hexagonal layout (`domain`, `ports`, `adapters/llm`, `adapters/python`, `orchestration`, `interfaces`). The intent, a core with no ADK or LiteLLM imports, stands and is the property that makes migration cheap. The recommended shape keeps the owner's names with one-way imports, `domain` (Pydantic models, grammar, parser, renderer, validator, merge, hashing; no I/O), `workspace` (the `.spec` tree, atomic LF writes, path policy, git and process runner), `orchestration` (settings, model factory, one file per stage, graph builder, plugins, run helper) and `interfaces` (the command and the login), and leaves out `ports/` and the twin adapter trees. ADK's typed node contract already is the port: the hands-on swap of an LLM step for a Python function changed one node definition and nothing else, so a second abstraction buys nothing yet ([hands-on verification](../research_notes/Spec%20driven%20framework%20on%20Google%20ADK/adk_hands_on_verification.md)). Layering should be enforced the way adk_review does it, by a test that reads the syntax tree plus probes that import the core in a fresh interpreter with `google` blocked, because a static check cannot see what a lazy import loads.

### The workflow: typed stage nodes, files as the record, sessions disposable

In ADK 2.x the supported way to mix model steps and code is `Workflow`, a graph whose nodes are LLM agents, plain functions or nested workflows; `SequentialAgent`, `LoopAgent` and `ParallelAgent` are deprecated ([ADK graph workflows](https://adk.dev/graphs/); [ADK custom agents](https://adk.dev/agents/custom-agents/)). The hands-on runs confirm what the plan needs on both versions: a function becomes a node by appearing in `edges`; the previous node's output arrives as `node_input`; routing is `Event(route=...)` plus a route table; a loop is a back-edge that **the engine does not bound**, so each loop carries its own counter in state; and one node may emit only one output ([hands-on verification](../research_notes/Spec%20driven%20framework%20on%20Google%20ADK/adk_hands_on_verification.md)).

The recommended shape follows adk_review's "one builder, two shapes" and OpenSpec's file-system state: each command (`propose`, `plan`, `check`, `approve`, `verify`, `archive`, `status`, `validate`) is one short workflow run whose first node loads state from `.spec/` and whose last node writes it back, on an in-memory session that is thrown away. This keeps the system of record in git, makes every node swap safe because no run is ever paused across a deployment, and keeps session content out of `.adk/session.db`, where ADK's own command-line tools write it by default. It also sorts the two kinds of human gate. Approval that can take days is a recorded fact checked by a Python node. Questions inside a run use `RequestInput`, which the runs show works with no model and no resumability configuration, and resumes from a new process with `SqliteSessionService` when that is wanted later. The client must answer with a function response named `adk_request_input` carrying the interrupt ID: **a typed "yes" forwarded as plain text silently restarts the pipeline from the start and overwrites state** ([hands-on verification](../research_notes/Spec%20driven%20framework%20on%20Google%20ADK/adk_hands_on_verification.md)).

Every drafting or judging stage uses the agent shape adk_review has run on both arms: an `LlmAgent` with an instruction built from state placeholders, `include_contents="none"`, a Pydantic `output_schema`, an `output_key`, and no tools. Context for existing codebases is gathered by Python nodes and by one separate read-only explorer agent that has tools and no schema, since no evidence exists of a schema combined with tools having been exercised on a Copilot model ([Copilot and Gemini notes](../research_notes/Spec%20driven%20framework%20on%20Google%20ADK/copilot_and_gemini_on_adk.md)). Three run results shape error handling. Invalid structured output raises `pydantic.ValidationError` and ends the run with no retry; a node `RetryConfig` does retry but sends the same request without the error; and a root agent with `output_schema` but no `output_key` is not validated at all. So every schema agent sets `output_key`, a plugin of the adk_review kind turns a mismatch into that stage's own recorded failure, and a Python checker routes back at most twice with the findings in state. Plugins go on `App(plugins=[...])`; because no agent, model or tool hook fires around a plain function node, any policy that must cover Python nodes lives in the node's own code ([hands-on verification](../research_notes/Spec%20driven%20framework%20on%20Google%20ADK/adk_hands_on_verification.md)). Spec files are written by the `workspace` layer, not by ADK's artifact service, whose on-disk layout is `apps/<app>/users/<user>/sessions/<session>/artifacts/<name>/versions/<n>/`, the wrong shape for files that must sit in a repository.

Where the runs overrule the documentation-based notes, the runs win. The ADK 2.0 migration page says custom `_run_async_impl` overrides are bypassed; they executed in all three placements. The resume page documents `run_async(invocation_id=...)`; that call does not answer a `RequestInput`. The notes pair human input with `ResumabilityConfig`; it is not required. The notes present `DatabaseSessionService` as the SQLite option; it needs the `db` extra, and the class that works on a plain install is `google.adk.sessions.sqlite_session_service.SqliteSessionService` ([hands-on verification](../research_notes/Spec%20driven%20framework%20on%20Google%20ADK/adk_hands_on_verification.md); [ADK 2.0 migration page](https://adk.dev/2.0/); [ADK resume page](https://adk.dev/runtime/resume/)).

### Two provider arms, four mechanisms

One settings module reads `SPEC_PROVIDER`, `SPEC_MODEL` and per-role overrides and imports nothing heavy; one factory module alone builds models. The Copilot arm must pass a `LiteLlm(model="github_copilot/<name>")` instance, because ADK's registry sends a bare `gpt-*` string to OpenAI's own API ([google-adk 2.15.0 files](https://pypi.org/project/google-adk/2.15.0/#files)). The LiteLLM settings adk_review measured carry over on 1.106.2: `LITELLM_MODE=PRODUCTION` and `LITELLM_LOCAL_MODEL_COST_MAP=True` set before import, `litellm.disable_copilot_system_to_assistant = True`, `_skip_mcp_handler=True`, a log filter that hides bearer tokens, retries set on the model and not on the request, one deadline over a call and its retries, and `FallbackModel` with 408 added to its retriable codes, since the default set excludes timeouts and the class is marked experimental ([adk_review reference notes](../research_notes/Spec%20driven%20framework%20on%20Google%20ADK/adk_review_reference_setup.md); [Copilot and Gemini notes](../research_notes/Spec%20driven%20framework%20on%20Google%20ADK/copilot_and_gemini_on_adk.md)). Login stays a separate blocking command: LiteLLM's device flow polls for only 60 seconds and refuses to start inside a running event loop ([litellm 1.106.2 files](https://pypi.org/project/litellm/1.106.2/#files)).

Three facts change the defaults. **`gpt-4.1`, the default in adk_review and in the roadmap, was retired from Copilot on 1 June 2026**, and adk_review's Gemini default, `gemini-2.5-flash`, is deprecated and reroutes to `gemini-3.5-flash-lite` from 1 December 2026 ([GitHub supported models](https://docs.github.com/en/copilot/reference/ai-models/supported-models); [Google Gemini models](https://aistudio.google.com/docs/models)). Every current Copilot GPT model is served only on the Responses API in LiteLLM's map, and for the GPT-5 and GPT-6 reasoning families LiteLLM refuses any temperature other than 1 unless parameters are dropped, while Copilot's Claude models stay on chat completions; adk_review's blanket temperature-zero rule therefore cannot be copied, and sampling has to be decided per model in the factory ([litellm 1.110.2 files](https://pypi.org/project/litellm/1.110.2/#files)). And the LiteLLM route is unofficial from GitHub's side: it signs in with a fixed client ID and labels its traffic as VS Code's Copilot Chat, usage is billed to the seat in AI credits (1,500 a month on Pro), and GitHub publishes no numeric rate limits ([litellm 1.110.2 files](https://pypi.org/project/litellm/1.110.2/#files); [GitHub usage-based billing](https://docs.github.com/en/copilot/concepts/billing/usage-based-billing-for-individuals); [GitHub rate limits](https://docs.github.com/en/copilot/concepts/rate-limits)). That argues for a token ledger with a ceiling from day one, a first-class Gemini arm as the fallback path, and a written position from GitHub before wide use.

Structured output is where the arms differ mechanically. Without tools, ADK sends a strict JSON schema to every non-Gemini LiteLLM model after forcing every property to be required; with tools, Copilot GPT models and Gemini on Google Cloud receive schema and tools together, while Copilot Claude models and Gemini with an AI Studio key get a `set_model_response` tool instead ([google-adk 2.15.0 files](https://pypi.org/project/google-adk/2.15.0/#files)). Keeping schema agents tool-free in version 1 collapses those four mechanisms to two. Model-facing schemas follow adk_review's measured rules: plain `BaseModel` (a model with `extra="forbid"` drew a 400 from Gemini's `response_schema`), nullable fields in place of optional ones, `Literal` scales, a description on every field, and a test that checks each arm's converted schema.

### Windows and macOS: the project is its own canary

ADK's CI runs on Ubuntu only, so "supports Python 3.14" does not extend to Windows or macOS, and an open pull request shows the consequence: on Windows a timed-out `LocalEnvironment` command references `signal.SIGKILL`, which does not exist there ([ADK CI workflow](https://github.com/google/adk-python/blob/v2.15.0/.github/workflows/continuous-integration.yml); [adk-python PR #8152](https://github.com/google/adk-python/pull/8152)). `ExecuteBashTool` refuses to run on Windows, and `LocalEnvironment` passes command strings to `cmd.exe` on one system and `/bin/sh` on the other ([ADK docs, full text](https://adk.dev/llms-full.txt); [LocalEnvironment source](https://github.com/google/adk-python/blob/v2.15.0/src/google/adk/environment/_local_environment.py)). A Windows-first framework should therefore run git and any other program through its own layer, which adk_review already has: full path from absolute `PATH` entries, argv lists, explicit encodings, a timeout, and `taskkill /F /T /PID` for the process tree.

The remaining rules are known and cheap. Pin 3.14 in both `.python-version` and `requires-python`, because uv 0.13 downloads 3.15 by default ([uv changelog](https://github.com/astral-sh/uv/blob/main/CHANGELOG.md)). Set `PYTHONUTF8=1` in the documented launch environment, because UTF-8 mode is not the default until 3.15 and ADK's own docs warn that LiteLLM may read cached files as cp1252 on Windows ([Using Python on Windows](https://docs.python.org/3.14/using/windows.html); [ADK docs, full text](https://adk.dev/llms-full.txt)). Ship `* text=auto eol=lf`, write every file with `newline="\n"` and hash after normalising CRLF, so a fingerprint is the same on both systems ([gitattributes](https://git-scm.com/docs/gitattributes)). Use lowercase ASCII for IDs that become directory names, compare paths case-insensitively, and reject reserved names with `ntpath.isreserved()`, which also works on macOS and catches `CON.md`, trailing dots and spaces ([os.path](https://docs.python.org/3.14/library/os.path.html)). Leave the default Proactor event loop alone and never enable reload. On Windows ARM64 there is no LiteLLM wheel, so those machines need an x64 interpreter (`UV_PYTHON_ARCH=x86_64`). Document plain `uv run` commands, one per line: the roadmap's PowerShell line joins commands with `;`, which runs every command whatever fails, and `&&` exists only from PowerShell 7 ([PowerShell chain operators](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_pipeline_chain_operators)). CI runs on `windows-latest`, `macos-latest` and `ubuntu-latest`.

### Testing and evaluation: offline by default, live by decision

The offline suite uses adk_review's technique: a fake model registered with ADK's model registry, so the real factory, loader, runner, workflow, callbacks and plugins all run and nothing is patched. The hands-on runs confirm the simpler variant too: a `BaseLlm` subclass with scripted replies inside `InMemoryRunner(node=workflow)` ran five tests in 0.6 seconds with every warning turned into an error, including a pause-and-resume test and an assertion that a Python replacement made zero model calls ([hands-on verification](../research_notes/Spec%20driven%20framework%20on%20Google%20ADK/adk_hands_on_verification.md)). The Copilot arm is tested offline at two levels, with ADK's LiteLLM client replaced and with only the HTTP send replaced, because a LiteLLM regression once passed every test above that level ([adk_review reference notes](../research_notes/Spec%20driven%20framework%20on%20Google%20ADK/adk_review_reference_setup.md)). The pure core gets ordinary pytest: render and parse round trips, every validator rule, and merge cases including a stale fingerprint.

Live measurement follows adk_review's scripts, not ADK's evaluation sets, for now: a labelled set of change requests with planted defects (an ambiguity, a contradiction between brief and delta, a requirement with no task), run several times per arm, scored on whether each stage catches them, with answers recorded so a fake can replay them. `adk eval` and `AgentEvaluator` are a reasonable later addition, but nothing here has run them, the `eval` extra cannot be installed from wheels alone because `rouge-score` ships only as source, and the efficiency metrics the roadmap wants as a gate are informational only, so a threshold on them raises an error ([Windows, macOS, Python 3.14 and uv notes](../research_notes/Spec%20driven%20framework%20on%20Google%20ADK/windows_macos_python314_uv.md); [validation: ADK claims](../research_notes/Spec%20driven%20framework%20on%20Google%20ADK/validation_adk_claims.md)). A token ledger plugin gives per-agent cost without them.

### Version 1: models do the work, Python holds the rails

The rule for version 1 is simple to state: Python does what OpenSpec and Spec Kit already do in code (paths, preconditions, structural validation, the delta merge) plus the three things neither does and every field report misses (IDs, recorded approval, write boundaries); a model does everything else.

| Stage | Version 1 | Contract | Later |
|---|---|---|---|
| Load, IDs, render, write, status | Python | Typed state from `.spec/` | Stays |
| Triage (tier and capabilities touched) | Model | `Triage` | Rules first, model on doubt |
| Explore existing code | Model with read-only tools | Notes in state | Capability-to-path map in Python |
| Brief, delta specs, design, tasks | Model | One Pydantic type each | Stays with models |
| Clarify | Model picks and words questions; Python counts | Answers in state | Python finds the gaps |
| Structure gate | Python | Findings with severity | Stays |
| Check (cross-artifact analysis) | Model | `Findings` | Coverage and placeholder passes to Python |
| Approve | Python | Hashes in the state file | Stays |
| Verify | Model judges the diff; Python grounds quotes | `Findings` | Python gathers test evidence first |
| Archive merge | Python | Merged spec | Stays |

The merge is the one place this departs from the roadmap, which starts it as an LLM agent. With stable IDs and a parser already present the merge is a small function, it rewrites the source of truth, and OpenSpec's experience with two merge paths is the cautionary case, so it is cheaper and safer in code from the start. The second departure is scope: version 1 does not edit application code. Both source frameworks hand implementation to the developer's coding agent, adk_review offers nothing to copy for write or execute tools, ADK's own execution environment mishandles Windows timeouts, and the roadmap itself lists "Phase 1 apply scope" as open. Version 1 produces approved specs and tasks that a coding agent such as Copilot in VS Code implements, then verifies the result from the diff, a stage where adk_review's read-only git layer and its rule that a finding must quote real diff lines apply directly.

The build order is confirmation first: a live smoke test of two or three candidate models per arm on a schema-bound call, and the offline suite on a real Windows machine. Then the skeleton with CI and the ported provider code; the pure core with no ADK import; `propose` for both tiers against the fake model; `plan`, `check`, `approve` and `status`; `verify` and `archive`; and a first live measurement on both arms.

### Migration: one stage per release, chosen by the ledger, proven by replay

Google's own account of ADK 2.0 gives the reason to migrate: "Executing deterministic logic via an LLM loop incurs high token costs and latency". The research notes derive an order of value from it: orchestration and gating first, then validators and parsers, then file and git operations, with drafting and judgement left to the model ([Why we built ADK 2.0](https://developers.googleblog.com/en/why-we-built-adk-20/); [LLM to Python migration notes](../research_notes/Spec%20driven%20framework%20on%20Google%20ADK/adk_llm_to_python_migration.md)). Version 1 already has the first group in code, so the ordered path starts at the second.

| Order | Step moved to Python | What stays with the model |
|---|---|---|
| 1 | Coverage and placeholder passes of `check` (requirement to task to scenario by ID, duplicates, orphan tasks, leftover markers) | Contradiction, ambiguity and constitution passes |
| 2 | Evidence for `verify` (run the project's tests through the process layer, map results to requirement IDs) | Judging what the evidence leaves open |
| 3 | Gap detection for `clarify` (markers, empty sections, unassigned capabilities) | Wording the questions |
| 4 | Triage by rules on measurable inputs | Cases the rules route to it |
| 5 | Context selection through a capability-to-path map | Exploration the map cannot answer |
| 6 | Drift check between living specs and code (new capability) | Explaining a drift |

The next candidate is chosen by five tests applied to the ledger and the gate records: the step's output is a function of its input that can be written down without judgement; a deterministic oracle for it already exists; its tokens multiplied by its frequency rank high; its failures (schema mismatches, retries, human overrides at the gate) rank high; and the Python needed is small. A step that fails the first test stays with the model whatever it costs.

Each swap is kept safe by the contract and by replay. The node keeps its name, its typed input and output and its state keys; downstream nodes annotate `node_input` with the Pydantic type, because an unannotated node can receive a dict from the LLM version and a model instance from the Python one ([hands-on verification](../research_notes/Spec%20driven%20framework%20on%20Google%20ADK/adk_hands_on_verification.md)). A recorder plugin keeps real inputs and outputs of the LLM stage for a number of runs; the Python candidate is run over those recordings offline and disagreements are read by a person; the offline suite asserts the migrated step makes zero model calls; the stage's mode is flipped in configuration, with the model kept one release as a route for inputs the code declines; and the labelled set is re-run live on both arms. Because every model stage in this design is pure (it returns data, Python writes), replay needs no in-graph shadow machinery. If an in-graph shadow is built later, the registry must compare the two implementations' schemas itself: ADK's graph rule 8 compares the two ends of one edge, and only when both are set ([validation: ADK claims](../research_notes/Spec%20driven%20framework%20on%20Google%20ADK/validation_adk_claims.md)). Code that reads the event stream should use `node_info.path`, `output` and state, never the author, the content field or an event count, all of which differ between an LLM node and a function node or between ADK versions.

## The existing roadmap is right in direction; its baseline and skeleton need correcting and half its early scope should wait

### What stands

The roadmap's main decisions survive the evidence: living specs with delta changes and a constitution; two first-class provider arms with a settings and factory split; a core free of ADK imports; an LLM-first build migrated stage by stage behind a fixed per-stage contract; human gates as Python `RequestInput` nodes from the first day; ceremony profiles; fingerprint-guarded archive; the three-day cooldown, the Python bound and the uv workspace with the terminal UI as a separate member; `adk web --no_use_local_storage`; and the cross-platform measures taken from adk_review ([owner's roadmap](02-adk-spec-framework-architecture-and-roadmap.md); [adk_review reference notes](../research_notes/Spec%20driven%20framework%20on%20Google%20ADK/adk_review_reference_setup.md)). Its four `ImportError` warnings and all twenty import lines of its skeleton were confirmed against the 2.15.0 source.

### What should be deferred, and the UI

The roadmap carries its twenty-four improvement options into the design, deferring some only by phase, and schedules a large share of them in Phases 0 and 1. Under the owner's standing rule, the following wait until a measured need appears, each for the same reason, a large or unproven mechanism for a benefit the first version does not yet need: the knowledge pack with its lock file and BM25 retrieval (its "about 10x capacity" figure is Anthropic's number for a different system); workflow overlays, contracts and roadmap files; nested `assess` and `bugfix` workflows beyond the `lean` tier; git worktrees and parallel task workers; `ModelConsultTool`, skills and the prompt optimizer; memory services, A2A federation and the MCP server; Model Armor and the tool-call integrity plugin; rewind; the FastAPI and AG-UI serving layer; and the in-graph shadow registry, replaced for now by replay ([validation: standards and UI claims](../research_notes/Spec%20driven%20framework%20on%20Google%20ADK/validation_standards_and_ui_claims.md)).

The UI workbench is later scope, and the evidence gives no reason to pull it forward. `adk web --no_use_local_storage` already provides a development inspector for the chat shape of the same graph, and a `status` command covers the dashboard's first job. When the workbench is taken up, three of its design assumptions need replacing first: the AG-UI 1.0 SSE binding states that "SSE's `Last-Event-ID` mechanism is not used, and a broken stream cannot be re-entered", so reconnect-and-replay is custom server work; neither ADK nor AG-UI events carry a monotonic sequence number; and Plannotator's documentation does not describe the AST-anchored patches the design credits it with ([AG-UI HTTP and SSE binding](https://docs.ag-ui.com/spec/1.0/basic/transports/http-sse.md); [Plannotator](https://github.com/backnotprop/plannotator)). The hands-on result adds one hard requirement for any UI: approvals must travel as function responses, never as chat text.

What remains unverified matters as much as what is recommended. **Nothing was run on Windows**: file paths, SQLite locking, the process-tree kill, `uv sync --locked` on Windows x64 and the LiteLLM import there are all untested, and adk_review's Windows CI results were not visible to the researchers. **No model provider was contacted**: whether any current Copilot model honours a strict JSON schema through LiteLLM 1.106.2, whether the Responses bridge works for Copilot's GPT models in that version, how often real models return invalid structured output, and what usage figures Copilot returns are all unknown; adk_review is live evidence only for `gpt-4.1`, a retired model. The hands-on runs used macOS on Apple silicon, the newest dependency versions (not the cooldown set) and a fake model, and did not cover `JoinNode` fan-in, parallel workers, `adk web` or `api_server`, crash recovery, evaluation runs or OpenTelemetry output. Whether LiteLLM releases after 1.107.0 are clean cannot be established from public sources. The comparison of the two frameworks in use rests on one structured evaluation of versions that are now two major releases old, and no independent evaluation of OpenSpec 2.x or Spec Kit 1.x was found. Several figures quoted from adk_review (retry counts, start-up times, the Gemini 400 on `additionalProperties`) are that project's own recorded measurements and were not reproduced.

## Conclusion

The durable asset in both OpenSpec and Spec Kit is not their prompts, which change from release to release, but a file contract and a few hundred lines of code that the prompts orbit. A framework that owns its runtime can extend that code to the places where both ask a model to behave, and that, more than any new artifact, is what the hybrid contributes: a gate is a node, an approval is a hash, a merge is a function. Seen this way the owner's migration plan is less "from LLM to Python" than "judgement stays, procedure leaves", and the typed node contract that ADK 2.x provides is what makes each departure a one-node change that can be replayed before it ships.

The risks that could sink the project sit outside the design. One is supply chain and provider standing: a LiteLLM line with two credential-stealing incidents in 2026 and a Copilot route GitHub has not blessed. The other is that ADK is tested upstream on Linux only, so a Windows-first project will meet regressions before anyone else does. Both are managed by the habits adk_review already has: pin, wait, measure on both arms and on three operating systems before accepting anything. The next useful act is therefore small and concrete: a schema-bound call on two current models per arm, and the offline suite on a Windows machine. What those two results show decides more of the plan than any further design work.
